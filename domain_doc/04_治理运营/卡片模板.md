# 知识卡片模板

**十种卡，一套 frontmatter。** 字段是契约 —— 写卡的人、查卡的脚本、评审的人都按它走，
所以**不要只在某一张卡上加私有字段**：需要新字段就在这里加，然后全库生效。

> **契约管的是「知识卡」。** 下面四类**基础设施文档**不是卡，不套这份字段契约：
> 知识库根文档（`type: 知识库根文档`）、域索引（`type: 域索引`）、
> 治理文档（`type: 治理文档`，`04_治理运营/` 那几份）、索引文档（`type: 索引文档`，
> `01_术语与索引/` 的术语表与缩写表）。它们的 `tags` 走标签字典的「知识库」维。
>
> **为什么单列出来**：把治理文档也塞进卡片契约，就得给「贡献指南」编一个
> `not_applicable` —— 那是为了字段好看而写废话。

## frontmatter（所有卡共用）

```yaml
---

type: 概念卡 | 方法卡 | 流程卡 | 工具卡 | 协议卡 | 组件卡 | 案例卡 | 模板卡 | FAQ卡 | 反模式卡
domain: <域之一 —— 见「域码」表>
subdomain: <子域目录名>
tags: []                          # 从 标签字典.md 里挑，别自造

stages: []                        # 生命周期哪一段：见 标签字典.md 的「阶段」维
summary: <三行以内，检索结果里显示的就是它>
applicable: <什么情况下该用它>
not_applicable: <什么情况下不该用它 —— 这条比上一条更值钱>
prerequisites: []                 # 读这张卡之前要先懂什么（用 id 或标题引用）
```

## 十种卡各自的正文骨架

每张卡**只写下面列的那些段**。多写不是加分 —— 读者要的是判断依据，不是字数。

| 卡型 | 正文段 | 什么算写好了 |
|---|---|---|
| **概念卡** | 定义 → 边界（不是什么）→ 与易混概念的区别 → 出处 | 读完能回答「它和 X 差在哪」 |
| **方法卡** | 适用场景 → 步骤 → 每步的产物 → 检查清单 → 坑 | 照着能做完一遍 |
| **流程卡** | 触发条件 → 各阶段与负责人 → 每阶段的准入/准出 → 制品 | 能回答「现在卡在哪、谁能放行」 |
| **工具卡** | 干什么 → 常用命令（贴真实命令）→ 常见报错与解法 → 版本坑 | 报错能对号入座 |
| **协议卡** | 信号与时序 → 合法/非法组合 → 检查点 → VIP 怎么接 | 能写出它的 coverpoint |
| **组件卡** | 职责 → 接口（端口/方法）→ 与邻居的边界 → 常见写错 | 能回答「这段逻辑该放谁那」 |
| **案例卡** | 背景 → 约束（时间/人力/工具）→ 选了什么 → 结果 → 复盘 | 说清了**当时为什么这么选** |
| **模板卡** | 用途 → 模板本体 → 填空项的说明 → 误用示例 | 复制粘贴就能用 |
| **FAQ卡** | 现象 → 原因 → 怎么确认 → 怎么解 | 现象描述能被搜到 |
| **反模式卡** | 错误做法 → 为什么诱人 → 后果 → 正确做法 | 说清了「为什么诱人」—— 不诱人就不会有人犯 |

## 写卡的四条纪律

1. **路径引用分两种写法，别混。**
   - **markdown 链接** `[文字](../别的卡.md)` —— 用**真相对路径**，必须能点开。
   - **正文里的 `反引号路径`** —— 用 **`domain_doc/` 根相对**，例如在任何一张卡里都写
     `` `verify/07_度量与报告/覆盖率收敛/` ``，不写 `../../../verify/...`。
   混用的结果：同一张卡里两种路径并存，改目录时改不全，而断的那一半没人发现。
   （指向仓库其它地方的路径 —— `config/`、`src/`、`doc/` —— 按**仓库根相对**写。）


2. **`not_applicable` 必填。** 一条知识说「该用」不难，说清「什么时候别用」才有判断价值。
3. **坑与取舍要具体到能复现。** 「注意时序」不是知识，「`valid` 拉高后数据保持到 `ready`
   才允许变」才是。
4. **引用不抄写。** 厂商文档贴链接就行；卡里只写你的理解和你的坑。
