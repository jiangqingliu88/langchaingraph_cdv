# 评审流程

## 状态机

```
草稿 ──提交评审──► 评审中 ──通过──► 已验证 ──过期──► 过期
                    │                  │              │
                    └──打回──► 草稿 ◄──┘              │
                                                      └──重写──► 草稿
```

**判据**——不是看写了多少，是看这四条：

| 状态 | 准入 |
|---|---|
| `草稿` | 结构合规（frontmatter 字段齐、卡型骨架在） |
| `评审中` | 作者认为「照着能做」或「读完能判断」 |
| `已验证` | **有人按它做过一遍**，且结论一致 |
| `过期` | 依据变了（工具换版、标准改版、方法被证伪） |

`已验证` 的含义要抠死：**不是"有人看过"，是"有人用过"**。看过只能证明它读得通，
用过才能证明它对。

## 谁评审

按域分 Owner（一个人可以管多个域）：

| 域 | Owner | 看什么 |
|---|---|---|
| 01 / 02 | 方法学组 | 定义是否与主流一致、边界是否说清 |
| 03 / 04 | 架构师 | 方法是否可执行、步骤有没有漏 |
| 05 / 06 | 资深 DV | 代码/命令能不能跑、版本坑是不是真的 |
| 07 | 协议负责人 | 时序与合法性 |
| 08 / 09 | 项目经理 | 案例的取舍说清楚没有、数据对不对得上 |
| 10 | 合规负责人 | 条款引用准不准 |

## 打回的常见理由

按出现频率排：

1. **`not_applicable` 没写** —— 只说了什么时候用，没说什么时候别用
2. **内容与已有卡重复** —— 该改那张，不是新建
3. **`已验证` 但没人用过** —— 状态降回 `评审中`
4. **坑点不可复现** —— 「注意时序」这种，退回补具体现象
5. **复制了别的卡** —— 改用 `related`

## 复审周期

`已验证` 的卡**每 12 个月**过一次，或者任一触发条件命中时立刻过：

- 卡里提到的工具发了大版本
- 引用的标准改了版
- 有项目按它做却失败了（这是最硬的触发，**必须**回退状态）
