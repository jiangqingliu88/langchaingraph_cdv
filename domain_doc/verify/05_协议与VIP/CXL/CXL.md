# CXL

> **一句话**：CXL = PCIe 的传输层 + 一套"让设备真正参与内存体系"的扩展——三类子协议
> （`.io` 兼容 PCIe 语义、`.cache` 让设备缓存主机内存、`.mem` 让设备当主机内存用）。
> **验 CXL 的增量，就是验一致性协议与它带来的新组合。**

## 一、CXL 相对 PCIe 增加了什么

| 维度 | PCIe | CXL 增加 |
|---|---|---|
| 设备角色 | 被动的 IO 端点 | 可缓存主机内存 / 可作为主机内存 / 可做加速器 |
| 一致性 | 无（设备不参与 cache 一致性） | **有**，主机与设备间维护一致性 |
| 内存语义 | 只能显式读写 | 设备可直接 load/store 主机内存 |
| 子协议 | 单一事务语义 | `.io` / `.cache` / `.mem` 三个 |
| 物理/链路 | 基础 | **沿用 PCIe PHY 与链路层**（这是 D 的关键前提） |

**关键前提**：CXL 复用 PCIe 的物理层与数据链路层。所以流控、重传、排序这些**基础
依旧来自 PCIe**（见 `verify/05_协议与VIP/PCIe/PCIe.md`）——本卡只写"增量"。

## 二、三类设备类型

| 类型 | 名称 | 能力 | 典型 |
|---|---|---|---|
| Type 1 | `.cache` 设备 | 有缓存但**无**本地内存（如加速器内部缓存） | 智能网卡、加速器 |
| Type 2 | `.cache` + 本地内存 | 有缓存**且**有本地内存（加速器自带显存） | GPU、FPGA 加速器 |
| Type 3 | `.mem` 设备 | **无**主机可缓存的私有缓存，**有**内存扩展 | 内存扩展卡（CXL 内存） |

> 记法：`.io` 是所有 CXL 设备都有的兼容层；`.cache` / `.mem` 是能力叠加。
> 具体枚举编码见 CXL 规范对应章节，**别凭记忆写常量**。

## 三、一致性协议：CXL 的核心增量

CXL 的一致性建立在**主机侧目录**之上：设备缓存主机内存行时，主机知道这一行在哪个设备
以什么状态被缓存。核心是**缓存行的状态与转移**，以及**一致性请求/响应**。

| 概念 | 语义 |
|---|---|
| 缓存行所有权 | 谁持有、以什么状态（独占可写 / 共享只读 / 无效） |
| 一致性请求 | 设备要读/要写主机内存时，向主机一致性代理发起 |
| 一致性响应 | 主机（或 snoop 到的对端）返回数据与状态 |
| 反向失效 | 主机要把某行的所有权收回时，发给持有它的设备 |
| 脏数据回写 | 设备持有独占且已修改的行，被收回时必须回写 |

**验证要点**：一致性协议的状态转移**必须穷举**（每个状态对每种事件），并且
**非法转移要显式声明**——否则"跑通了"只是没碰上。

## 四、合法 / 非法组合

| 组合 | 合法性 | 该不该验 |
|---|---|---|
| 设备独占（已改）的行被反向失效 | 合法 | 必验——必须触发脏数据回写 |
| 多设备共享同一行只读 | 合法 | 必验 |
| 设备持有独占时主机也直接写该行 | **非法** | 断言——会丢更新 |
| 反向失效尚未确认，主机就复用/重分配该行 | **非法** | 断言——经典一致性 bug |
| Type 3 设备被当作可缓存（发 `.cache` 请求） | **非法** | 断言——能力不匹配 |
| 一致性响应携带的状态与请求不符 | **非法** | 断言 |
| 设备崩/链路断时持有脏数据 | 合法但危险 | 必验——断电数据一致性 |
| 主机重映射内存范围时行仍被缓存 | **非法** | 断言——需先失效 |

## 五、检查点

| 层级 | 检查点 | 手段 |
|---|---|---|
| 一致性状态机 | 每个状态 × 每个事件 → 合法目标状态 | 断言 + 形式（穷举转移） |
| 状态机 | 非法转移不出现 | 断言 |
| 回写 | 脏行在失效/收回前必须回写 | scoreboard |
| 反向失效 | 发出到确认之间的行不被复用 | 断言 |
| 设备类型 | 只发与自己能力匹配的子协议请求 | 断言 |
| 内存范围 | 重映射/热插拔前先失效相关行 | 定向用例 |
| 错误处理 | 设备崩溃后主机状态可恢复 | 定向用例 + 错误注入 |
| 复用 PCIe 层 | PCIe 层的流控 / 重传 / 排序仍成立 | 复用 PCIe 卡检查点 |

## 六、VIP 怎么接（通用做法）

| 部件 | 通用接法 |
|---|---|
| 主机侧一致性代理 | 需要能收发一致性请求/响应与反向失效 |
| 设备侧 agent | 按设备类型（Type 1/2/3）配置能力；Type 2/3 需内存模型 |
| 一致性 scoreboard | 维护一份"谁缓存了哪一行、什么状态"的模型，逐事件核对 |
| 内存模型 | `.mem` 场景下需可寻址内存模型，验证 load/store 可见性 |
| 错误注入 | 设备崩溃、链路断、反向失效超时 |

**通用原则**：CXL 的 VIP 必须能**建模主机侧目录的状态**——否则只能验"数据对不对"，
验不了"一致性有没有被维护"。这是 CXL 验证与 PCIe 验证最大的方法差异。

## 七、能写出它的 coverpoint

| 维度 | 覆盖点方向 |
|---|---|
| 设备类型 | Type 1 / 2 / 3，各能发/不能发哪些请求 |
| 一致性状态 | 独占/共享/无效，及其两两转移 |
| 事件类型 | 一致性请求、一致性响应、反向失效、回写 |
| 转移序列 | 多步转移：独占→被失效→回写→共享；多设备交互 |
| 并发 | 多设备同时对同一行；反向失效与主机访问并发 |
| 脏数据处理 | 有/无脏数据被收回；回写时延 |
| 错误 | 设备崩溃时持有/不持有脏数据；反向失效超时 |

```systemverilog
// 一致性覆盖点方向
cp_coh_state : coverpoint coh_state { bins excl = {EXCLUSIVE}; bins shared = {SHARED};
                                      bins invalid = {INVALID}; }
cp_coh_evt   : coverpoint coh_event { bins req = {REQ}; bins rsp = {RSP};
                                      bins back_inval = {BACK_INVAL}; bins wb = {WB}; }
cp_coh_trans : coverpoint coh_state { bins e_to_i = (EXCLUSIVE => INVALID);
                                      bins e_to_s = (EXCLUSIVE => SHARED);
                                      bins i_to_e = (INVALID => EXCLUSIVE); }
illegal_bins t_illegal = (INVALID => SHARED);      // 非法转移显式声明
X_state_evt  : cross cp_coh_state, cp_coh_evt;
cp_dirty     : coverpoint dirty { bins clean = {0}; bins dirty = {1}; }
```

## 八、坑

| 坑 | 为什么诱人 | 修正 |
|---|---|---|
| 只验功能不验一致性 | 数据读写看着都对 | CXL 的价值/风险都在一致性，数据对≠一致性对 |
| 状态机只列状态不列转移 | 状态枚举简单 | 必须穷举转移，尤其非法转移 |
| 忘了脏数据回写 | 干净行收回最省事 | 带脏行的收回才是 bug 高发区 |
| 反向失效不确认就复用 | 时序上"看起来"够了 | 必须等确认，否则丢更新 |
| 设备类型能力不约束 | 所有设备按同一套路验 | Type 3 不该发 `.cache` 请求，得挡住 |
| 把它当 PCIe 验就完了 | 复用 PCIe 用力 | PCIe 层只是地基，一致性是增量，两者都要 |
| 断电/崩溃场景不验 | 跑不出可控的崩溃 | 设备持有脏数据时崩溃是真实风险，要注入 |
| 凭记忆写子协议常量 | 觉得自己记得 | 查 CXL 规范，编码写错会指向另一套语义 |
