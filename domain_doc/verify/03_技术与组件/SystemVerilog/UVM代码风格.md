# UVM 代码风格

> **一句话**：风格规范说「怎么好看」没人听；说「**不这么写会出什么事**」才有人守。
> 本卡每条规则都配一句「防的是什么」—— 没有后果的风格不是规范，是口味。

## 适用场景

- 手写或评审 UVM 环境代码（含模板生成后又手改的部分）
- 制定团队编码规范，需要给每条规则一个**能被反驳的理由**
- 代码评审时判断某处风格问题「值不值得卡」

| 你实际想干的事 | 该去哪 |
|---|---|
| 判断一段逻辑该落在 driver 还是 scoreboard | `../UVM组件/UVM组件职责与边界.md` |
| 生成代码和手改代码怎么共存、怎么回填 | `../../../verify/02_验证方法学/UVM/生成式环境与手改共存.md` |
| 激励的随机与约束怎么写 | `./随机约束.md` |

## 一、命名：后缀与大小写是「免读声明」的类型标签

| 规则 | 例子 | 防的是什么 |
|---|---|---|
| 类 / 变量小写蛇形 | `apb_master_driver` | 大小写混用导致同名不同拼写，搜索搜不全 |
| 句柄加 `_h` 后缀 | `mon_h`、`cfg_h` | 分不清「这是个句柄」还是「这是个值」，误赋值句柄给变量 |
| 端口加 `_p` 后缀 | `in_p`、`out_p` | 端口当普通变量用，方向搞反；连接时左右放错 |
| 宏与参数全大写 | `` `UVM_ERROR ``、`ADDR_WIDTH` | 与变量混淆，宏没被展开时看不出是哪一类名字 |
| 枚举值全大写 | `READ`、`WRITE` | 枚举值与局部变量撞名，作用域出错 |

**判据**：一个人读一行代码，**不看声明**能不能知道 `xxx_h` 是句柄、`xxx_p` 是端口？
能，就省掉了一次「跳过去看声明」；一个上千行的类里，这个省法是数量级的。

> **别把后缀当形式**：`_h` / `_p` 的价值在**跨函数、跨文件**时兑现 ——
> 局部小函数里当然能看清，但句柄常要跨层传递，那时后缀就是唯一的线索。

## 二、缩进与 begin/end：让「作用域」在视觉上可数

| 规则 | 防的是什么 |
|---|---|
| 2 空格缩进，禁用 tab | 不同编辑器 tab 宽度不同，代码在别人机器上错位成迷宫 |
| `begin` 与语句同行 | `begin` 独占一行时，一个 `if` 的作用域要往下数好几屏才看到 `end` |
| `end` 单独一行 | `end` 和语句挤一起，括号匹配全靠临时对齐，漏 `end` 编译报错难定位 |

**这条最容易被当洁癖，理由是**：SV 的作用域靠 `begin`/`end` 而不是大括号，
缩进错了**不会**编译报错 —— 于是错误只以「读错作用域」的形式在评审时出现，
比语法错误贵得多。

## 三、注释：写「为什么」，不写「是什么」

| 规则 | 防的是什么 |
|---|---|
| 中文注释、类头写职责 | 类头一句话说清职责，评审时不用读完整个类才知道它干嘛 |
| 非显然逻辑必须注释「为什么」 | 半年后没人记得「这里为什么加一拍延迟」，改的人直接删掉引发回归 |
| 协议时序逐拍注释（setup / access / 撤拍） | 协议波形是时间维度的，纯代码看不出「第几拍在干什么」 |

**「为什么」与「什么」的分水岭**：`paddr <= req.paddr;` 不需要注释「把地址赋给引脚」——
代码已经说了；需要注释的是「**为什么这里要等两拍**」「**为什么用 `!==` 而不是 `!=`**」。
注释复述代码 = 噪音，注释解释决策 = 资产。

> **反例**：`// 等待`、`// 赋值`、`// 循环` —— 这类注释在改动后**从不更新**，
> 最后变成误导。宁可没有，不要有错的。

## 四、打印：走 UVM 报告机制，且消息带上下文

| 规则 | 防的是什么 |
|---|---|
| 用 `uvm_info/error/fatal`，不用 `$display` | `$display` 不受 verbosity 控制、不分严重度、不进 UVM 报告统计，回归里刷屏还筛不出错误 |
| 消息里带 `get_name()` / `get_type_name()` + 关键值 | 只打印「mismatch」而不知**哪个组件、哪笔事务**，调试时靠猜 |

**错误信息的价值 = 一次定位成功率。** 一条 `uvm_error` 如果没写「哪个 agent 的哪个
monitor、第几笔事务、期望 vs 实际」，调试就得复现 + 加打印重跑；
写全了，日志里直接就能定位到那一笔。

| 差 | 好 |
|---|---|
| `uvm_error("ERR", "mismatch")` | `uvm_error(get_type_name(), $sformatf("addr=%0h exp=%0h got=%0h", addr, exp, got))` |

## 五、禁止 magic number：改动只应有一处

| 规则 | 防的是什么 |
|---|---|
| 硬编码数字换成参数 / 宏 / 配置字段 | 同一个字面量散在多处，改一处漏一处，回归出现「只改了一半」的诡异失败 |

**magic number 的危险不是难读，是难改。** `repeat (3)` 散在五个文件里，
需求改成 4 时你会漏掉某一个 —— 而漏掉的那处**编译照样通过**，
只在特定场景下行为出错，是最贵的一类 bug。

**判据**：一个数字如果**它的含义需要注释解释**，它就该有个名字（参数/宏/配置项）；
如果它天生自解释（`1'b0`、`i + 1`），别过度抽象。

## 六、时序代码一律走时钟块，不裸写信号

| 规则 | 防的是什么 |
|---|---|
| 驱动 / 采样都通过 `vif.<cb>` 时钟块，不在 `@(posedge clk)` 后裸写信号 | 裸写信号依赖仿真器的采样/驱动竞争语义，换工具、换 `timescale`、加一个 `#0` 就变行为，**race 类 bug 极难复现** |

**为什么这是铁律**：SV 里「在时钟沿之后驱动信号」在各仿真器上的竞争处理不完全一致；
时钟块把「**采样在时钟沿前、驱动在时钟沿后**」这件事**写进了语义**，
不依赖模拟器的调度细节。一条时序逻辑如果不是通过时钟块写的，
它在你的机器上过、在别人的机器上挂，都不奇怪。

```systemverilog
// 差：裸写信号，竞争语义未定义
@(posedge vif.clk);
vif.valid <= 1'b1;              // 依赖默认竞争处理

// 好：显式时钟块，采样/驱动语义确定
@(vif.master_cb);
vif.master_cb.valid <= 1'b1;    // 时钟块定义了驱动时刻
```

> 采样同理：monitor 采样走时钟块，才能保证采到的是**时钟沿前稳定的值**，
> 而不是沿上正在翻转的旧值/新值（不定）。

## 七、生成代码与手改代码遵守同一套规范

| 规则 | 防的是什么 |
|---|---|
| 模板生成的部分和人在槽里手改的部分，都用这套规范 | 两套风格并存 → 评审时无法判断「这处风格差异是笔误还是有意」，规范失去效力 |
| 手改不重复定义模板已有的信号 / 成员 | 同名成员被声明两次（一处模板、一处手改），编译报重定义或行为取错的那个 |
| 手改只写差异逻辑，不复制整个 task | 复制整段 → 模板更新后，手改的那份与模板分叉，两边各自演化，再也合不回来 |

**「同一套规范」的深层原因**：生成的和手改的最终**在同一个文件里、由同一个编译器编译、
被同一个人维护**。规范若只管手写不管生成，库里的代码就是「半合规」——
而人只会照着库里的样子写，库不合规，规范整体失效。

## 检查清单

| 检查项 | 问题 |
|---|---|
| 命名后缀 | 句柄都有 `_h`、端口都有 `_p` 吗？宏/参数/枚举全大写吗？ |
| 缩进 | 有没有 tab 混入？`begin` 与语句同行、`end` 独立成行吗？ |
| 注释 | 类头有职责说明吗？非显然逻辑解释了「为什么」吗？协议时序逐拍注释了吗？ |
| 打印 | 有没有残留 `$display`？错误消息带组件名 + 关键值了吗？ |
| 数字 | 有没有需要注释才能懂的字面量？它有没有名字？ |
| 时序 | 驱动/采样是否全走时钟块？有没有 `@(posedge clk)` 后裸写信号？ |
| 一致性 | 生成部分与手改部分风格一致吗？手改有没有重定义模板已有的成员？ |
| 差异最小 | 手改是写差异，还是复制了整个 task？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 用 `$display` 调试 | 「先打出来看看」最快，不用管 verbosity | 回归里刷屏、不分严重度、报告统计不到；上线前忘了删 |
| 错误消息只写「mismatch」 | 打字少 | 调试要靠复现 + 加打印重跑，一次定位成功率降到零 |
| 裸写 `@(posedge clk)` 驱动 | 少写一层 `vif.xxx_cb`，看着更直接 | 采样/驱动竞争语义依赖仿真器，换工具或加 `#0` 就变行为，难复现 |
| 硬编码字面量 | 参数化要额外定义一个宏，当下懒得写 | 改动漏一处，编译照过，只在特定场景出错 |
| 注释复述代码 | 「每一行都注释显得规范」 | 注释在改动后从不同步，从提示变成误导 |
| 手改时复制整个 task | 「照着改最稳」 | 模板更新后手改份与模板分叉，两边各自演化，合不回来 |
| 只在手写代码上守规范 | 「生成的代码管不了」 | 库里大半不合规，人照着库写，规范整体失效 |
| 用 tab 缩进 | 「我的编辑器显示得挺好」 | 别人机器上错位，`begin`/`end` 对齐失效，作用域靠猜 |

> **最值钱的两条**：**时序走时钟块**（否则 race bug 换机器就现形）、
> **打印带上下文**（否则每次失败都要重跑才能定位）。
> 这两条不是可读性问题，是**正确性**与**调试成本**问题。
