# 随机约束怎么写才是可控的

> **一句话**：随机的目的是「让验证器想不到的组合也能出现」，但**发现 bug 靠的是分布**，
> 不是随机本身。一份失控的约束，跑一亿次也到不了边界 —— 而它看起来「一直在随机」。
> 写约束就是写分布。

## 适用场景

- 写新 transaction / sequence 的约束，不知道 `rand` 该修饰谁、`dist` 该怎么配
- 回归跑了很多，覆盖率报告上某些 bin 恒为 0
- 仿真报「constraint solver failed」或 `randomize()` 返回 0，不知道从哪查

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 决定**该测什么**（覆盖点推导） | `功能覆盖率建模.md`（同库 07 域） |
| 让已有 bin 命中率上去 | `verify/07_度量与报告/覆盖率收敛/` |
| 纯定向激励（明确知道要发什么） | 不用这张卡 —— 直接写定向 sequence |

**这条比「适用」值钱**：把「怎么随机」和「该覆盖什么」混在一张卡里，
下一次换个模块，两件事都得重读。约束只负责**把覆盖模型要的东西生成出来**，不负责决定要什么。

## 一、四种控制分布的手段（按力度递增）

| 手段 | 作用 | 典型写法 | 代价 |
|---|---|---|---|
| `dist` 权重 | 调**相对**概率 | `x dist {1:=3, [2:9]:=1}` | 与其它约束叠加后实际分布会变 |
| `inside` + 区间 | 划**取值域** | `x inside {[0:15]}` | 叠加多个 `inside` 会意外收窄 |
| `solve...before` | 定**求解顺序** | `solve mode before len` | 求解时间上升，且只对简单场景可靠 |
| `randc` | 一轮内**不重复** | `randc bit[2:0] addr;` | 状态开销大，域大时退化严重 |

### `dist`：权重是相对的，不是绝对的

```systemverilog
class pkt;
  rand bit [7:0] len;
  rand bit [1:0] kind;
  constraint c_len {
    len dist { 1 := 40, [2:8] := 20, [9:255] := 1 };  // 边界值要显式加权重
  }
  constraint c_kind {
    kind dist { READ := 1, WRITE := 1, NOP := 0 };     // :=0 等于禁掉，用 !inside 更清楚
  }
endclass
```

**坑**：`dist` 的权重是**在可行解空间内的相对权重**，不是最终概率。
如果别的约束把 `[9:255]` 砍掉一半，`dist` 权重没变，但实际出现的分布已经变了。
**判据**：想确认分布，别读 `dist`，去跑一万次打印直方图。

### `rand` vs `randc`：语义差一个字，代价差一个量级

| | `rand` | `randc` |
|---|---|---|
| 语义 | 每次随机，可能重复 | 一个**循环周期**内所有值用一遍才重复 |
| 实现 | 直接取值范围 | 内部维护「已用」集合 |
| 适用 | 绝大多数场景 | 地址、端口号这类「要穷举小域」的 |

**`randc` 的两个陷阱**：

1. **循环按「值」算，不按「上下文」算**。若 `addr` 域是 4 个值而你在不同模式下各要穷举一遍，
   `randc` 是全局不重复，不会分模式各来一轮 —— 结果是某个模式永远拿不到想要的地址。
2. **和约束冲突时 `randc` 会退化**。域被约束砍得很小时，`randc` 退化成 `rand`，
   且随机化可能失败。

```systemverilog
// 想「每个 mode 下都穷举一遍 port」——randc 做不到，要靠嵌套：
class seq_item;
  rand bit [1:0] mode;
  rand bit [1:0] port;
  constraint c_exhaustive { solve mode before port; }  // 只能保证顺序，不保证穷举
endclass
// 真要穷举，用 sequence 里显式的循环，别指望 randc
```

### `solve...before`：它是提示，不是保证

```systemverilog
constraint c_order { solve mode before len; }
```

语义是「先定 mode，再在 mode 决定的空间里定 len」。**它只对变量间有隐含依赖时才有可观测效果**，
且**不保证**一定按此顺序（LRM 允许求解器重排，只要求最终解满足所有约束）。

**代价**：求解器被剥夺了整体优化的空间，复杂约束下求解时间显著上升，甚至求解失败。

**判据**：能用显式约束表达依赖，就不要用 `solve...before`。
例如「mode 是 READ 时 len 才有效」直接写 `mode == READ -> len > 0`，比 `solve mode before len` 稳。

## 二、约束求解失败怎么定位：三步

`s.randomize()` 返回 0，或工具报 `constraint solver failed` / `inconsistency`。
**不要靠改约束猜**，按这三步缩小范围。

| 步 | 做什么 | 产物 |
|---|---|---|
| 1 | **二分删约束**：注释掉一半约束再随机化，确定是哪一半导致的冲突 | 冲突的约束子集 |
| 2 | **单独验证每条**：对冲突子集里的每条约束单独随机化，看哪条单独就失败 | 最紧的那条 |
| 3 | **打印 `s` 的内容**：`sprint()` / `s.print()`，看求解器实际走到了哪一组值 | 一组近似解 |

**冲突的本质永远是**：两条约束的交集为空。常见形态：

```systemverilog
constraint c_a { len inside {[1:8]}; }
constraint c_b { len > 16; }            // 与 c_a 完全不相交 —— 求解必然失败
constraint c_c { data.size() == len; }
constraint c_d { data.size() inside {[4:64]}; }  // len=1..8 时 size 冲突
```

**最隐蔽的一类**：`soft` 约束被 `hard` 约束否定。`soft` 是可被覆盖的**默认值**，
一旦某条 `hard` 与它矛盾，`soft` 被静默丢弃 —— **不报错，只是分布悄悄变了**。

```systemverilog
constraint c_default_len { soft len == 64; }   // 只想做默认值
constraint c_big         { len > 128; }        // 与 soft 矛盾 → soft 静默失效
```

**判据**：`soft` 只用来表达「没什么特别要求时倾向这样」，**绝不用来表达「我需要这样」**。
需要就写 `hard`，冲突时让求解失败把问题喊出来，而不是静默偏向。

## 三、约束过紧 vs 过松：两种失败对称

| | 约束过紧 | 约束过松 |
|---|---|---|
| 表现 | 求解失败 / 某类激励永远生不出 | 跑得多，边界和异常永远不出现 |
| 排查信号 | `randomize()` 返回 0、覆盖率某 bin 恒 0 | 分布直方图全挤在中间，极端值计数为 0 |
| 修正 | 二分找冲突约束、放开 `inside` 域 | 给边界值显式 `dist` 权重、加异常注入约束 |

**「过松」更危险**，因为它**不报错**。约束过紧你立刻知道；约束过松你以为一切正常，
直到签核时才发现异常路径一次没测。**这就是覆盖率收敛卡住的第一嫌疑。**

## 四、检查清单

| 检查项 | 问题 |
|---|---|
| 边界 | 每个随机变量的 max / min / 0 / 特殊值都有**显式权重**吗？ |
| 异常 | 有注入非法值 / 越界 / 超时的约束或开关吗？ |
| `dist` | 只用 `dist` 声明分布，但**跑过直方图确认**实际分布吗？ |
| `randc` | 用的地方真需要「一轮不重复」吗？域大不大？和别的约束冲突吗？ |
| `solve` | 每处 `solve...before` 都能换成显式约束吗？能就换。 |
| `soft` | 每处 `soft` 都不是「其实必须成立」的需求吗？ |
| 层次 | 约束分层了吗（base class 通用约束 + 子类场景约束）？还是一坨？ |
| 冲突 | 有没有两条约束的交集可疑地为空（跑一次随机化就能暴露）？ |
| 复现 | 随机化设了 `srandom(seed)` 吗？失败能复现吗？ |

## 五、坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 用 `dist` 当「绝对概率」 | 写法看着像百分比 | 别的约束一叠加，实际分布和你想的完全不同，且不报错 |
| `soft` 表达硬需求 | 「冲突时还能跑，多稳健」 | 需求被静默放弃，分布悄悄偏，测试盲区无告警 |
| `solve...before` 滥用 | 「显式指定顺序，肯定更可控」 | 求解时间暴涨甚至失败，且不保证顺序 |
| 多层约束叠加不检查交集 | 每个 base class 的约束单看都合理 | 组合后交集为空 → 求解失败，报错点离真凶很远 |
| 随机化不设 seed | 「反正是随机的」 | 出错复现不了；**可复现是签核的前提** |
| 变量全 `rand` 无权重 | 省事 | 边界值概率被域宽稀释到接近 0，永远测不到 |
| 把该定向的写成随机 | 「随机更全面」 | 关键时序场景永远凑不齐，覆盖率数字虚高但没测到 |

**最值钱的两条**：`soft` 静默失效、随机化不设 seed ——
前者制造看不见的盲区，后者让发现的问题复现不了。
