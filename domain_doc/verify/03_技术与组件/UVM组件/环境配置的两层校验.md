# 环境配置的两层校验

> **一句话**：描述符的错分两种 —— 「**结构就不对**」（键拼错、类型不对、必填缺失）
> 和「**结构对但说不通**」（端口引用了不存在的事务字段、TLM 一头接了另一头没接）。
> 前者在**归一化之前**拦，后者在**归一化之后**拦，**两层都要、顺序不能反**。

## 适用场景

- 环境 / 接口 / bench 由 YAML 描述符驱动生成，写错描述符 = 生成一堆错误代码
- 已经踩过「生成的环境连不上」「引用了不存在的名字」这类问题
- 想让 IDE / 编辑器实时提示描述符写错，而不必跑生成

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 配置就是手写 SV，没有描述符 | 编译器即校验器，不用本卡 |
| 生成后手改的内容怎么在重新生成时保留 | `../../../verify/02_验证方法学/UVM/生成式环境与手改共存.md` |
| 一段逻辑该落在哪个组件 | `./UVM组件职责与边界.md` |

## 第 1 步：语法层——键名 / 类型 / 必填 / 枚举（+ 未知键）

语法层校验的是**「这份描述符合不合法」**，与它描述什么无关。四件事：

| 检查 | 例子 | 不查的后果 |
|---|---|---|
| 键名 | 键是不是在允许集合里 | 拼错的键被静默忽略（见第 3 步） |
| 类型 | 该是列表的写成了标量 | 归一化时类型转换失败或悄悄变成了「单元素列表」 |
| 必填 | `name` / `type` 这类必须存在的键 | 缺名的条目在归一化时被整条丢弃 |
| 枚举 | 模式只能取 `MASTER` / `SLAVE` | 非法枚举值落到默认分支，行为与预期不符 |
| **未知键** | **任何不在 schema 里的键 → 报错** | 归一化静默吞掉，错到跑回归才发现 |

**为什么「未知键」也算语法错误**：它不是「多写了点东西」，而是
**「你以为你写了，其实你没写」** —— 归一化器只认它认识的键，拼错的键被
当成「用户没提这个事」而**静默吞掉**，默认值悄悄生效。这是最贵的一类错：
**没有报错、没有警告、结果不对**。

> 归一化器天然倾向于「宽容」（`unknown` 键直接丢，缺省用默认），
> 所以**语法层必须比归一化器严格**，否则归一化器就是错误的缓冲区。

## 第 2 步：语义层——归一化之后的跨字段一致性

语法层过了，只说明「每句话合法」，不说明「这几句话之间不矛盾」。
语义层管**字段与字段之间的关系**，必须在**归一化之后**做（因为要基于归一化后的
统一形态来判断）。

| 一致性 | 检查什么 | 违背后果 |
|---|---|---|
| **端口 ↔ 事务字段** | 引用的端口名、事务字段名是否真实存在 | 生成的代码引用悬空名字，编译不过或连错信号 |
| **TLM 连接两端** | 一个 `connect` 的源与目的都定义了吗 | 生成的环境一头有 exporter 一头没有 imp，连不上 |
| **引用不悬空** | 所有「按名字引用」的地方，目标都存在 | 悬空引用在编译期才暴露，且报错点离原因很远 |
| **配置 ↔ 结构** | 配置里提到的组件/agent 真的会被例化吗 | 配了一个不存在的组件，配置静默没生效 |
| **层次路径** | 路径字符串与例化层次对得上吗 | 运行期 `config_db` 取不到值，组件用默认值跑 |

**为什么语义层必须独立**：这些错**单看任一字段都不错** —— 端口名合法、
事务字段名合法、连接语法合法，问题只在**它们对不上**。
语法层看不到这种「跨字段的矛盾」。

## 第 3 步：为什么顺序不能反

```
原始描述符
   │
   ├─[语法层]─ 键/类型/必填/枚举/未知键     ← 拦在归一化之前
   │                │ error 则阻断
   ▼                ▼
 归一化（统一形态、填默认、丢未知键）
   │
   ├─[语义层]─ 跨字段一致性、引用完整性     ← 拦在归一化之后
   │                │ error 则阻断
   ▼                ▼
 渲染 / 生成代码
```

| 如果顺序反了 | 会发生什么 |
|---|---|
| 先语义后语法 | 语义层在**未归一化**的形态上判断，字段形态不统一（单值 vs 列表），判定逻辑混乱且不稳 |
| 只有语义层 | 未知键、类型错不报错，语义层面对的是被归一化**悄悄改过**的数据，判了个寂寞 |
| 只有语法层 | 合法但矛盾的描述符放行，到生成后才炸，报错点远离根因 |

**判据**：**语法层的工作是「保证归一化器的输入是干净的」**，
语义层的工作是「保证归一化器的输出是自洽的」。两者夹住归一化，
各拦在它唯一能拦住的位置。

## 第 4 步：校验必须在生成之前

| 位置 | 好处 |
|---|---|
| **生成前**（渲染前） | 报错指向**描述符里的那一行**，人直接改描述符 |
| 生成后（对生成代码检查） | 报错指向**生成出来的代码**，人得反推回描述符，多一层映射 |

**为什么这是硬要求**：生成后的检查面对的是**模板产物**，
错误的位置已经被模板结构搅乱，且往往是几十个文件一起炸。
生成前校验把错误**钉在源头**：一次报清楚「第几个 agent 的哪个字段错了」，
比生成后再去 .sv 里大海捞针便宜一个数量级。

- **语法层 error → 阻断生成**（结构都不合法，没有生成的意义）
- **语义层 error → 阻断生成**；warning 可放行但**落盘报告**（记录但不拦）
- 报告应**持久化**（落成文件），因为「这次为什么没生成」需要可追溯

## 每步产物

| 步骤 | 产物 |
|---|---|
| 语法层 | schema 契约（键/类型/必填/枚举/未知键策略）+ 一份校验报告 |
| 语义层 | 一组「一致性规则」+ 一份校验报告（error 阻断 / warning 落盘） |
| 顺序 | 生成流程把两层卡在归一化前后，**归一化夹在中间** |
| 时机 | 生成前执行；error 阻断、报告落盘、可关（应急） |

## 检查清单

| 检查项 | 问题 |
|---|---|
| 未知键 | schema 对未知键是**报错**还是忽略？（必须报错） |
| 必填 | 每个「缺了就没意义」的键都在必填里吗？ |
| 枚举 | 所有枚举字段都有取值集合吗？非法值怎么处理？ |
| 归一化 | 归一化器会不会静默丢键/改形态？它丢的东西语法层拦住了吗？ |
| 跨字段 | 端口↔事务字段、TLM 两端、引用完整性，各有一条规则吗？ |
| 顺序 | 语法层是不是在归一化前、语义层在归一化后？ |
| 时机 | 校验在生成之前吗？error 会阻断吗？报告落盘吗？ |
| 可复用 | schema 能被编辑器/IDE 复用来做实时提示吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 未知键忽略而非报错 | 「宽容一点用户更好用」 | 拼错的键被归一化静默吞掉，默认值悄悄生效，跑到回归才发现 |
| 只做语法层 | 有 schema 检查就以为够了 | 合法但矛盾的描述符放行，生成后才炸，报错点远离根因 |
| 只做语义层 | 「跨字段才是关键，键名不重要」 | 未知键、类型错不拦，语义层在被归一化改过的数据上瞎判 |
| 顺序反了（语义在前） | 「先查逻辑再查格式」直觉合理 | 语义层面对未归一化的不统一形态，判定不稳、误报漏报 |
| 校验放在生成之后 | 「生成完统一检查更省事」 | 报错指向生成代码，人要反推回描述符，且几十个文件一起炸 |
| 报告只打印不落盘 | 「控制台能看到就行」 | 「上次为什么没生成」无从追溯，CI 里翻日志靠运气 |
| schema 与校验器各写一套 | 快 | 两套定义漂移，schema 说合法、校验器说不合法（或反之） |
| 未知键报错但枚举不报错 | 只盯了最显眼的 | 非法枚举值落到默认分支，行为与预期不符且无人发现 |

> **最值钱的两条**：**未知键必须报错**（否则归一化静默吞错）、
> **两层顺序不能反**（否则各自的拦截位置失效）。
> 这两条决定校验是「真的拦住了」还是「看起来在拦」。
