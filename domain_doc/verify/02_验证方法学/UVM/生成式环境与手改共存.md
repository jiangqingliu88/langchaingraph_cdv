# 生成式环境与手改共存

> **一句话**：生成器能省掉 90% 的样板，但剩下 10% 的协议特有逻辑**永远要人写**。
> 可维护性的分水岭不在「生成得多全」，而在**手改的东西住在哪** ——
> 住在一个模板认得出、回填时搬得动的**细粒度语义槽**里，还是散落在文件各处、
> 下次重新生成就人间蒸发。

## 适用场景

- 一个环境由模板批量产出（agent / env / bench 各层），项目里仍要加定制逻辑
- 已经出现「改一处 → 重新生成 → 手改没了 → 再改一遍」的循环
- 多项目复用同一套模板，但每个项目都想在若干点上做差异

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 环境只生成一次，之后纯手工维护 | 直接改，不用槽 |
| 协议时序本身怎么写才不裸写信号 | `../../../verify/03_技术与组件/SystemVerilog/UVM代码风格.md` |
| 一段逻辑该落在 driver 还是 monitor | `../../../verify/03_技术与组件/UVM组件/UVM组件职责与边界.md` |
| YAML 描述符本身该怎么校验才拦得住错 | `../../../verify/03_技术与组件/UVM组件/环境配置的两层校验.md` |

## 第 1 步：先承认「手改是常态，不是意外」

生成式环境的第一个错误假设是「生成即完成」。真实情况：**协议时序、定制成员、
非常规连接，模板必然覆盖不到**，人一定会动手改。承认这点之后，问题就从
「怎么让人别改」变成「**怎么让人改在一个可被回填的位置**」。

| 不承认手改的做法 | 后果 |
|---|---|
| 把文件生成成「完整成品」 | 人改在任意位置，重新生成全被覆盖 |
| 禁止手改、要求回模板里加分支 | 每次小改动都要动模板，模板变成第二个项目 |
| 生成后就不敢重新生成 | 模板改进无法回收，环境随项目腐烂 |

## 第 2 步：在模板里留**细粒度语义槽**（按职责切，不按文件切）

槽是模板里**带命名的一块可替换区域**，生成器知道它边界在哪、回填时往哪搬。
**关键判据只有一条：槽按「职责」切，不按「文件」切。**

| 切法 | 例子 | 结果 |
|---|---|---|
| 按文件切（粗区域） | 「driver 文件的自定义区」一块 | 粒度太粗，一个文件里多种职责挤一块，改一处牵连一片 |
| 按职责切（细槽） | 「成员声明」「构建逻辑」「驱动时序」「采样逻辑」各自独立 | 每处手改归属明确，互不干扰 |

**为什么细槽不是「洁癖」**：粒度一粗，手改量一大，槽就退化成
「整个文件都是我的地盘」—— 等于**手工维护**，生成器只剩第一次生成有用。
细槽的价值在于：**手改面小且边界清晰，回填时能精确搬运，改动之外的部分继续吃模板的更新。**

| 职责 | 槽的粒度参考 | 落点 |
|---|---|---|
| 新增成员 | 每个类体一个「声明槽」 | 声明区 |
| 构建/连接附加逻辑 | build 一个槽、connect 一个槽 | 各自 phase 末尾 |
| 协议驱动时序 | driver 驱动 task 一个槽 | 驱动体 |
| 帧采集逻辑 | monitor 采样 task 一个槽 | 采样体 |
| 自定义序列体 | sequence 类体一个槽 | 类体 |

> **反例**：把所有「自定义」塞进一个 `custom_code` 大块 —— 那是粗区域的变体，
> 只是换了个名字。判断标准是**能不能只搬一块而不动另一块**。

## 第 3 步：手改只发生在槽内，槽外只读

| 区域 | 谁能写 | 重新生成时 |
|---|---|---|
| 槽内 | 人 | 被回填（按优先级） |
| 槽外 | 模板 | 整块重写，人手改丢失 |

**这条规则必须写进团队约定并让生成器配合**：重新生成时**备份原文件**，
且对「槽外被改动」给出提示或报错（说明这次生成会覆盖掉非槽改动）。
没有这层提醒，人会以为「我改的都在槽里」，直到被覆盖才发现槽外也改了。

## 第 4 步：定义回填优先级，冲突时谁赢

槽在「生成时」需要内容，可能有三个来源：模板默认、槽内手改、配置注入。
**优先级必须显式定义，不能靠隐式覆盖顺序。**

| 优先级 | 来源 | 语义 |
|---|---|---|
| 高 | 槽内手改内容 | 人写得最具体的，赢 |
| 中 | 模板默认实现 | 没人填时的兜底，保证能跑 |
| —— | 配置注入 | **下线，不要有**（见第 5 步） |

**「手改 > 模板默认」为什么是唯一合理的方向**：模板默认是「通用的、能跑的」，
手改是「这个项目特有的、必须的」。让模板默认赢，等于把项目特性抹掉，
项目就没法用生成器了；让手改赢，模板的**结构更新**照样通过槽边界渗透进来，
而**槽内差异**被保留 —— 两边各取所需。

> **方向反了会怎样**：模板默认盖过手改 → 每次重新生成都把项目定制推平，
> 团队最终放弃重新生成，模板更新永远进不来。

## 第 5 步：不要用「配置注入代码」代替手改

一个很诱人的替代方案：让模板从配置（YAML/JSON）里读代码片段注入槽内。
**这是可读性灾难，且让「真相」有两个。**

| 问题 | 说明 |
|---|---|
| 代码住进配置 | 人会往 YAML 里贴大段 SystemVerilog —— 语法高亮、括号匹配、编译检查全失效 |
| 真相分裂 | 同一段逻辑，一个版本在配置里、一个版本在生成的 .sv 里，改哪个？ |
| 校验断层 | 配置里的代码块**不过编译器**，错误要等生成 + 编译才暴露 |
| 覆盖语义混乱 | 「配置非空就盖手改」让人分不清手上这份文件到底谁说了算 |

**结论**：自定义代码就以**它本来的语言**住在**槽里**（.sv 文件内），
配置只负责描述**结构**（有哪些组件、怎么连），不负责携带**行为代码**。
行为与结构分离，各自用适合自己的语言表达。

## 第 6 步：划槽不重叠——边界靠「职责+位置」双锚定

槽与槽必须**不重叠**，否则回填时一段代码可能被搬进两个地方。

| 原则 | 含义 | 检查 |
|---|---|---|
| **位置唯一** | 一个槽在同一文件内只出现一次 | 出现两次 → 回填搬到哪？必须报错 |
| **职责单一** | 一个槽只承接一类手改 | 一个槽里既声明成员又写时序 → 拆分 |
| **锚点明确** | 槽靠「类/phase/task」定位，不靠行号 | 靠行号 → 模板一变就错位 |
| **默认可跑** | 槽留空时模板有兜底实现 | 空槽导致编译不过 → 默认实现缺失 |

**重叠的典型信号**：模板里两个槽紧挨着、或一个槽的默认实现里又出现另一个槽 ——
说明职责没切干净，回填顺序会变得不可预测。

## 每步产物

| 步骤 | 产物 |
|---|---|
| 1 承认手改 | 团队约定：槽外只读、重新生成会覆盖槽外改动 |
| 2 拆细槽 | 一份「职责 → 槽」映射表（哪些类、哪些 task 开槽） |
| 3 槽内手改 | 生成的 .sv 文件，手改内容全部落在槽内 |
| 4 定优先级 | 优先级文档：手改 > 模板默认；配置不携带代码 |
| 5 拒绝配置注入 | 配置 schema 里不出现「代码承载」字段 |
| 6 划边界 | 每个槽：唯一位置 + 单一职责 + 明确锚点 + 默认实现 |
| 回填 | 重新生成后备份原文件 + 槽内容完整迁移 + 迁移报告 |

## 检查清单

| 检查项 | 问题 |
|---|---|
| 粒度 | 槽是按职责切的吗？有没有「一个文件一个大槽」的粗区域？ |
| 唯一性 | 同一文件里有没有同名槽出现两次？ |
| 重叠 | 两个槽的默认实现有没有互相嵌套？ |
| 回填方向 | 优先级是不是「手改 > 模板默认」？有没有反向的覆盖？ |
| 配置纯净 | 配置里有没有藏代码片段？代码是不是只住在槽里？ |
| 默认实现 | 槽留空时环境能不能独立编译、跑通？ |
| 覆盖保护 | 重新生成前会不会备份？槽外改动有没有被提示？ |
| 迁移完整 | 每个非空手改槽，回填后内容一字不差吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 用「整块替换」代替细槽 | 实现简单，一个洞全塞进去 | 粒度退化成手工维护，生成器只剩第一次有用 |
| 把自定义代码放进配置注入 | 「配置驱动一切」听起来很优雅，还不用改模板 | YAML 里贴 SV，可读性崩、编译器管不到、真相分裂成两处 |
| 回填优先级不明确 | 谁最后写谁赢，省得定义 | 重新生成结果不可预测，模板默认静默盖掉项目定制 |
| 槽靠行号定位 | 行号直观 | 模板一改行号全错位，回填搬错位置 |
| 槽与槽边界重叠 | 就近放省事 | 一段代码被两个槽认领，回填顺序依赖巧合 |
| 槽留空没默认实现 | 「反正人会填」 | 空槽导致编译不过，环境开箱跑不起来 |
| 重新生成不备份 | 想省磁盘 / 想一步到位 | 覆盖后无法回滚，手改彻底丢失 |
| 允许槽外手改 | 「就改一行，无伤大雅」 | 下次生成被覆盖，且人以为改在槽里 |
| 让模型直接写粗区 | 「模型能力够，写整段更灵活」 | 细槽约束被绕过，退化成整块替换的全部问题 |

> **最值钱的两条**：槽要**按职责切**（否则退化成手工维护）、
> 代码**不许进配置**（否则真相分裂、校验断层）。
> 这两条守住，剩下的优先级和边界规则才有意义。
