# 形式验证

> **一句话**：仿真问「在我随机撒的这一百万个激励里，有没有出错」；
> 形式问「**在所有可能的激励里，有没有出错**」。
> 前者是采样，后者是证明 —— 所以形式能给「没找到反例」之外的第三种结论：**已证明**。

## 一、定义

形式验证（Formal Verification）用**数学方法**穷举设计的**状态空间**，
判断某个性质（property）在所有可达状态 / 所有合法输入序列下是否恒真。
它不依赖激励，因此结论比仿真强，但代价是**容量有限**（状态空间会爆炸）。

**三种结论**（这是形式区别于仿真的根本）：

| 结论 | 含义 | 仿真能不能给 |
|---|---|---|
| **证明通过（proven）** | 该性质在所有可达状态下恒真，不存在反例 | **不能**（仿真只能说「没找到」） |
| **反例（counterexample）** | 存在一条具体激励序列违反性质，工具给波形 | 能（但要碰运气碰到） |
| **未定（inconclusive / bounded）** | 在给定深度 / 时间内没证出也没证伪 | 仿真一直是这种状态 |

## 二、FPV / 等价性 / 属性验证的分工

三件事常被统称「形式」，但目标、产物、用法完全不同：

| 种类 | 全称 | 问什么 | 典型场景 | 输出 |
|---|---|---|---|---|
| **FPV** | Formal Property Verification | 「这条性质在这份 RTL 上恒真吗」 | 控制逻辑、仲裁、状态机、协议规则 | proven / 反例 / 未定 |
| **等价性检查** | LEC（Logic Equivalence Check） | 「这份网表 == 这份 RTL 吗」 | 综合后、插入 DFT 后、ECO 后 | 等价 / 不等价的点 |
| **属性验证** | ABV（Assertion-Based Verification） | 「这些断言在仿真里有没有被违反」 | 仿真中随手加断言、动态检查 | 断言失败 / 覆盖到 |

> 关键区分：**FPV 是「无激励的证明」，等价性是「两份设计对不上对得上」，ABV 是「在仿真里加检查」**。
> ABV 本身是仿真的一部分，不是「形式」；只有把 ABV 的断言拿去做**形式穷举**，才变成 FPV。
> 很多人把「加了断言」叫「做了形式」，这是最常见的名实不符。

## 三、什么时候形式比仿真值

| 值的情况 | 为什么形式赢 |
|---|---|
| **状态空间小而复杂** | 仲裁器、状态机、握手协议：状态不多但组合多，仿真很难撒全，形式能穷举 |
| **需要「无激励结论」** | 要证明「任何情况下都不会死锁 / 不会溢出 / 不会越权」，仿真给不了这种保证 |
| **需要「不可达」证明** | 证明某条路径 / 某个状态**永远到不了**（安全属性、覆盖模型的自检都需要它） |
| **输入组合爆炸** | 输入很多、取值空间大，仿真只能采样，形式能覆盖全空间（只要不爆炸） |
| **等价性 / ECO 后** | 改了一小块，要证明其余等价 —— 仿真重跑代价大，等价性几分钟出结论 |
| **早期无激励** | 设计刚写、TB 还没搭，先用形式抓基本属性 |

## 四、什么时候形式不值

| 不值的情况 | 为什么 |
|---|---|
| **数据通路 / 算术密集** | 乘法器、大位宽 ALU、加解密：状态空间随位宽指数爆炸，形式证不动，仿真更实际 |
| **需要「跑真实场景」** | 端到端系统场景、软件交互、多核调度：形式表达不了，也没容量 |
| **没有好性质可写** | 形式的威力全在性质（property）的质量上 —— 写不出好性质，形式等于什么都没有 |
| **性能 / 时序相关** | 「DUT 在 X 拍内响应」这类带时序深度的性质，形式可能证不动（深度爆炸） |
| **一次性、小模块** | 写性质 + 建约束的成本 > 手写几个定向激励，直接仿真更快 |
| **依赖大量环境** | 需要复杂外部环境的性质，约束（constraint）会难写到失真 |

**判据一句话**：**控制逻辑上形式，数据通路上仿真；要证明用形式，要跑场景用仿真。**

## 五、与易混概念的区别

| 易混对 | 差在哪 |
|---|---|
| 形式 vs 仿真 | 采样 vs 穷举。仿真给「没找到反例」，形式给「已证明」。形式容量受限，仿真容量几乎无限。 |
| 形式 vs 断言（ABV） | 断言是**检查手段**，可在仿真里跑，也可在形式里跑。默认「加断言」属于 ABV（仿真），不等于 FPV。 |
| FPV vs 等价性 | FPV 对一个设计验性质；等价性对**两份设计**做对照。目标不同，工具与流程也不同。 |
| 形式 vs 静态检查（Lint / CDC / RDC） | 静态检查查**结构规则**（有没有同步器、有没有组合环），不证明功能；形式证明**功能性质**。两者常配合，不互相替代。 |
| 反例 vs 仿真失败 | 形式的反例是一条**真实可达的**违规路径（若不违规就是约束写错了）；仿真失败可能只是 TB 激励写错。前者更可信，但前提是环境建模正确。 |

## 六、真正的难点：性质与约束

形式的效果 = **性质的质量** × **约束的正确性**。两者任一拉胯，形式就白做。

| 要素 | 作用 | 写坏的后果 |
|---|---|---|
| **性质（property）** | 描述「什么必须永远成立」 | 写太弱 → 假通过（证了个没意义的东西）；写太强 → 假反例 |
| **约束（constraint / assume）** | 描述「环境保证什么输入合法」 | 约束松 → 反例是环境非法造成的，不是设计错（噪声）；约束紧 → 把真 bug 挡在门外（假通过） |
| **抽象 / 切割** | 把证不动的大模块切成可证的子问题 | 切割错 → 证的是一份和真设计行为不同的模型 |

> **最危险的失败模式**：**约束过紧导致的假通过**。它看起来是「proven」，
> 实际是你的约束把反例挡掉了 —— 和仿真里激励撒不到是一个病，只是更隐蔽（有个绿色勾）。

## 七、检查清单

| 检查项 | 问题 |
|---|---|
| 性质来源 | 每条性质能追溯到规格条款或需求吗？还是「想到就写」？ |
| 性质强度 | 有没有「证了等于没证」的弱性质（只是重复了 RTL 行为）？ |
| 约束审计 | 每条 `assume` 都论证过「环境真的保证它」吗？ |
| 未定处理 | inconclusive 的性质是当「通过」算了，还是留了尾巴？ |
| 反例判读 | 反例是设计 bug，还是约束不完整？两者要分开处置。 |
| 覆盖/自检 | 有没有证明「性质本身可被触发」（vacuous pass 检测）？ |
| 与仿真关系 | 形式覆盖的和仿真覆盖的有重叠 / 缺口吗？ |
| 领域选择 | 用形式的部分是控制逻辑，还是误用了数据通路？ |

## 八、坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 把 ABV 当形式交差 | 「我们加了一堆断言」听起来很形式 | 仿真没撒到的反例照样漏，给的是采样保证，不是证明 |
| 约束过紧导致假通过 | 反例太多、想让它干净点，就加约束 | 绿色 proven 是假的，真 bug 被约束挡在门外（最隐蔽的坑） |
| 性质写得与 RTL 同构 | 照着 RTL 写「性质」，轻松 proven | 证的是「RTL 等于 RTL」，什么都没证明（vacuous） |
| 拿形式证数据通路 | 想给算术模块一个「证明」 | 状态爆炸，要么证不动，要么被抽象简到失真 |
| 忽略未定项 | 只想看 proven 的绿勾 | inconclusive 被当成通过上报，签核证据有洞 |
| 没有 vacuous 检测 | 不知道性质到底有没有被触发过 | 一条永远不触发的性质也报「通过」，白写 |
| 用等价性代替功能验证 | 「等价性过了，说明没问题」 | 等价性只证明「两份设计一样」，不一样不一定错、一样也不一定对 |
