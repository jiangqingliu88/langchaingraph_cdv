# 功能组织树与专题

> **一句话**：用例空间有两条轴 —— 纵向的**结构骨架**（功能组织树：这条路径属于哪个
> 功能的哪个能力点）和横向的**横切关注点**（专题：这个关注点穿过哪些功能路径）。
> 只有叶子生成用例；专题按优先级分层横切在树上。

## 适用场景

- 一个对象（如一条流水线、一个控制器）需要按功能逐层拆，而不是平铺一堆子对象
- 有一组关注点（配置、异常、性能常稳、随机压力）要作用在多条功能路径上
- 发现「专题 A 和专题 B 都在同一个叶子、选同一批维度」，产出用例开始重复
- 拿不准某两个维度该不该交叉

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 一个用例到底由哪几层属性组成 | KB-DV-METH-005 用例属性模型 |
| 诊断维度/字段分层错在哪 | KB-DV-METH-007 用例属性层级错位 |
| 覆盖点从接口/功能/异常契约怎么推 | `verify/07_度量与报告/覆盖率模型/` |
| 缺口怎么收、什么 bin 该豁免 | `verify/07_度量与报告/覆盖率收敛/` |

**为什么单列**：骨架和横切是**两种不同的切法**，混在一张卡里讲「维度」会让人
以为专题也是维度 —— 专题是**关注点**，维度才是可取值的东西。

---

## 一、结构骨架：功能组织树

**功能组织树是纵向的结构骨架**：像处理流水线那样分段落，每段下面还能再分能力点，
层级由「子节点」表达。

| 规则 | 说明 |
|---|---|
| 逐层分解 | 一个节点可以再切出若干子节点；分解到「能直接写用例」为止 |
| **只有叶子生成用例** | 分支节点是**范围**，不是用例主体；分支会被展开到它的叶子 |
| 扁平列表是特例 | 所有节点都是叶子的树，退化成平铺清单 —— 旧模型不用改 |
| 叶子标识必须唯一 | 叶子标识进用例 ID，重复就是重名用例，回归结果里分不开 |

**判据（一个节点该切成子节点吗）**：

- 能否用**外部可观察行为**分别描述？能 → 值得切成两个叶子
- 两者能否**独立地覆盖进度**？（一个覆盖够了、另一个还差）能 → 应该分开
- 只是个实现细节、永远一起变 → 不该切，留着当一个叶子的内部属性

**产物**：一棵树（每个分支记它的子节点，每个叶子记它的标识与代号）。

## 二、横切关注点：专题

**专题是横切的验证关注点**：它不改变树的结构，只回答「这个关注点打在树的哪些节点上、
配哪些维度、用什么方法」。

专题的核心属性只有三个：

| 属性 | 含义 |
|---|---|
| 作用范围 | 打哪些节点（可指向分支，自动展开到叶子；也可全树） |
| 维度 | 选中哪些维度参与（可留空表示全部维度） |
| 优先级 | P0 / P1 / P2 |

**优先级分层与「空洞」**：

| 级别 | 含义 | 典型内容 |
|---|---|---|
| P0 | 不做就不算验完 | 配置与参数、基础功能路径 |
| P1 | 常见异常与关键交互 | 错误与异常、关键接口的反压组合 |
| P2 | 压力与边角 | 全量随机、边界组合、长尾 |

**空洞判定**：从 P0 起逐级必须连续 —— 只声明了 P2 而没有 P0（或只声明 P0/P2 跳过 P1），
就是优先级空洞。空洞意味着「压力测试优先于基础功能」，那是不可能成立的验证顺序。

## 三、三类专题：由两个正交槽位派生

专题的**三类**（全量随机 / 正交 / 结构类）不是三个类型标签，而是
**两个正交槽位**（作用范围、维度）取值组合的产物。

| | 作用范围**留空** | 作用范围**非空 / 全树** |
|---|---|---|
| **维度留空 / 全维度** | 全量随机（不对树、不对具体维度） | 全维度随机组合（**随机专题**） |
| **维度指定** | 正交专题（**错误和异常** / **性能常稳**） | 结构类专题（**P0 配置** / **P1 反压 cross** / **P2 边界 cross**） |

**四个格子各自的语义**：

| 格子 | 语义 | 为什么归这一类 |
|---|---|---|
| 范围空 + 维度空 | 全量随机：撒网，不承诺覆盖什么 | 没有承诺，只能算背景压力 |
| 范围非空 + 维度空 | 随机专题：打某些节点，但维度全放随机 | 有范围无维度 → 关注点是「这片区域的随机强度」 |
| 范围空 + 维度指定 | 正交专题：不在树上定位，只针对某些维度 | 如异常注入、性能常稳 —— 它是**手段**，不绑定某条功能路径 |
| 范围非空 + 维度指定 | 结构类专题：打这些节点，且约束这些维度 | 最具体的一类，如「P1 反压 cross 只打在发射与写回两个叶子」 |

### 为什么由字段派生，而不设独立类型字段

| 设独立类型字段 | 由两个槽位派生（本卡主张） |
|---|---|
| 类型字段与「范围/维度」两处都要填 | 类型是两者的**函数**，填错一处就自相矛盾 |
| 「类型=结构类」但范围留空 → 两处打架 | 不可能打架：类型没有独立存储 |
| 加一类要改词表、改校验、改生成三处 | 加一类只需确认它落在哪个格子里 |

**根本理由**：**两处真相必有一处先腐坏**。能算出来的东西不要存 —— 存了就得同步，
同步就得写规则查不一致，而规则本身又是一处新的真相。

## 四、维度交叉的三态

专题选完范围，还要约束「这些维度怎么配」。任意两个维度之间只有三种关系：

| 态 | 含义 | 生成语义 |
|---|---|---|
| **必需一起变** | 这两个维度的取值必须两两组合（笛卡尔积） | 对每一对取值都产用例 |
| **可选** | 允许一起出现，但不强制穷尽 | 按需组合，不保证全枚举 |
| **禁止同时变** | 这两个维度不允许在同一用例里同时变化 | 二者取一 |

**判据（怎么定这三态）**：

| 你想问的问题 | 答案对应的态 |
|---|---|
| 这两个一起变会引发新行为吗？（交互 bug 藏在这） | 必需一起变 |
| 一起变不常见，但偶尔会 | 可选 |
| 这两个从物理上/语义上互斥，没有「同时」的情形 | 禁止同时变 |

**交叉矩阵**是这三态的载体：对称矩阵，行列为各维度，非对角元填三态之一。
它天然是对称的，且一旦声明，就必须与「交叉组」保持一致（组内只能放必需的行）。

**规模控制**：两个维度各 N、M 个取值 → 交叉出 N×M 个用例。声明「必需」前先估规模，
N×M 超过可接受规模时要拆成多个小交叉组，而不是硬上。

## 五、「禁止」是硬约束，与专题冲突怎么办

**禁止态优先于专题的维度选择**。这是一个刻意的排序，不是巧合：

| 情形 | 处理 |
|---|---|
| 专题同时列了两个禁止同时变的维度 | 模型**自相矛盾**：分析必须报出来，不能沉默 |
| 生成时 | 保留先声明的那个维度、丢掉后一个，**并记账**（说明丢了什么） |

**为什么这么定**：

- 「禁止」表达的是**物理/语义约束**（两者根本没有同时成立的情形），
  那是比「这个专题想测什么」更硬的真相
- 若让专题覆盖禁止，就会生成物理上不可能的用例 —— 那些用例跑到仿真里必然失败，
  且失败原因会被误判成设计 bug
- **不静默**：丢掉维度必须记账。静默丢弃 = 你以为是交叉覆盖，其实少了一半，
  而且报告上看不出来 —— 这比直接报错更坏

## 六、每步的产物

| 步 | 动作 | 产物 |
|---|---|---|
| 1 | 按流水/功能分段建树 | 功能组织树（分支+叶子） |
| 2 | 叶子标识去重 | 唯一叶子清单 |
| 3 | 列横切关注点，定优先级 | 专题清单（P0/P1/P2） |
| 4 | 给每个专题填「范围 + 维度 + 方法」 | 专题的定义 |
| 5 | 建维度交叉矩阵 | 各维度对的三态表 |
| 6 | 由必需要素建交叉组 | 交叉组清单 |
| 7 | 展开：叶子 × 专题 × 交叉组 → 用例 | 用例属性表 |

## 七、检查清单

| 检查项 | 问题 |
|---|---|
| 唯一叶子 | 叶子标识有重复吗？（重复 = 重名用例） |
| 叶子可达 | 有没有叶子一个用例都没生成（零覆盖）？ |
| 无死结构 | 有没有子树永远不被任何专题选中？ |
| 优先级连续 | P0/P1/P2 有空洞吗？ |
| 专题不重叠 | 两个专题会同节点、同维度、同方法吗？（会在同一格产重复用例） |
| 维度被选 | 每个维度都被至少一个专题选中吗？ |
| 维度参与交叉 | 每个维度都进了交叉矩阵吗？ |
| 禁止一致 | 有没有专题选了禁止同时变的维度对？ |
| 规模可控 | 必需交叉的规模估过吗？会爆炸吗？ |
| 专项够猛 | 专项类专题推得动边界，还是只能在中间打转？ |

## 八、坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 叶子标识重复 | 不同分支下叫同一个名字很自然 | 用例 ID 撞车，回归结果里两个用例混成一个 |
| 专题大面积重叠 | 每个专题各管一摊，覆盖听起来更全 | 同一格产重复用例，覆盖率数字虚高 |
| 优先级空洞 | 先写最急的 P2 压力，P0 回头补 | 验证顺序错乱；压力测试先于基础功能毫无意义 |
| 设独立的专题类型字段 | 直接读类型名最直观 | 类型与「范围/维度」两处打架，两套真相 |
| 维度平铺、不建交叉矩阵 | 有什么维度列什么，省事 | 必交叉/可选/禁止表达不出，交互 bug 测不到 |
| 让专题覆盖禁止态 | 专题说「我就要测这两个维度」 | 生成物理上不可能的用例，失败原因误判成设计 bug |
| 静默丢弃冲突维度 | 报错打断流程，丢了继续跑更顺 | 少了半个覆盖且报告看不出，比报错更坏 |
| 分支节点也生成用例 | 分支看起来也是个「东西」 | 用例挂在分支上，按叶子统计覆盖时它不出现 |

> **最值钱的两条**：**优先级空洞**（验证顺序立不住）与**禁止冲突**（生成不可能的用例）。
> 前者让计划从根上失去意义，后者让失败原因指向错误的方向。
