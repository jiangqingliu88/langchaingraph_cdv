# 用例属性模型

> **一句话**：把属性塞进用例名（如 `tc_bp_tail_max_len_full_rnd_01` 这种示意写法），
> 信息密度高但**没法检索、没法组合、错了必须手改**。把属性显式分层之后，
> 用例由属性**组合生成**而不是手写 —— 覆盖率缺口也就能直接映射回某个字段的取值。

## 适用场景

- 新写一份测试用例清单，不想再起一堆读不出结构的名字
- 用例越加越多，但发现「这两个是不是重复了」永远要靠人回忆
- 覆盖率报告说「`反压模式=尾拍` 没中」，你要能在用例表里一键查出「哪些用例该打它」
- 想把「跑一次随机」这种机会性覆盖，改成「我先声明要覆盖什么、再生成用例」

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 把对象切成一层层的能力点 / 流水段 | KB-DV-METH-006 功能组织树与专题 |
| 诊断「这个维度怎么老是跟别的撞」 | KB-DV-METH-007 用例属性层级错位 |
| 覆盖点怎么从接口/功能/异常契约推出来 | `verify/07_度量与报告/覆盖率模型/` |
| 定签核门槛、waiver 比例 | `02_流程与签核/` |

**为什么单列一张卡**：分层判据（下面第二节）是**所有**用例组织问题的公理。
把它混在「怎么生成」里，下次只想知道「这条该放维度还是字段」时就得重读一遍生成流水线。

## 一、六层 + 环境：每层回答一个问题

一个用例 = 六层属性各取一个（或一组）值，再配一份环境指纹。

| 层 | 名称 | 回答什么问题 | 判断标准 | 中性示例 |
|---|---|---|---|---|
| L1 | 对象 | **测哪个主体** | 能用外部行为描述的验证主体 | 该类事务的主控 / 通路 |
| L2 | 子对象 | **主体的哪个能力点** | 对象的细分，不是另一个对象 | 「接收侧」/「发射侧」 |
| L3 | 维度 | **哪一类会变化的条件** | 一组语义相关、可互相约束、通常一起随机的字段 | 「长度」/「反压」 |
| L4 | 字段 | **这项条件取什么值** | 真正承载取值的单元 | 长度 ∈ {小, 中, 大, 最大} |
| L5 | 方法 | **怎么生成** | 独立于对象与维度 | 定向 / 随机 / 组合 / 重放 / 专项 |
| L6 | 检查 | **验证什么** | 与用例名无关的验证目标 | 功能 / 白盒 / 性能 |
| — | 环境 | **在什么环境下跑** | 会改变结果、但不属于用例主体的外来因素 | 工具 / 设计 / 约束 / 配置 / 种子 |

**关键判据（三个各管一件事）**：

| 判据 | 一句话 |
|---|---|
| 维度**只归类** | 维度是「一组字段的集合」，它自己不承载取值 |
| 字段**才取值** | 落到具体值的一定是字段，不是维度 |
| 方法**不混入对象/维度** | 「随机」「定向」是生成方式，不是被测属性 |

**一句话记忆**：对象定义主体，子对象定义能力点，维度归字段，字段承载取值，
方法决定生成，检查定义验证目标，环境保证可复现。

## 二、每层为什么这么分

分层的价值不在「好看」，在于**每层独立可枚举、可组合、可筛选**。

| 层 | 独立枚举的收益 | 拆错会怎样 |
|---|---|---|
| 对象 / 子对象 | 可以问「这个能力点覆盖够了没」 | 塞进维度 → 无法按能力点统计进度 |
| 维度 | 可以问「这个维度被哪些专题选过」 | 塞进对象 → 组织树爆炸，一个维度变一个主体 |
| 字段 | 可以问「这个取值命中了几次」，缺口映射回取值 | 塞进维度的名字里 → 缺口无处安放，只能拆维度 |
| 方法 | 可以问「哪些用例是随机跑出来的」（去重时只差方法的算重复） | 塞进维度 → 随机/定向各变一个维度，组合爆炸且语义失真 |
| 检查 | 可以问「功能检查覆盖了哪些用例」，也可反向问「这条用例验证了什么」 | 塞进对象 → 白盒检查变成一个被测主体 |

## 三、每一层的产物

| 层 | 该层产物 | 形态 |
|---|---|---|
| L1/L2 | 功能组织树（逐层分解，只有**叶子**生成用例） | 树 |
| L2 | 专题（横切在树上的验证关注点） | 带优先级的清单 |
| L3 | 维度清单 + 维度内的**字段关系表** | 字段 A × 字段 B：独立 / 联动 / 互斥 |
| L4 | 取值点清单（含边界 / 特殊 / 非法） | 每字段的取值集合 |
| L5 | 每维度可用的生成方法 | 方法标签 |
| L6 | 检查项清单 + 用例↔检查的挂载 | 多对多 |
| 环境 | 环境指纹规范（哪些键必记） | 键清单（值在运行时填） |

**维度内部必须维护字段关系表**，否则约束写不清：同维度内的字段不总是平铺的 ——
有的并列（互不依赖）、有的联动（一长一久）、有的互斥（无该现象与该项取满互相排斥）。

## 四、L5 五种生成方法

方法**不是用例类型**，是用例的生成属性。同一个维度，五种方法都可用。

| 代号 | 方法 | 语义 | 什么时候用 |
|---|---|---|---|
| D | 定向 | 固定取值，手工指定 | 关键场景、求解器解不出的序列 |
| RND | 随机 | 约束随机取值 | 大面积取值组合的撒网 |
| G | 组合 | 枚举笛卡尔积 | 需要穷尽两三个维度的组合 |
| RPLY | 重放 | 复现失败种子 | 失败复现、bug 关闭后回归 |
| SPCL | 专项 | 针对性变异 | 边界附近、异常注入、模型推不动的地方 |

**同一个维度用三种方法生成是常态**：长度取固定值 → D；长度在范围内随机 → RND；
长度 × 反压模式 全枚举 → G。它们产出的属性取值可能相同、只是方法不同 ——
这种在去重时应判为**同一覆盖点、不同手段**，而不是两条独立用例。

## 五、L6 检查为什么也是属性

**这是最容易漏的一层。** 一个用例往往**同时**挂多种检查：

| 检查类别 | 采什么 | 例（中性） |
|---|---|---|
| 功能检查 | 数据完整性、协议正确性 | 事务是否完整、有无丢失 |
| 白盒检查 | 内部状态、计数、队列水位 | 队列不溢出、资源计数平衡 |
| 性能检查 | 时序 / 吞吐 / 恢复 | 解除后吞吐恢复时间达标 |

**为什么不能塞进用例名**：同一份激励可以用不同检查去观察。若把检查编进名字，
就得出「功能检查版」和「白盒检查版」两份几乎一样的激励 —— 重复，且改一处忘一处。
把检查做成可挂载的属性，一个用例就能同时挂多个检查标签。

## 六、环境指纹为什么必须记

工具版本 / 设计版本 / 约束版本 / 接口版本 / 配置档位 / 种子 / 编译选项 ——
这些**不属于用例主体**（它没在测工具版本），但会改变结果。

| 不记会怎样 | 具体后果 |
|---|---|
| 失败无法复现 | 换个工具版本重跑，结果不一样，且不知道差异从哪来 |
| 「回归通过」不可信 | 你跑的和别人跑的不是同一个东西 |
| 覆盖率数字漂移 | 约束版本变了，命中分布跟着变，但报告看不出来 |

**判据**：凡「会改变结果、但不属于被测主体」的因素，一律进环境指纹，
**每个用例执行时都必须带**。它不是用例的属性，是用例的**执行属性**。

## 七、属性正交：分类成立的前提

这套方法成立的**唯一前提是属性正交** —— 同一信息只能存在于一个层级。

反例（都是示意）：

| 破坏正交的写法 | 哪里错了 |
|---|---|
| 「尾拍」既是维度取值，又当用例名前缀 | 同一信息出现在两层 → 检索时两处都要查，且可能只改一处 |
| 「随机」既是一种方法，又当一种反压模式的取值 | 生成方式与现象混层 → 组合时凭空多出一批语义错误的用例 |

**判断标准**：*同一个信息只能存在于一个层级。*
如果一条信息你在两处都写了，那么两处迟早会不一致，而没有任何规则能告诉你哪处对。

## 八、属性表的最小字段集

属性表才是用例的**真正主体**，文件名只是索引。

| 字段 | 含义 |
|---|---|
| 用例 ID | 唯一标识（人读的坐标，结构化用） |
| 对象 / 子对象 | L1 / L2 |
| 涉及维度 | L3（一组） |
| 字段取值集合 | L4（维度下每个字段取什么值） |
| 生成方法 | L5 |
| 所属交叉组 | 该用例属于哪个维度组合 |
| 检查项 | L6（可多个） |
| 覆盖仓映射 | 这些取值对应哪些覆盖点 |
| 环境指纹 | 见第六节 |
| 预期结果 | 判据（与检查项配合） |
| 关联用例 | 与谁同组 / 谁的重放 |

**命名只保留必要层次**：人读的坐标（对象-子对象-方法-序号）留在名字里，
其余属性放元数据 —— **命名是人读的坐标，属性表是机器可检索的坐标**。

## 九、检查清单

| 检查项 | 问题 |
|---|---|
| 维度只归类 | 有没有哪个「维度」其实带着取值（该是字段）？ |
| 字段才有取值 | 有没有哪个「字段」其实是一组东西（该是维度）？ |
| 方法不混入 | 「随机/定向/组合」有没有被当成一个被测属性？ |
| 检查可挂载 | 一个用例能不能同时挂功能+白盒+性能，而不是各写一份？ |
| 环境齐全 | 每个用例都带环境指纹吗？失败能靠它复现吗？ |
| 正交 | 有没有同一信息出现在两个层级？ |
| 去重 | 两个用例若对象+子对象+字段取值全同、只差方法，判过是重复还是不同手段吗？ |
| 缺口可映射 | 覆盖率缺口能直接指到「某字段的某取值」吗？ |

## 十、坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 把属性塞进用例名 | 名字自解释，一眼看懂这条测什么 | 无法检索、无法组合；改一层要改全部名字 |
| 把维度当字段（如「尾拍反压」做成维度） | 「尾拍反压」听起来就是个完整场景 | 维度数随取值数膨胀，取值变化要新增维度 |
| 把字段当维度 | 一个字段就是一组相关条件，看起来合并很自然 | 覆盖统计串味，缺口归不到具体取值 |
| 把方法当维度（如「随机反压」） | 「随机」「定向」确实像两种模式 | 组合爆炸，且去重规则失效 |
| 把检查当对象 | 「白盒检查」是个明确的验证活动 | 检查挂了，激励却没写，验证主体被偷换 |
| 漏环境指纹 | 只关心「用例测什么」，觉得版本是环境的事 | 失败无法复现，「回归通过」不可复现即不可信 |
| 一个对象平铺所有维度 | 有什么就列什么，省事 | 维度交叉矩阵无从建起，必交叉/可选/禁止表达不出 |

> **最值钱的两条**：**正交**（同一信息只在一个层级）与**环境指纹**（不记就无法复现）。
> 前者决定属性表能不能当查询用，后者决定它是不是一张可信的表。
