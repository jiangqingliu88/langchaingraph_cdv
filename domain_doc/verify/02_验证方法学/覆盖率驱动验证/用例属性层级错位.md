# 用例属性层级错位

> **一句话**：分层方法给的是一套**判据**，错位给的是**违背判据时的症状**。
> 四类错位都极其诱人 —— 它们不是「不小心」，而是「听起来完全合理」。
> 所以本卡的重点是「**为什么诱人**」那一列：不诱人就不会有人犯。

## 适用场景

- 用例表越写越长，但说不清「是不是已经覆盖到了」
- 覆盖率报告里某一块永远涨不上去，删掉一个「维度」它反而涨了
- 评审别人的测试计划，觉得层级不对劲但说不上哪里不对
- 要重构一份历史遗留用例表，先得知道它到底错在哪几处

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 建立正确的六层模型 | KB-DV-METH-005 用例属性模型 |
| 结构树 / 专题 / 交叉怎么组织 | KB-DV-METH-006 功能组织树与专题 |
| 覆盖点本身推得不全 | `verify/07_度量与报告/覆盖率模型/` |
| 缺口怎么收、豁免门槛 | `verify/07_度量与报告/覆盖率收敛/` |

## 一、四类错位速查

| 错位 | 错误做法（示意） | 一句话后果 |
|---|---|---|
| 把字段当维度 | 维度叫「尾拍反压」，没有下层字段 | 维度随取值数膨胀，加取值要加维度 |
| 把维度当对象 | 把「反压比例」当独立被测对象 | 组织树爆炸，一个取值维度变一个验证主体 |
| 把方法当维度 | 维度叫「随机反压」，字段是各种比例 | 方法混入属性，组合爆炸、去重失效 |
| 把检查当对象 | 把「白盒检查」当被测主体 | 检查挂了，激励却没写，主体被偷换 |

> 下表用**中性示意**：`尾拍反压` / `白盒检查` 这类写法是重灾区示范，
> 不是要你去本仓库找它们，而是让你认出这个**形状**。

## 二、把字段当维度

### 错误做法
维度叫「尾拍反压」（把某个**取值**当成维度名），底下没有字段。

### 为什么诱人
- 「尾拍反压」是个**完整、可命名的场景** —— 读起来就像验证计划里该有的一条
- 一条维度配一条用例，**一一对应**，写起来心理负担最小
- 从测试工程师视角看，场景名就是维度名，这正是传统 hand-written 用例的思维惯性：**先想场景，再起名字**

### 后果
- 维度数量随取值数**线性膨胀**：反压模式有 5 种取值 → 5 个维度
- 新增一种反压模式 = **新增一个维度**，而维度是要进交叉矩阵、要进专题的 → 改动面放大
- 覆盖统计**没法做**：反压模式这一维的覆盖率本该是「命中取值 / 总取值」，
  现在变成「命中的维度数 / 维度总数」，两者在数字上巧合相同、在语义上完全不同

### 正确做法
- 维度叫**条件类**（`反压模式`），取值 5 个（无 / 某拍 / 持续 / 随机 / …）作为字段取值
- 新增一种模式 = **在字段下加一个取值点**，维度不动、矩阵不动、专题不动

### 判据
**维度名如果只能在某个取值下成立，它就是字段。** 能这样造句的：反压模式**取**尾拍 ——
「尾拍」是「反压模式」的取值。反过来不能造句的（如 `反压模式` 只能是某个「尾拍」的一部分）才可能是维度。

## 三、把维度当对象

### 错误做法
把「反压比例」当成独立的被测对象，与真正的对象（如流控）平级。

### 为什么诱人
- 它**可以独立观察**：反压比例确实能在波形上量出来，看起来满足「外部可观察的行为」
- 很多验证计划就是按「可测参数」组织章节的 —— 参数即章节，读起来条理清晰
- 一个维度单独成章，**章节粒度均匀**，排版上舒服

### 后果
- 组织树**爆炸**：对象/子对象的判定标准是「验证主体」，而维度只是主体的一个条件，
  一旦升格，树里塞满了本不该是主体分量的东西
- **一个维度只能属于一个对象**了：同一维度的取值不能跨主体复用了 —
  可实际上「比例」这类条件往往在多个主体上都要用
- 功能组织树（结构骨架）和维度（横切条件）**两条轴混成一条** →
  「同一批属性测多个主体」这种组织方式再也表达不出来

### 正确做法
- 对象/子对象是**验证主体**（用外部行为可描述的**那个东西**）
- 维度是主体**之下**的一组会变化的条件，可以被多个主体共享
- 一个维度能被复用，恰恰证明它是维度而不是对象

### 判据
**能问「它在哪个主体上变化」的东西，是维度不是对象。**
反向自检：如果两个主体共用它，那它只能是维度 —— 对象是不共享的。

## 四、把方法当维度

### 错误做法
维度叫「随机反压」，字段是各种比例。把「随机」当成了反压属性的一部分。

### 为什么诱人
- 「随机反压」和「定向反压」读起来像**两种测试模式**，而模式听起来就是属性
- 团队口头禅就是「再跑一轮随机」，**表述习惯直接搬进了模型**
- 它确实**改变了生成结果**，所以和被测属性在现象上难以区分

### 后果
- **组合爆炸**：方法被当成维度后，方法数 × 其他维度数 进入笛卡尔积，
  出现「随机版本」和「定向版本」两批取值完全相同、只有生成方式不同的用例
- **去重规则失效**：正确的去重是「对象+子对象+字段取值全同、只差方法 → 判为同一覆盖点的不同手段」；
  方法混进维度后，去重器看不出它们该合并
- 语义失真：跑「定向」时你其实是在**指定某些取值**，而不是在测「定向」这件事 —
  把它当维度等于宣称「定向」是一个被测条件，可它对被测对象毫无意义

### 正确做法
- 方法**独立于对象与维度**，是每个用例的生成属性
- 同一个维度，五种方法都可用：固定取值 → 定向；范围内随机 → 随机；
  多维枚举 → 组合；复现种子 → 重放；边界变异 → 专项
- 方法写在用例的**属性表**里，不写进维度

### 判据
**问「它在被测对象上是否真实存在」** —— 方法只存在于生成侧，被测对象根本不知道
自己是被随机还是被定向激励出来的。真属于被测对象 → 维度；只属于生成侧 → 方法。

## 五、把检查当对象

### 错误做法
把「白盒检查」当成一个被测对象，与功能实体平级。

### 为什么诱人
- 「白盒检查」**是一个明确的验证活动**，有它自己的资源、进度、负责人
- 从项目管理的视角，检查项确实是可跟踪的工作包 → 自然成了组织单元
- **它是可观察的**：白盒检查的通过/失败在回归报告里一目了然，看起来完全满足「可观察行为」

### 后果
- **激励被偷换**：一旦检查成了主体，用例会围绕「怎么检查」写，
  而**忘掉怎么制造被检查的状态** —— 检查挂了，激励却没写
- 同一个激励被迫拆成多份：功能检查一份、白盒检查一份、性能检查一份 ——
  三份几乎一样的激励，改一处忘两处
- 覆盖统计被污染：检查覆盖率混进了**功能路径覆盖**，
  「白盒检查覆盖了 80%」这句话不含任何关于被测对象的信息

### 正确做法
- 检查是**可挂载的属性**，一个用例可同时挂功能 / 白盒 / 性能多个检查标签
- 同一份激励可以用不同的检查去观察，**不必为检查重写激励**
- 检查项清单独立维护，与用例是多对多关系

### 判据
**检查是「观察什么」，对象是「被观察的那个东西」。**
问「这个用例的激励在测谁」 —— 答案是被测对象；
再问「拿什么判它对不对」 —— 答案是检查。两问答案不该是同一个。

## 六、通用判据：同一信息只能存在于一个层级

四类错位有一个共同的根：**同一信息被放进了两个层级**（或放进了不该放的那个层级）。

| 自检问题 | 若答「是」则 |
|---|---|
| 这条信息在两处都写了吗？ | 立刻合并 —— 两处迟早不一致 |
| 这个「维度」名能在某个取值下才成立吗？ | 它是字段 |
| 这个「维度」能被两个主体共用吗？ | 它是维度（不是对象） |
| 这个「维度」在被测对象上真实存在吗？ | 不存在则是方法 |
| 这个「对象」的激励是在测谁？ | 与「拿什么判断」同答案则是检查 |

**一句话**：*同一个信息只能存在于一个层级。*
如果一条信息你在两处都写了，那么两处迟早会不一致，而没有任何规则能告诉你哪处对 ——
**两处真相必有一处先腐坏**。

## 七、检查清单

| 检查项 | 问题 |
|---|---|
| 维度不携带取值 | 有没有维度名里嵌着某个取值（如 `尾拍反压` 这种形状）？ |
| 对象是主体 | 有没有对象其实只是个可测参数？ |
| 方法独立 | 有没有「随机/定向」被写成了一个被测条件？ |
| 检查可挂载 | 有没有检查占了对象的位置、导致激励被偷换？ |
| 无两处真相 | 同一信息有没有在两个层级各写一遍？ |
| 去重有效 | 「只差方法」的用例能被判成同一覆盖手段吗？ |
| 缺口可归因 | 覆盖缺口能指到「某字段的某取值」而不是「某维度没跑」吗？ |

## 八、坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 用场景名当维度 | 场景即维度，一一对应，心智负担最小 | 加取值 = 加维度，改动面放大；统计语义错 |
| 用可测参数当对象 | 参数确实可观察，按参数分章很整齐 | 树爆炸，维度跨主体复用能力丢失 |
| 用测试模式当维度 | 团队口头禅直接进模型 | 方法×维度组合爆炸；去重规则失效 |
| 用检查当对象 | 检查是明确的工作包，管理视角很自然 | 激励被偷换；同一激励拆多份；覆盖统计被污染 |
| 「先这么写着、后面再拆」 | 错位的写法当下更好写 | 越晚拆代价越大：所有下游引用都建在错的分层上 |
| 只在报告里纠正、模型不动 | 报告能圆回来就以为没事 | 生成侧仍按错的分层造用例，重复持续产生 |

> **最值钱的两条**：**「为什么诱人」**（不承认诱人就会反复犯）与**两处真相**
> （所有错位的共同根因）。前者决定你能不能识别，后者决定你能不能根治。
