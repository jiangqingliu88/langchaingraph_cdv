# 约束设计方法学

> **一句话**：约束不是在"限制随机"，是在**声明激励空间有多大**。
> 空间画错了，再多种子也只是在错的地方反复走。

## 适用场景

- 新写一批约束，不知道怎么组织
- 覆盖率卡住，要判断是**约束的问题**还是**种子的问题**
- 接手别人的约束，要判断哪些能动、哪些不能动

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 覆盖点怎么推导 | `verify/07_度量与报告/覆盖率模型/功能覆盖率建模.md` |

| 缺口归因四分类 | `verify/07_度量与报告/覆盖率收敛/覆盖率收敛.md` |

## 一、六条设计原则

| 原则 | 说明 |
|---|---|
| **对准覆盖点** | 每个约束必须声明服务于**哪个覆盖点的哪个 bin** |
| **分层组织** | 指令生成 → 序列依赖 → 场景约束，逐层收紧 |
| **单维变化** | 每次只改一个维度，否则无法定位效果 |
| **保留基线** | 用 `constraint_mode()` 动态开关，**不直接删** |
| **小跑验证** | 改完先跑少量种子确认目标 bin 能命中，再放量 |
| **记录变化** | 哪一批、哪个缺口、改了什么、效果如何 |

**第一条是这套方法学的支点。** 没有 `targets` 的约束是**孤儿约束** ——
它可能没错，但没人知道它为什么存在，也没人敢删。评审时孤儿约束应该被质疑，
不是因为它有害，而是因为它**不可维护**。

> 为什么强调"保留基线、用 `constraint_mode()` 而**不是**直接删"：
> 删掉的约束在下一次设计变更后可能又要加回来，而那时没人记得原来写成什么样。
> 动态开关把"这次不启用"和"这个约束不要了"分成两件事。

## 二、三层约束

```text
第 1 层：基础约束（单条激励的取值空间）
    ↓
第 2 层：序列约束（激励之间的依赖关系）
    ↓
第 3 层：场景约束（针对特定缺口的定向约束）
```

| 层 | 管什么 | 典型内容 | 什么时候动它 |
|---|---|---|---|
| **1 基础** | 一条激励合法吗 | 操作码分布、地址范围、字段互斥 | 空间本身画错了 |
| **2 序列** | 两条激励之间的关系 | 写→读、配置→启动、依赖链 | 有 bin 需要特定**顺序**才命中 |
| **3 场景** | 针对某个缺口的定向收紧 | 固定到边界值、强制某种组合 | 前两层都对，就是差那一个 bin |

**分层的好处是定位**：覆盖率不涨时，先看是哪一层没覆盖到 ——
第 3 层的问题不该去动第 1 层。动错层会把已有覆盖打散。

## 三、缺口类型 → 约束手法（本卡最值钱的一张表）

**先判断缺口属于哪一类，再动对应的手法。判错类型 = 白改一轮。**

| 缺口类型 | 手法 | 具体做法 | 例子 |
|---|---|---|---|
| **bin 命中少** | 加权重 | 提高目标值概率 | `opcode dist { MUL := 20 }` |
| **边界不命中** | 收窄范围 | 固定到边界值 | `num_writes == FIFO_DEPTH` |
| **序列不命中** | 加条件 | 固定操作顺序 | `instrs[i].rs1 == instrs[i-1].rd` |
| **组合不命中** | 加新变量 | 增加交叉维度 | 引入 `data_pattern` |
| **完全不可达** | 放松约束 | 去掉过紧的限制 | 去掉过紧的 `inside` |

**最容易搞反的是最后一行。** 前四种都是"收"，最后一种是"放" ——
当所有收紧都无效时，要考虑**是不是约束本身把那条路径堵死了**。
一个过紧的 `inside` 会让某个 bin 永远命中不了，而现象与"随机化不足"完全一样。

> **还有第六种，不在约束层解决**：bin 命中了但结果错 —— 那是 DUT bug，
> 进 debug，不要试图用约束绕过它。

## 四、约束变化流程

```text
发现覆盖率缺口
    ↓
分析缺口类型（上文五类 + DUT bug）
    ↓
修改约束 —— 每次只改一个维度
    ↓
跑少量种子验证（确认目标 bin 真能命中）
    ↓
放量跑，合并覆盖率
    ↓
记录约束变化和效果
```

**「每次只改一个维度」是这条流程里唯一不能省的一步。** 一次改三处，
覆盖率涨了也不知道是哪处起的作用，跌了更不知道是哪处搞坏的 ——
而约束之间的相互作用正是最难凭直觉判断的东西。

**「先小跑」同样不能省**：放量跑一轮回归的代价是几小时到几天，
而验证"目标 bin 能不能命中"只需要几个种子。

## 检查清单

| 检查项 | 问题 |
|---|---|
| targets | 每个约束都声明了它服务于哪些 coverpoint 的哪些 bin 吗？ |
| 孤儿 | 有没有没人认领的约束？（评审时应该被质疑） |
| 分层 | 这个约束属于哪一层？改动是否越层了？ |
| 单维 | 这次改动是不是只动了一个维度？ |
| 基线 | 旧约束是用 `constraint_mode()` 关掉的，还是直接删了？ |
| 过紧 | 有没有 `inside` / 固定值把某条路径堵死了？ |
| 小跑 | 放量之前，用少量种子验证过目标 bin 能命中吗？ |
| 记录 | 这一轮改了什么、覆盖率变化多少，记下来了吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 约束不写 `targets` | 「我自己知道它是干嘛的」 | 孤儿约束：后人不敢动、不敢删，也不知道能不能改 |
| 直接删掉不用的约束 | 干净利落 | 设计变更后要加回来时，没人记得原来怎么写的 |
| 一次改多个维度 | 「这几处都要调，一起改了快」 | 覆盖率变化归因不了，下一轮继续瞎调 |
| 改完直接放量 | 「先跑起来看看」 | 目标 bin 命不中，白跑一整轮回归才发现 |
| 用约束硬凑覆盖率 | 「反正 bin 命中了就行」 | 覆盖点可能本身定义错了，凑出来的是假覆盖 |
| 认为"不涨 = 约束不够" | 直觉如此 | 有时是约束**太紧**（见上表最后一行），方向完全相反 |
| 层混着改 | 反正都是约束 | 第 3 层的定向约束会打散第 1 层的空间分布，已有覆盖回退 |
