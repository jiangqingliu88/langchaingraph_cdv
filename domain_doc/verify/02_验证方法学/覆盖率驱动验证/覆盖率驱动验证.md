# 覆盖率驱动验证

> **一句话**：覆盖率是**输入**，不是**输出**。
> 先定「要测到什么」（覆盖目标），再由目标反推「激励该怎么长」（约束 / 场景），
> 跑完看差距、补激励 —— 这个闭环叫 CDV（Coverage-Driven Verification）。
> 把覆盖率当成绩单，就退化成「先写激励、再统计碰巧覆盖了什么」。

## 一、定义

覆盖率驱动验证是一套**闭环方法**：用可测量的覆盖目标定义「验证完成」，
用随机 + 约束生成激励去逼近目标，用覆盖率反馈决定下一步激励该补什么。

**闭环的四步**：

| 步 | 动作 | 方向 |
|---|---|---|
| 1 | 从规格 / 契约**推导覆盖面** | 规格 → 覆盖点 |
| 2 | 从覆盖点**反推激励约束** | 覆盖点 → 约束 / 场景 |
| 3 | 运行、**测**覆盖率 | 运行 → 覆盖率数字 |
| 4 | **缺口 → 补激励 → 回到 3** | 覆盖率 → 下一轮激励 |

**第 2 步是「驱动」二字的全部含义**：不是先随便撒激励再看覆盖了什么，
而是先看缺哪个 bin、再问「什么样的激励才能命中它」。

## 二、边界（不是什么）

- **CDV 不是「跑随机 + 看覆盖率报告」**。只随机不反推，就是「撒网碰运气」；
  有覆盖目标牵引的随机才叫 CDV。
- **CDV 不等于「覆盖率数字高」**。数字高只说明「模型里定义的 bin 被碰过」，
  不说明模型本身全（模型漏了，数字照样 100%）。
- **CDV 不是「不用定向测试」**。反推出来的约束若求解器解不出，就得用手写定向激励补 ——
  定向是 CDV 的**工具**，不是对立面。
- **CDV 不负责判据**。覆盖了「发生了」不等于「被正确处理了」——
  正确性靠 scoreboard / 断言，这两者是 CDV 之外的另一条腿。

## 三、为什么覆盖率是「驱动」而不是「度量」

这是本卡的核心命题。区别在**激励是在覆盖率之前还是之后写的**：

| | 度量视角（错） | 驱动视角（对） |
|---|---|---|
| 顺序 | 先写激励 → 跑 → 统计覆盖了什么 | 先定覆盖目标 → 再反推激励 |
| 覆盖率的作用 | 汇报进度、给领导看 | 决定**下一条激励该写什么** |
| 100% 的含义 | 「测够了，可以收工」 | 「我定义的范围测够了」，范围有没有洞是另一回事 |
| 缺 5% 时 | 「时间不够，忽略掉」 | 「这 5% 是哪条规格？豁免要拿可达性证据换」 |
| 回归的价值 | 收集数字 | 数字指出下一轮激励的方向 |

> 一句话判别：**如果你写完激励从来没因为覆盖率数字改过激励，那你做的是度量，不是驱动。**

## 四、从覆盖目标反推激励：怎么做

**核心动作：把「要命中的 bin」翻译成「激励必须满足的条件」。**

| 覆盖目标（想命中） | 反推出的激励条件 | 落成什么 |
|---|---|---|
| FIFO 满时写被拒 | 先写满（连续 `DEPTH` 笔写）→ 再在满状态下发起写 | 约束：`pre_fill == DEPTH` 后再 `wr`；或先发满场景 sequence |
| 非法 opcode 被拒 | 生成一个协议不允许的 opcode 取值 | 约束里**反向**放开非法值（`op inside {illegal}`），不能只靠默认合法约束 |
| 读-写同拍竞争 | 同一拍同时拉高 `rd_en` 与 `wr_en` | 约束：`rd_en && wr_en` 同周期；或定向 sequence |
| 背压下的传输 | 让 `ready` 保持低若干个周期 | 需要在**对端模型/TB**上注入背压，随机约束管不到 |
| 特定状态转移 A→B→C | 让激励连续三步都满足转移条件 | 多周期约束 / 定向 sequence，单笔随机做不到 |
| 边界值（max/min） | 让分数字段取到极值 | 约束：`len dist {MAX := 1, MIN := 1, [中间] := w}` |
| 并发事件 | 两个端口同拍都有请求 | 约束两端口 `req` 同周期 |

**三条反推原则**：

1. **随机解决「组合」，定向解决「序列」**。取值组合交给约束随机；多周期序列、
   对端背压这类「环境行为」，约束随机管不到，要写定向激励或改环境模型。
2. **覆盖率上不去，先分「激励没撒到」还是「模型漏了」**。
   前者补约束 / 补定向，后者回去改覆盖模型（见 `verify/07_度量与报告/覆盖率模型/`）。
3. **补激励要补在**约束 / sequence**层**，不要在 test 里加 `if` 硬编码 ——
   后者破坏随机、不可复用、下个项目还要再写一遍。

## 五、与易混概念的区别

| 易混对 | 差在哪 |
|---|---|
| CDV vs 随机测试（CRV） | CRV 是「怎么生成激励」的技术；CDV 是「用覆盖率牵引随机」的方法学。有 CRV 不一定有 CDV。 |
| 覆盖率 vs 覆盖模型 | 模型是**定义**要测什么（coverpoint/bin），覆盖率是**测量**测到了多少。数字受模型对错支配。 |
| 功能覆盖率 vs 代码覆盖率 | 代码覆盖率（行 / 条件 / 翻转）说「RTL 有没有被跑过」；功能覆盖率说「**应该测的情况**有没有被测到」。代码覆盖率高 ≠ 功能覆盖够。 |
| CDV vs 断言 / 形式 | CDV 管「测到了没有」，断言 / 形式管「对不对」。两者互补：CDV 找激励缺口，形式补不可达证明。 |
| 覆盖率驱动 vs 需求驱动 | 需求驱动定「验什么」的**范围**，CDV 定「怎么知道验完了」的**判据**。CDV 的覆盖点应追溯到需求。 |

## 六、检查清单

| 检查项 | 问题 |
|---|---|
| 目标先行 | 覆盖模型是在写激励**之前**定的吗？ |
| 反推痕迹 | 有没有「因为某个 bin 没中，而改了约束 / 补了序列」的具体记录？ |
| 可命中性 | 每个 bin 都问过「什么激励能命中它」并且能做到吗？ |
| 缺口归因 | 缺的 bin 判过是「激励没撒到」还是「模型漏了」吗？ |
| 序列兜底 | 多周期 / 背压类目标，有没有配定向激励，而不是指望随机？ |
| 判据独立 | 覆盖率之外，「发生了」和「被正确处理了」分开覆盖了吗？ |
| 豁免证据 | 每个 ignore 都拿得出可达性证据吗？（不是「难就 ignore」） |

## 七、坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 先写激励后看覆盖率 | 写激励是「正经工作」，覆盖率看起来只是统计 | 退化成撒网碰运气，覆盖模型成了事后补的装饰 |
| 把 100% 当验证完成 | 数字好看、汇报有底气 | 模型漏洞时 100% 是假象；「测够了」其实是「我定义的太少」 |
| 缺的 bin 直接 ignore | 收敛快、月底好交差 | 用「删掉目标」冒充「达成目标」，签核证据是假的 |
| 只补激励不改模型（或反之） | 认准一个方向省事 | 模型漏的洞，永远补不出来；激励撒不到的 bin，永远涨不上去 |
| 在 test 里硬编码补激励 | 定向激励见效快 | 破坏随机、不可复用，下个项目重写一遍 |
| 代码覆盖率高就当功能覆盖够 | 代码覆盖率工具自动出、数字全 | 代码被跑到 ≠ 功能场景被覆盖，两者不是一回事 |
| 覆盖率与判据混建 | 一个 covergroup 又采样激励又采样结果 | 判据不独立，scoreboard 形同虚设 |

> **最值钱的两条**：**反推**（有没有因为覆盖率改过激励）和**豁免**（ignore 拿不拿得出证据）。
> 前者决定你做的是不是 CDV，后者决定你的数字是不是真的。

## 出处

- CDV 作为「覆盖目标牵引激励、闭环收敛」的方法学，是 `UVM` / `SV` 验证流程与 `ABV` 结合后的
  通用实践，非本仓库特有。
- 本卡只讲**方法学原理**。**覆盖点怎么建模** → `verify/07_度量与报告/覆盖率模型/`；
  **缺口怎么收、豁免门槛** → `verify/07_度量与报告/覆盖率收敛/`；**签核标准** →
  `02_流程与签核/`；**形式补不可达证明** → `verify/02_验证方法学/形式验证/`。
