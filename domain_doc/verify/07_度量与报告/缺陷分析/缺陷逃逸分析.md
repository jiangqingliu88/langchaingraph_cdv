# 缺陷逃逸分析：漏出的 bug 该回到哪里补

> **一句话**：逃逸的 bug **不是「运气不好没测到」，是某条防线有个确定的缺口**。
> 修 bug 只是止血；找到「哪一类防线缺了」并把它补成覆盖点或断言，才是分析的目的。

## 适用场景

- 回归全绿，但后仿 / FPGA 原型 / 硅上出现了功能 bug
- 一次 bug 复盘，想把「下次不再犯」落成具体动作
- 要评估当前验证环境的「防逃逸能力」，而不是只看覆盖率百分比

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 当前这个 bug 怎么定位、怎么改 | 调试流程 / 设计侧 RTL 卡 |
| 覆盖率数字推不上去 | `verify/07_度量与报告/覆盖率收敛/覆盖率收敛.md`（KB-DV-COV-005） |
| 回归跑得慢 / 不稳定 / 怎么选种子 | 回归治理相关卡 |
| 这个项目一共出了多少 bug | 项目案例域 |

## 步骤

### 第 1 步：确认它确实是「逃逸」，不是「没测」

不是所有漏网都叫逃逸。先分清楚：

| 情况 | 是不是逃逸 | 说明 |
|---|---|---|
| 该场景**没有用例**覆盖 | 不是（是缺口，不是逃逸） | 这属于覆盖率收敛问题 |
| 该场景**有用例、跑过、且绿**，bug 仍在 | **是逃逸** | 用例没打到，或检查没报 —— 这才是本卡对象 |
| 该场景**跑到一半报错**但被判成「已知问题」waiver 了 | 是逃逸 | waiver 用错了，见坑表 |

**判据**：逃逸的 bug 一定满足「激励到达过该逻辑、但没被判定为错」。

### 第 2 步：归到四类根因

| 根因 | 判据（怎么确认） | 本卡的对策方向 |
|---|---|---|
| **① 激励缺失** | 触发 bug 需要的**输入序列/时序**随机激励结构上到不了 | 新增覆盖点描述该场景；补 sequence / 定向用例 |
| **② 检查缺失** | 激励**到了**，但 scoreboard / 断言**没检查这个行为** | 新增断言 / 参考模型检查项 |
| **③ 模型漏洞** | 检查模型（参考模型、VIP）本身**对错误的建模是错的** | 修参考模型；加对模型自身的自检 |
| **④ 环境问题** | 环境（时钟/复位/VIP连接/sample时序）导致该场景**实际没被真正执行** | 修环境；加环境自检断言 |

**归因顺序**：先排除 ④（环境问题会伪装成前三种），再分 ①②③。

> **① 与 ② 的分界线**：问「如果激励到了，检查会不会报错」。
> 会报 → 缺的是激励（①）；不会报 → 缺的是检查（②）。
> 这个问句用一个**临时的定向用例**就能验证：手写激励打进去，看 scoreboard 报不报。

### 第 3 步：把结论落成防线（这一步最常被跳过）

**修 bug ≠ 分析完成。** 分析完成的标准是：

| 根因 | 必须产出的东西 |
|---|---|
| ① 激励缺失 | **一个新增覆盖点**（描述这个场景）+ 一个能命中它的用例 |
| ② 检查缺失 | **一条新增断言或 scoreboard 检查**，且能用修复前的 RTL 复现报错 |
| ③ 模型漏洞 | 参考模型的修复 + 一条针对模型的自检 |
| ④ 环境问题 | 环境自检断言（如「该场景标志本该拉高」） |

**验证防线有效性的方法**：把 bug 修复**回退**（或用 bug 版本的 RTL），
重新跑新增的用例/断言 —— **必须失败**。不失败说明防线没接上。

### 第 4 步：记录并复用

每条逃逸记一行：

| bug | 逃逸阶段 | 根因 | 防线产物 | 回退验证 | 负责人 |
|---|---|---|---|---|---|
| 仲裁在背压下漏 grant | 后仿 | ① 激励缺失 | `cp_arb.gnt_under_backpressure` | 通过（回退后报错） | 张三 |
| 复位释放多拍导致状态错 | 硅上 | ② 检查缺失 | `assert_ff_reset_sync` | 通过 | 李四 |
| 参考模型对溢出处理错 | 后仿 | ③ 模型漏洞 | 参考模型修复 + 自检 | 通过 | 王五 |

**为什么要记这张表**：根因分布本身就是度量 —— 若四类里某一类反复出现，
说明验证环境在该方向系统性地弱，比「覆盖率 95%」更有信息量。

## 检查清单

| 检查项 | 问题 |
|---|---|
| 逃逸确认 | 该场景确实有用例、跑过、且当时是绿的吗？ |
| 归因顺序 | 先排除环境问题了吗？（它会伪装成前三种） |
| 分界 | ①/② 的分界是用实际激励验证过的，还是猜的？ |
| 防线 | 除了修 bug，新增了覆盖点或断言吗？ |
| 回退验证 | 用 bug 版 RTL 跑过新防线，确认它会失败吗？ |
| 记录 | 根因入库了吗？能看出四类的分布趋势吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 修完 bug 就算完 | 「问题解决了」最省事 | 同一个缺口下次换个地方再漏，等价于没分析 |
| 补了定向用例但不加检查 | 用例能复现就以为够了 | 下次相似场景换个形态，仍然漏 |
| 新增检查不回退验证 | 「逻辑上它应该能抓到」 | 防线可能压根没接上，以为自己有了保护 |
| 把 ① 和 ② 混为一谈 | 都是「没测到」 | 补错方向：该加断言却去加激励，反复补不上 |
| 环境问题当成功（假绿） | 用例绿了好交差 | 该场景从没真正被执行，覆盖率是虚的 |
| 根因只记不统计 | 「记下来就行了」 | 看不出系统性弱项，防逃逸能力原地踏步 |

> **本卡与覆盖率收敛卡的分工**：收敛卡处理「**已知**没覆盖的 bin 怎么推上去」；
> 本卡处理「**未知**的缺口已经在硅上暴露了，怎么把它变成已知」。两者的产物都是覆盖点，
> 但入口相反 —— 一个从覆盖率报告进，一个从 bug 进。
