# 覆盖率收敛：缺口归因四分类与对策

> **一句话**：覆盖率不涨，**九成时间不是「测得不够」，是「没搞清为什么不涨」**。
> 每个未覆盖 bin 都要被归到四类之一，四类的对策完全不同 —— 归错类就是把
> 随机激励反复加到同一个不管用的方向。

## 适用场景

- 回归跑了 N 轮，覆盖率数字纹丝不动
- 几个 bin 反复不命中，不知道是随机不到还是根本到不了
- 有人提议「再加点种子」「换个约束比例」，但没人说得清为什么

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 覆盖模型本身够不够全 | `verify/07_度量与报告/覆盖率模型/功能覆盖率建模.md`（KB-DV-COV-001） |
| 判断「现在能不能签核」 | `../../../02_流程与签核/验证签核.md`（KB-DV-FLOW-002） |
| 漏出去的 bug 该往哪补 | `../缺陷分析/缺陷逃逸分析.md`（KB-DV-COV-006） |
| 覆盖率数字怎么统计出来的 | 报告模板域 / 工具域 |

**边界提醒**：这张卡管**怎么把数字从 80% 推到 95%**；签核卡管**95% 之后能不能签字**。
两张卡在「未覆盖 bin 全部有归因」这一点上衔接 —— 归因是这里的产物，签核卡消费它。

## 步骤

### 第 1 步：先把「不涨」和「涨得慢」分开

| 现象 | 判据 | 含义 |
|---|---|---|
| **不涨**（平台期） | 连续 3+ 轮回归，新命中 bin 数为 0 | 剩余 bin 有系统性原因，必须逐条归因 |
| **涨得慢** | 每轮仍有新命中，但斜率很低 | 多半是随机分布问题，先调约束比例，别急着定向 |

**先量一轮的斜率，再决定要不要逐条归因。** 曲线还在缓慢上升时做归因，
会把「再跑几轮就到了」的 bin 误判成「到不了」。

### 第 2 步：对每个未覆盖 bin 做归因（四分类）

**这是本卡的核心。** 四类的判据互斥，逐条走一遍：

| 类别 | 判据（怎么确认） | 典型证据 |
|---|---|---|
| **① 随机化不足** | 该 bin 的**前置条件在别的 bin 里命中过**，只是这个组合没被随机出来 | 覆盖率数据库里同一 coverpoint 的邻近 bin 已覆盖；约束里能找到对应的 `dist` / `solve...before` |
| **② 缺定向用例** | 前置条件需要**特定序列或特定外部激励**，随机激励结构上到不了 | 需要「先做 A 再做 B 再做 C」的时序场景；或需要特定寄存器配置 / 协议错误注入 |
| **③ 架构不可达** | 目标值在 RTL 结构上**物理不可能出现** | 位宽决定的死值（如 2 位计数器不可能到 4）；参数化后恒假的分支 |
| **④ 工具问题** | 仿真行为正常，但覆盖率数据库**没记上** | 采样点放错时序（在时钟节拍之外采）；跨模块 / 跨仿真器合并丢失；X 值导致采样被丢弃 |

**归因的顺序很重要**：先排除 ④（工具问题排最后是因为它最容易被当成借口），
再排除 ③（不可达的要改模型或加 waiver），剩下才在 ① 和 ② 之间分。

> **① 与 ② 的分界线**：问「随机约束能不能表达出这个场景」。
> 能表达（有约束语言机制）只是没命中 → ①；不能表达（本质是序列/外部事件）→ ②。

### 第 3 步：按类别下手

| 类别 | 对策 | 代价 |
|---|---|---|
| **① 随机化不足** | 调约束（`dist` 权重、`solve...before`、加约束块）、调种子数 | 低 —— 优先做 |
| **② 缺定向用例** | 写定向 test，或把场景做成可复用的 sequence | 中 —— 每个场景一个用例 |
| **③ 架构不可达** | 改覆盖模型（删掉不可达 bin）或加 waiver 并写明理由 | 低，但**必须留证据** |
| **④ 工具问题** | 修采样点时序 / 修合并流程 | 低，但一旦是真问题，影响的是**全部**数字 |

**为什么先动 ①**：调约束的成本是一个文件的几行，改模型要评审，改 RTL 要重跑回归。
能用约束解决的绝不写定向用例。

### 第 4 步：把归因结论落成表

每个未覆盖 bin 一行：

| bin | 类别 | 判据 | 对策 | 负责人 | 状态 |
|---|---|---|---|---|---|
| `cp_arb.gnt_3` | ① 随机化不足 | 相邻 `gnt_0..2` 已覆盖 | 调 `dist` 提高 gnt_3 权重 | 张三 | 进行中 |
| `cp_err.timeout_after_retry` | ② 缺定向用例 | 需重试后再超时的两段序列 | 写定向 test | 李四 | 待办 |
| `cp_cfg.mode_111` | ③ 架构不可达 | 该模式被参数 `MODE_W` 钳死 | 加 waiver，注明参数依据 | — | 已 waiver |
| `cx_mem.rd_after_wr_same_cyc` | ④ 工具问题 | RTL 有该行为，DB 无记录 | 查采样时钟 | 王五 | 待查 |

**这张表就是签核的输入** —— 签核卡要求「所有未覆盖 bin 都有 waiver 或已覆盖」，
本表提供每条归因的证据。

## 检查清单

| 检查项 | 问题 |
|---|---|
| 斜率 | 归因之前，量过曲线斜率吗？确认是平台期不是上升期？ |
| 互斥 | 每个 bin 真的只归到一类吗？（归两类通常说明判据没走完） |
| 证据 | 每条归因都附了「怎么确认的」吗？还是只是猜的？ |
| 不可达 | 「不可达」的 bin 是查过 RTL 结构，还是只是没随机到？ |
| 工具 | 是否存在同一 bin 在别的回归里命中过？（那就是工具/合并问题） |
| 闭环 | 对策动完之后，**回来复测**该 bin 命中了吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 覆盖率不涨就加种子 | 「多跑总有」成本看起来最低 | 若是 ②③④ 类，跑再多轮也是白跑，浪费回归算力 |
| 把不可达 bin 也去追 | 「覆盖率要 100%」目标听起来正当 | 追一个物理达不到的值，最后靠自欺的 waiver 收场 |
| 缺定向用例当成随机不足 | 「就是没随到」最省事 | 反复调约束命中不了，几轮之后才承认要写定向 |
| 直接把到不了的 bin 删掉 | 删了数字立刻上去 | 掩盖了「这个场景到底该不该有」的判断，模型越来越松 |
| 怀疑工具问题但不去证 | 「大概是 DB 合并丢了」 | 若真成立，影响的是全部数字；不证就白等 |
| 归因不做表 | 口头说「这几个是随机的」 | 下一轮复用不了结论，签核时拿不出证据 |

> **本卡与签核卡的分工**：这张卡的产物是**归因表**，签核卡的产物是**结论**。
> 归因表没有，「未覆盖 bin 全有理由」这条签核准入就是空的。
