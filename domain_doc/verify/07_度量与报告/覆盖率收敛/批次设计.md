# 批次设计

> **一句话**：批次的设计原则不是"怎么把 case 分组"，而是
> **下一批跑什么，由上一批的缺口说了算**。

## 适用场景

- 要把一批用例组织成有推进节奏的回归
- 规划一个收敛周期（从环境自检到回归固化）怎么走

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 单个测试该跑多少种子 | `verify/07_度量与报告/覆盖率收敛/种子管理与平台期.md` |
| 批次怎么执行、怎么保证可复现 | `verify/04_工具与脚本/脚本与CI/回归流水线.md` |
| 覆盖率不涨怎么归因 | `verify/07_度量与报告/覆盖率收敛/覆盖率收敛.md` |

## 一、五条设计原则

| 原则 | 说明 |
|---|---|
| **覆盖率驱动** | 下一批由上一批的缺口决定，不是一次排好 |
| **小步快跑** | 每批 1–3 天，反馈快 |
| **目标明确** | 每批有明确的覆盖目标 |
| **种子匹配** | 不同批次用不同的种子策略 |
| **产出可量化** | 每批结束有覆盖率数字 + 缺口清单 |

**第一条决定了批次设计的性质**：它不是"计划"（一次排定），
而是**迭代**（每批结束时才知道下一批长什么样）。
把四个季度的批次一次性排满，等于放弃了这套方法学。

## 二、批次演进模型

```text
第 1 批：环境自检
  目标：验证测试平台本身能用
  种子：固定 1 个

第 2 批：功能探索
  目标：大面积扫描
  种子：50–200 个

第 3 批：空洞打击
  目标：定向补缺
  种子：少量，精准命中

第 4 批：回归固化
  目标：稳定收敛
  种子：黄金种子集 + 探索种子
```

| 批次 | 在回答什么问题 | 典型产出 |
|---|---|---|
| **1 环境自检** | 测试平台本身对不对？ | 冒烟通过 / 环境 bug |
| **2 功能探索** | 空间有多大是能走到的？ | 覆盖率从 0 到 60% 量级 |
| **3 空洞打击** | 剩下的洞各是什么性质？ | 归因结论 + 定向用例 |
| **4 回归固化** | 这个数字稳不稳、能不能复现？ | 黄金种子集 + 稳定覆盖率 |

**第 1 批的种子是 1 个，理由是它要证伪的对象是环境而不是 DUT。**
环境 bug 在第一个种子就会暴露，跑 100 个种子只是把同一个 bug 报 100 遍。

**第 2 批到第 3 批的种子数会骤降**（50–200 → 少量），这是对的：
第 2 批是广度，第 3 批是精度。第 3 批的定向约束本身就是"精准命中"，
再用大量种子去撞是重复劳动。

## 三、批次配置表

| 批次 | 测试名 | 约束 | 目标覆盖点 | 种子策略 | 预期覆盖率 |
|---|---|---|---|---|---|
| 1 | `<basic_test>` | `<基础约束>` | `<基础覆盖点>` | 固定 1 个 | 30% |
| 2 | `<random_test>` | `<宽松约束>` | `<主要覆盖点>` | 50 个随机 | 60% |
| 3 | `<directed_test>` | `<定向约束>` | `<缺口覆盖点>` | 20 个随机 | 75% |
| … | … | … | … | … | … |
| N | `<random_mix_test>` | `<宽松混合>` | `<全部>` | 100 个随机 | 防过拟合 |

**最后一行的「混合」批次是必须的**：如果回归里全是定向用例，
覆盖率会很漂亮，但那是"我们知道要测什么所以测到了" ——
它证明不了"我们不知道的角落也走到了"。混合批的作用就是带回随机性。

> 这张表的**格式**（它作为计划文件长什么样）见
> `verify/07_度量与报告/覆盖率模型/功能覆盖率YAML建模.md`；
> 本卡讲的是**怎么决定表里填什么**。

## 四、推进节奏

```text
批次大小：小步快跑，每批 1–3 天
每批 case 数：5–20 个
每批种子数：视 case 类型而定
每批产出：合并覆盖率 + 缺口清单 + 下一批计划
```

**「每批产出」里第三项是这条节奏能持续的原因**：每批结束必须产出
**下一批的计划**，否则"覆盖率驱动"就断了 —— 变成一批批跑完再看。

**不要一次设计几十个 case 跑一周。** 批次太大，反馈周期太长，
缺口分析滞后于设计变更，跑完发现要改的东西已经过期了。

## 检查清单

| 检查项 | 问题 |
|---|---|
| 驱动 | 这一批的目标是从上一批的缺口清单里来的吗？ |
| 迭代 | 下一批的计划是这一批结束时才定的吗？（还是早就排满了） |
| 时长 | 这一批跑几天？超过 3 天了吗？ |
| 目标 | 每批有明确的覆盖目标，还是"尽量多测"？ |
| 种子 | 不同批次用了不同的种子策略吗？ |
| 混合 | 有防止过拟合的混合批次吗？ |
| 产出 | 每批结束有覆盖率数字 + 缺口清单 + 下批计划三样吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 一次排满所有批次 | 「计划性强、好汇报」 | 放弃覆盖率驱动，第 3 批该打哪儿只能靠猜 |
| 批次太大 | 「少跑几轮省事」 | 反馈周期长，缺口分析滞后，跑完发现要改的已过期 |
| 环境自检也撒大网 | 「反正跑都跑了」 | 环境 bug 第一个种子就暴露，其余全是重复报错 |
| 全是定向用例 | 覆盖率数字好看 | 只证明「知道的都测了」，证明不了「不知道的也走过了」 |
| 每批都用同一套种子 | 「统一策略好管理」 | 探索批次与固化批次的目的是相反的，一套策略满足不了两边 |
| 批次无目标 | 「这周把回归跑完」 | 跑完了也不知道达成了什么，下一批无从设计 |
| 批次产出不含下批计划 | 「先把这批跑完再说」 | 闭环断在这里，退化成"跑一批、看一批" |
