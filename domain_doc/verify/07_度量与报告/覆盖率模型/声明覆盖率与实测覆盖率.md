# 声明覆盖率与实测覆盖率 —— 两个不能合成的覆盖率数字

> **一句话**：「用例把该测的都写了吗」和「仿真真的打到了吗」是两个**正交**的问题，
> 各自一个数，**必须分列**。合成一个数，就等于把两种完全不同的故障混成一种。

## 一、定义

两个数字，两条链，各自独立闭环：

| | **声明覆盖率** | **实测覆盖率** |
|---|---|---|
| **回答** | 用例把**该测的都写了吗** | 仿真**真的打到了吗** |
| **量纲** | 模型 vs 用例表（完备性） | 实测命中 / **声明**的覆盖点 |
| **分子/分母** | 被任一线索命中的取值点 / 模型声明的取值点 | 仿真打到的 bin / 覆盖点里声明的 bin |
| **数据来源** | 用例模型 + 生成/整理的用例列表 | 仿真覆盖率数据库（跑出来的采样结果） |
| **负责角色** | 写测试计划的 DV 工程师（建模问题） | 跑回归、开 bin 的 DV 工程师（激励/采样问题） |
| **变更触发** | 改模型结构才会变 | 每次跑回归都会变 |

**一句话记法**：
- 声明覆盖率 = **写在纸上的够不够**（模型的属性）
- 实测覆盖率 = **真的打到了没有**（仿真的属性）

> 声明覆盖率的详细判法（八个方面）见 KB-DV-COV-007；
> 覆盖点本身怎么推导出来见 KB-DV-COV-001。

---

## 二、边界（不是什么）

这一节比定义更值钱 —— 说清「不是什么」，才不会把两个数用错地方。

| 它**不是** | 为什么 |
|---|---|
| 不是「过程覆盖率」 | 过程覆盖率量的是「哪些用例跑了」，两个数字都量的是「覆盖到了什么」 |
| 不是「代码 / 断言覆盖率」 | 那量的是 RTL / 断言的结构，两个数字量的都是**功能**覆盖点 |
| 不是「通过率」 | 用例通过 ≠ 覆盖点被打到；一个全通过的回归可能大半 bin 仍为 0 |
| 声明覆盖率**不是**「仿真结果」 | 它不跑仿真，只比对模型与用例列表 —— 100% 时仿真可能一次都没打中 |
| 实测覆盖率**不是**「模型完备性」 | 它不知道模型漏没漏点 —— 模型漏了，实测只会「在漏掉的范围里打得很满」 |
| 两者都**不是**签核结论 | 签核看的是缺陷收敛 + 覆盖达标 + waiver 门槛（见 `02_流程与签核/`） |

**最容易犯的边界错误**：把「实测覆盖率」当成「模型对不对」的证据。
实测高只说明「声明过的那部分打到了」，**对「有没有漏声明」完全无信息**。

---

## 三、与易混概念的区别

### 1. 声明覆盖率 vs 实测覆盖率

**这是本卡的核心区分。** 两者**交叉**而非重合：

| 情形 | 声明覆盖率 | 实测覆盖率 | 说明 |
|---|---|---|---|
| A 模型写全了 + 激励打到了 | 高 | 高 | 理想 |
| B 模型写全了 + 激励没打到 | **高** | 低 | **该测的没测** —— 补激励 |
| C 模型漏了点 + 打到的都打中了 | 低 | **可能高** | **测了的没打中**的反面：漏掉的范围根本没进分母 |
| D 模型漏了点 + 激励也不够 | 低 | 低 | 两头都缺 |

**从 B 与 C 看得很清楚**：声明 100% **丝毫不保证**实测 100%；
反过来实测 100% 也不能说明模型全 —— 分母是模型给的，模型漏了点数就不会低。

### 2. 两个「缺口」意味着什么

**缺口必须分列，因为两种缺口的动作完全不同**：

| 缺口 | 含义 | 谁的问题 | 动作 |
|---|---|---|---|
| **声明缺口**（声明覆盖率的洞） | 该测的没写进模型 | 建模者 —— 模型有没有洞 | 补模型 / 补用例，见 KB-DV-COV-007 与 [覆盖率收敛](../覆盖率收敛/覆盖率收敛.md) |
| **实测缺口**（实测覆盖率的洞） | 测了的没打中 | 激励/约束/采样 —— 跑得够不够、采得到不到 | 补激励、调约束、查采样点 |

**这就是为什么不能合成一个数**：
合成之后，一个「90%」你分不出它是
「模型全了、激励差一点」（补激励）还是「模型漏了一大块、打到的都满了」（补模型）——
**两种缺口要做的两件事，被一个数字抹平了。**

### 3. 「声明」在这里的两层含义（别绕晕）

本卡说的**声明覆盖率**里的「声明」，指**模型声明的取值点**（完备性的分母）；
而**实测覆盖率**的分母，也来自**覆盖点声明的 bin**。
两者都从「声明」出发，但一个是「模型对用例表」、一个是「仿真对覆盖点」——
**方向不同**：前者问「用例够不够」，后者问「跑到了没有」。

> 记住：**声明是分母，两条链都在用；差别在于分子是谁。**
> 声明覆盖率分子 = 用例命中；实测覆盖率分子 = 仿真命中。

## 四、两者必须分列：合成为什么有害

| 合成后的做法 | 后果 |
|---|---|
| 把两个数加权平均成一个「功能覆盖率」 | 分不出「该测的没测」和「测了的没打中」，缺口无法定位 |
| 只报合成数，不报分项 | 数字涨了不知道是建模改善还是激励改善；掉了一块也不知道该找谁 |
| 用一个数做签核门槛 | 可能被「模型漏点但打满」蒙混过关（C 情形） |
| 用一个数做项目对比 | 两个项目一个模型强、一个激励强，合成后看不出差异根源 |

**分列的最小要求**：

| 列 | 内容 | 谁看 |
|---|---|---|
| 声明覆盖率 | 模型对用例表的完备性（含八方面明细，见 KB-DV-COV-007） | 建模者 |
| 实测覆盖率 | 仿真打到 / 声明覆盖点（含逐 bin 缺口） | 跑回归、开 bin 的人 |
| （可选）差异说明 | 两者落差的原因归类 | 评审 / 签核 |

> **判据**：报表里若能用一个数答完「该测的测了没」和「打到了没」两问，
> 这个报表一定丢信息 —— 因为这两个问题**逻辑上不可能由一个数回答**。

## 六、坑

| 坑 | 表现 | 修正 |
|---|---|---|
| **把两个数字合成一个** | 报表只有一个「功能覆盖率」 | 分列声明与实测两列 |
| **拿声明 100% 当覆盖达标** | 模型全了就以为打到了 | 声明 100% 只保证「该测的都写了」，实测要另跑 |
| **拿实测高当模型全** | 「打到 95% 了，模型肯定没问题」 | 分母是模型给的，模型漏点数不会低，要另评模型完备性 |
| 缺口不分型 | 「差 10%」，不知补激励还是补模型 | 分声明缺口 / 实测缺口，各自定位动作 |
| 把合成数当签核门槛 | 用单一数字判放行 | 用 C 情形（模型漏点但打满）就能蒙混过关 |
| 声明侧混入真实用例缺陷 | 模型分因实现落后而变 | 声明覆盖率只量模型对用例表，实现差距另计（见 KB-DV-COV-007 原则二） |
| 忽略「测了的没打中」 | 只看「没写到的」 | 两个缺口都要看，C 情形最容易被漏 |
| 用实测覆盖率做项目对比 | 两个项目差异看不出根源 | 分列对比，才看得出是建模强还是激励强 |

**最值钱的两条**：
「把两个数字合成一个」直接摧毁缺口定位能力 —— 这是本卡存在的全部理由；
「拿实测高当模型全」让模型漏点在漂亮数字下被永久掩盖。
