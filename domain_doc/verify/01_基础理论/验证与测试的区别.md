# 验证与测试的区别

> **一句话**：测试是「拿已经做出来的东西去用，看能不能用」；
> 验证是「在设计还没做出来（或刚做出来）时，论证它是不是符合规格」。
> 方向、判据、证据三者都不同，所以它们的「通过」根本不是一回事。

## 一、定义

| | 测试（Test） | 验证（Verification） |
|---|---|---|
| 对象 | 已经存在的实体（硅、封装后的样片） | 设计本身（RTL、网表、模型） |
| 问题 | 「它能不能用 / 坏没坏」 | 「它是不是我（按规格）想要的那个东西」 |
| 参照物 | **规格**（功能是否达标） | **规格**（实现是否等价于规格） |
| 何时做 | 芯片回来之后（或流片前的原型） | 设计阶段，越早越好 |
| 判据 | 通过率、良率、失效模式 | 覆盖率、断言、形式证明、对照模型 |
| 能不能改 | 不能改设计（只能筛 / 分 bin / 报废） | **能改** —— 发现问题就回去改 RTL |
| 失败的含义 | 制造 / 工艺 / 边际问题 | 设计错误 |

**核心分野**：测试是「判断一个已存在的东西好不好的**筛选**行为」；
验证是「在东西定型前，反复施加激励去**证伪**设计意图」的工程行为。
验证的目标不是「通过」，而是「找到不通过的地方」。

## 二、边界（不是什么）

- **验证不是「跑很多 test」**。跑一万条激励但没有判据（reference model），
  只是跑了一万次仿真，什么都没证明。
- **验证不是「覆盖率涨到 100%」**。覆盖率是「我测到了哪些情况」的**度量**，
  不是「设计是对的」的**证明**（见 `verify/07_度量与报告/`）。
- **验证不等于仿真**。形式验证、等价性检查、静态检查、Emulation 都是验证手段，
  仿真只是其中最常用的一种（见 `verify/02_验证方法学/形式验证/`）。
- **测试不是低配版验证**。后仿、量产测试（ATE）、系统级 bring-up 是**不同阶段**的独立环节，
  不能拿「验证做完了」去替代它们，也不能拿「测试通过了」回来删掉验证。

## 三、与易混概念的区别

| 易混对 | 差在哪 |
|---|---|
| 验证 vs 测试 | 方向相反：验证是**设计 → 规格**（证伪），测试是**实体 → 规格**（筛选）。前者能改设计，后者不能。 |
| 验证 vs 确认（Validation） | 验证问「做对了没有（build the thing right）」，确认问「做对了**东西**没有（build the right thing）」。确认的对象是需求，验证的对象是规格。 |
| 验证 vs 调试（Debug） | 调试是**发现失败之后**定位根因的过程；验证是**制造能触发失败的机会**的过程。两者在时间上前后接力，不是同一件事。 |
| RTL 验证 vs 网表验证 | 对象不同：前者对 RTL 源，后者对综合 / 布局后的网表（含时序、DFT 插入）。同一个激励，两边能过的条件不一样 —— 这就是后仿存在的理由（见 `verify/` 后仿相关卡）。 |
| 功能验证 vs 形式验证 | 手段不同、目标相同（都为回答「实现 == 规格」）。形式穷举、仿真采样，覆盖的完备性来源不同。 |
| 验证 vs 签核（Sign-off） | 签核是**用验证/测试产出的证据做放行决策**的流程节点。验证是生产证据，签核是消费证据（见 `02_流程与签核/验证签核.md`）。 |

## 四、为什么常被混为一谈

| 诱因 | 具体表现 |
|---|---|
| 词都叫「test」 | `run_test`、`testcase`、`vcs -test` —— 验证的激励载体在代码里就叫 test，于是「跑测试」被理解成「做验证」。 |
| 都要「通过」 | 两者都有 pass / fail，但通过的含义完全不同：一个是「没发现反例」，一个是「筛掉了坏品」。 |
| 都归到「质量」名下 | 组织上常把 DV 与测试、可靠性放进同一个质量部门，职责边界被抹平。 |
| 「我测过了」的口语 | 口头说「测过了」时，说的人往往指的是「跑过仿真」——而听的人理解成「芯片能用」。 |

## 五、对实践的三个直接后果

| 后果 | 说明 |
|---|---|
| 验证计划不能照抄测试计划 | 测试计划按「失效模式 / 用例」组织，验证计划要按「**规格条款 → 覆盖点 → 激励**」组织。 |
| 「没找到 bug」不等于「设计正确」 | 验证只能**证伪**，不能**证实**（穷举除外）。所以签核要的是「覆盖了哪些 + 用了哪些手段」，不是「跑过了」。 |
| 有 bug 是正常的 | 测试发现了坏品会报废，验证发现了错误是**工作成果** —— 把「零 bug」当 KPI 的团队会逼人隐瞒。 |

## 六、检查清单（判断自己有没有在「验证」）

| 检查项 | 问题 |
|---|---|
| 判据 | 每个激励都有独立的**期望值来源**（参考模型 / 断言 / 协议 checker）吗？还是只看「波形没红」？ |
| 方向 | 我是在**证伪**设计，还是在**演示**它工作？ |
| 证据 | 「验证完了」能不能列出：覆盖了哪些规格条款、用了哪些手段、还有哪些没覆盖？ |
| 改设计 | 发现问题后，流程**允不允许**回改 RTL？如果答案是「测试阶段了不能改」，那这已经不是验证。 |

## 七、坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 用测试思维写验证计划 | 「列用例」看起来最省事、最像项目管理 | 验证计划变成用例清单，无规格追溯，覆盖率来了也对不上需求 |
| 把「跑过很多仿真」当成验证完成 | 跑的次数是可见的工作量 | 没有判据的仿真不证明任何事，越跑越自信 |
| 拿「测试通过」回填签核证据 | 芯片回来了、测试过了，看起来板上钉钉 | 测试通过只说明**这批样片**，不说明**设计**符合规格；两者证据不可互换 |
| 把「零 bug」当验证团队 KPI | 「零缺陷」听起来是最高标准 | 逼得人不敢报 bug，验证失去价值 |
| 以为形式验证/Emulation「也是测试」 | 都跑软件、都要等结果 | 手段混同 → 手段选择失去依据，该用形式的去堆仿真，该上 Emulation 的还在跑 RTL sim |

## 出处

- 概念辨析源自 IEEE 标准对 verification / validation 的区分，以及 DV 方法学（`UVM` 相关著作）对
  「验证目标是证伪、不是演示」的一贯表述。
