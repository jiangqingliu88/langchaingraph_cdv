# 回归流水线：一次回归怎么组织才是可复现的

> **一句话**：回归的价值不在「跑过了」，在于**任何一次失败都能被任何人用同一个种子
> 重新跑出来**。做不到这一点，回归产出的覆盖率数字和「全绿」结论都不可信 ——
> 因为它说不清「绿的是哪一份输入」。

## 适用场景

- 从零搭一条回归，或现有的回归老是「这次过下次挂」
- 覆盖率合不上，或者合并出来的数对不上单 case 报告
- 挂了一个 case，想单独重跑却复现不出同样的失败

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 跑一个 case，看波形定位 | `../Verdi/Verdi.md` |
| 查某个仿真器的命令行开关怎么写 | `../VCS/VCS.md` / `../Questa/Questa.md` |
| 定覆盖率签核门槛 | `../../07_度量与报告/` |
| 想设计 TB 结构本身 | `../../03_技术与组件/` |

## 可复现的定义（先立规矩）

一条回归可复现，必须满足：**给定同一份（RTL + TB + 编译开关 + 工具版本 + 种子），
任何人在任何机器上重跑，得到逐位相同的日志与覆盖率。**

| 要素 | 不钉死会怎样 |
|---|---|
| RTL / TB 版本 | 两次跑的其实是两份设计，数字不可比 |
| 编译开关 | 覆盖率度量集合变了，百分比就没意义 |
| **工具版本** | 随机求解器实现跨版本会变，同种子也给不同结果 |
| **种子** | 直接决定随机激励序列 —— 不记种子 = 不可复现 |
| 环境变量 / 依赖库版本 | UVM 库、VIP 版本不同，行为不同 |

> **工具版本也算输入**。这就是为什么「同一个种子必须给出同一个结果」这句话，
> 前面要隐含一句「在同一个工具版本下」。

## 步骤

### 第 1 步：种子管理 —— 种子是一等公民

**种子只有两种用法，不要混**：

| 用法 | 种子来源 | 用途 |
|---|---|---|
| **固定种子（定向复现）** | 人手指定一个数 | 复现某个失败、钉一条已知 bug 的触发条件 |
| **记录式随机种子（回归）** | 每跑一个 case **随机生成并记录** | 日常回归，追求覆盖面；**跑完必须把用到的种子写进结果** |

**怎么做**：

- 每个 case 运行时生成一个种子，**写进该 case 的结果文件**（不是只在日志里闪过）。
- 失败重跑时**先拿结果文件里的原始种子**再跑 —— 不要重新随机。
- 想扩覆盖就**换新种子重跑同一 case**：同一 case 多个种子 = 多条激励，这是回归覆盖率增长的主要来源。
- **禁止**「自动随机、失败就换个种子重跑到过为止」—— 那等于把失败藏起来。

```
case 表（生成） ──▶ 每个 case: {case_id, seed} ──▶ 跑 ──▶ 结果 {pass/fail, seed, 覆盖率库路径}
                                                        │
                                              失败 → 用记录的原种子 + debug 开关重跑 → 波形
```

> 仿真器侧的种子开关：VCS 用 `+ntb_random_seed=<N>`，Questa 用 `-sv_seed <N>`
> （见 `../VCS/VCS.md`、`../Questa/Questa.md`）。**流水线脚本要把这个值显式传进去并回写结果**。

### 第 2 步：编译与仿真的编排 —— 只编一次

| 阶段 | 跑几次 | 为什么 |
|---|---|---|
| 编译 | **一次**（每个配置/每套编译开关一次） | 分钟级；重编让「同一个 simv」不再成立，破坏可复现 |
| 仿真 | 每个 case × 每个种子一次 | 这才是并行展开的维度 |

**并行**：按「case × 种子」展开成任务列表，用调度器（GNU Make `-j`、`xargs -P`、
或集群提交）并行跑。要点：

- **每个任务独立工作目录**，别共享编译产物/覆盖率库 —— 互相覆盖是不可复现的隐形主因。
- 并行度受 license 与机器内存限制，**不是越高越好**：仿真器比 CPU 核更吃 license。
- 编译产物**只读共享**（各任务符号链接到同一份 `simv`），**运行期产物各自落目录**。

### 第 3 步：失败重跑 —— 分清「真失败」与「环境抖动」

| 类型 | 特征 | 处理 |
|---|---|---|
| **真失败** | 用原种子重跑**稳定复现** | 挂进 bug 跟踪，保留波形 |
| **抖动 / 非确定** | 原种子**复现不出**同样的失败 | **这是最危险的** —— 说明有非确定性来源（多线程、文件竞争、未初始化、时钟域竞态），当成 bug 查，别当运气 |

**重跑策略**：

- **不要**「失败自动重跑 N 次，过了就算过」—— 这会把真 bug 洗成绿。
- 正确做法：失败 → **用原种子 + 调试开关（dump 波形）** 重跑一次，拿到波形人查。
- 若确要区分抖动，也必须是「**用原种子**重跑仍失败才判过」，而不是「换种子」。

### 第 4 步：覆盖率数据库合并 —— 先对齐口径再合

**合之前必须保证**：

| 对齐项 | 不对齐的后果 |
|---|---|
| 覆盖率度量集合（VCS `-cm ...` / Questa `-coverage` + 度量开关） | 各 case 的数据库口径不同，合并后的分母/分子对不上 |
| 工具版本 | 新旧版本库格式不认，合并直接报错或丢数据 |
| DUT / TB 版本 | 结构变了，同一条 bin 在两份库里的含义不同 |
| 层次/实例名 | 改过例化名后，旧库的覆盖点映射不到新结构 |

**合并命令**：

```bash
# VCS：把每个 case 的 vdb 全喂给 urg
urg -full64 -dir cov/case1.vdb -dir cov/case2.vdb -dir cov/case3.vdb \
    -dbname merged.vdb -format both -report report -l urg.log

# Questa：把每个 case 的 ucdb 合并
vcover merge merged.ucdb cov/case1.ucdb cov/case2.ucdb cov/case3.ucdb
vcover report -html -htmldir cov_html merged.ucdb
```

**两个必须保留的东西**：

- **合并后的库（`merged.vdb` / `merged.ucdb`）**：下次增量回归要拿它当基线继续合。
- **单 case 与「哪些 case 覆盖了哪条」的映射**（URG `-show tests` 一类）：
  覆盖率漏洞定位时，你要知道的是「**缺哪条激励**」，不是「总百分比多少」。

> 覆盖率建模与签核门槛另成体系，见 `../../07_度量与报告/`。

### 第 5 步：结果归档 —— 让失败可复现、结论可审计

每个 case 至少归档这些（**缺一项，这一跑就不算可复现**）：

| 归档项 | 内容 | 为什么 |
|---|---|---|
| **case 标识** | case 名 / id | 定位 |
| **种子** | 实际用到的种子值 | 复现的钥匙 |
| **工具版本** | 仿真器版本号（+ UVM/VIP 版本） | 跨版本行为会变 |
| **编译开关** | 完整命令行（`vcs ...` / `vlog ...`） | 覆盖率口径与二进制都由它定 |
| **运行开关** | `simv` 后的 plusarg / `vsim` 的开关 | test 名、dump 开关等都在这 |
| **状态** | pass / fail / 抖动 | 汇总与门禁 |
| **日志** | 完整 stdout/stderr | 有错才有据 |
| **覆盖率库路径** | 该 case 的 `.vdb` / `.ucdb` | 合并要用 |
| **失败时的波形** | 仅失败 case 存 FSDB | 只失败才 dump，省空间 |

**一条铁律**：把上述归档和「同一个种子必须给出同一个结果」绑在一起 ——
**没归档这几项的回归结果，不能作为签核证据**，因为它经不起「再来一次」。

## 检查清单

| 检查项 | 问题 |
|---|---|
| 种子 | 每个 case 的种子都写进结果了吗？失败重跑用的是原种子吗？ |
| 编译 | 编译只做了一次吗？各并行任务共享同一份 `simv` 吗？ |
| 隔离 | 每个任务有独立工作目录与独立覆盖率库吗？ |
| 合并 | 合并前各库的度量集合、工具版本、DUT 版本一致吗？ |
| 门禁 | 失败判定是「用原种子稳定失败」还是「重跑随意」？ |
| 归档 | 版本/开关/种子/日志/覆盖率库都齐了吗？ |
| 环境 | 工具版本、UVM/VIP 版本、环境变量都记录了吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| **失败自动换种子重跑到过** | 「省事，绿了就好」 | 真 bug 被洗白，签核结论建立在假绿上 —— 这是最严重的一条 |
| 不记种子 | 反正日志里能翻到 | 换台机器/隔天就复现不了，失败只能整条重跑 |
| 所有 case 共享一个编译目录 / 覆盖率库 | 省磁盘、省搭建 | 互相覆盖，覆盖率数不可信，失败原因互相污染 |
| 覆盖率不先对齐口径就合并 | 想快点出总报告 | 合并后的数没有意义，甚至合并报错丢数据 |
| 只归档「总覆盖率百分比」 | 报告好看 | 漏洞定位时不知道缺哪条激励，也回不到单 case |
| 抖动当运气 | 「偶发，重跑过了」 | 非确定性是真 bug 的典型信号（竞态/未初始化），放过去后仿/硅上爆 |
| 用不同工具版本混跑再合并 | 机器上装了两个版本 | 库格式不认或行为不同，结果不可比 |
| 全 case 都 dump 波形 | 「万一要用」 | 磁盘爆、回归变慢，最后谁都不看 |

> **这套流水线的所有规矩，本质只有一条**：
> 一次回归是一份**可被独立重放**的实验记录 ——
> 输入（版本/开关/种子）齐全、过程（日志）完整、产物（覆盖率/波形）落地。
> 少任何一样，「同一个种子给同一个结果」就断了，后面依此做的签核也就没有根基。
