# SpyGlass：Lint / CDC / RDC 检查

> **一句话**：SpyGlass 报出来的东西，**百分之几才是真问题**取决于你**在它前面喂进去的约束**。
> 同步结构、时钟定义、复位策略没告诉工具，它就只能按最保守规则报一堆 —— 那堆里掺着大量**假违例**，
> 而把它们一条条 waiver 掉，比配置好工具本身还费时。**先把工具教会，再看报告。**

**这是验证翼的 CDC 卡 —— 只管「工具怎么报、报出来的怎么判读」。**
设计侧同步器该怎么写，是 `../../design/04_DFT_CDC_安全/CDC同步器处理.md`，不在这里重复。

## 干什么

| 族 | 检查什么 | 典型目标 |
|---|---|---|
| **Lint** | RTL 编码规范：可综合子集、位宽、敏感列表、未驱动/未使用、锁存器推断、隐式类型、命名 | RTL Freeze 前把明显错拦住；跨工具的编码一致性 |
| **CDC** | 跨时钟域信号：有没有同步器、同步器结构对不对、多比特是否原子、握手是否完整 | 挡住亚稳态（仿真抓不到，只能靠这套） |
| **RDC** | 跨复位域：复位有没有同步、复位域交叉、复位释放是否同步 | 挡住复位释放不一致导致的随机失效 |
| **其他** | 功耗（Power）、可测性（DFT）、结构分析 | 按需 |

**三族的「该认真看」清单完全不同** —— 用同一种眼光看三份报告，等于白跑。

## 常用命令

### 批处理

```bash
# 入口：读工程/配置，跑指定的 goal
spyglass -project my_proj.prj -goal lint/lint_rtl   -batch
spyglass -project my_proj.prj -goal cdc/cdc_setup   -batch
spyglass -project my_proj.prj -goal cdc/cdc_verify  -batch
spyglass -project my_proj.prj -goal rdc/rdc_setup   -batch

# 只跑增量（改了少量文件）
spyglass -project my_proj.prj -goal cdc/cdc_verify -batch -incremental
```

### 关键配置（这些没配好，违例数量根本不可信）

```tcl
# ── 读设计 ──
read_file -type verilog ./rtl/top.sv
read_file -type sourcelist ./filelist.f
read_file -type sgdc ./constraints/top.sgdc      # 约束文件，CDC/RDC 的核心

# ── 时钟定义（每一条都必须给，否则工具靠猜）──
current_design my_top
clock -name clk_core  -period 2 -edge {0 1}
clock -name clk_apb   -period 20 -edge {0 1}

# ── 复位定义 ──
reset -name rst_n -value 0

# ── 时钟关系：哪些时钟是异步的 ──
# 这句话决定了工具把哪些路径当跨域、报告里哪些违例该出
set_parameter -name cdc_async_clock_groups ...

# ── 同步结构识别：告诉工具「这个两级 FF 是同步器，别报」──
# 常见做法：命名约定 + 结构识别参数
set_parameter -name cdc_sync_style ...
```

### 报告

```bash
# 生成报告
spyglass -project my_proj.prj -goal cdc/cdc_verify -batch -report ./rpt/cdc.rpt

# 生成 waiver 文件模板（看哪条该 waiver 的时候用）
spyglass -project my_proj.prj -goal cdc/cdc_verify -waiver -batch
```

### 典型 SGDC 约束片段

```tcl
# 声明两个时钟异步
set_parameter -name cdc_async_clocks {clk_core clk_apb}

# 让工具识别一个已知的同步器结构（按命名）
set_parameter -name cdc_sync_ff_name_regexp {sync_*_ff}

# 指定复位同步器
set_parameter -name rdc_reset_sync_regexp {rst_sync_*}
```

## 什么该认真看 / 什么该 waiver

### Lint

| 该认真看 | 为什么 |
|---|---|
| **位宽不匹配** | 实际就是功能 bug（截断/扩展错误），且仿真不一定报 |
| **未驱动 / 未使用信号** | 未驱动 = 悬空输入；未使用 = 可能漏接 |
| **敏感列表不全 / 组合环路** | 仿真与综合不一致的源头 |
| **锁存器推断** | 非预期锁存器是综合后时序灾难 |
| **可综合子集之外** | 用 `initial`/延迟/系统任务写 RTL |

| 常见噪声，可 waive（带理由） | 为什么 |
|---|---|
| 风格类（命名、行宽、注释） | 与功能无关，团队规范决定 |
| 已验证的第三方 IP 内部 | 别在别人的 IP 上刷报告 |
| 综合工具明确忽略的编码变体 | 但要记录「确认过综合无差异」 |

### CDC / RDC —— 判读顺序（本卡核心）

**报出来一片违例时，不要按报告顺序一条条改。按下面的顺序，先分类再处理。**

```
第 1 步：先问「工具知道我的时钟/复位关系吗？」
  ├─ 时钟定义齐了吗？（少定义 = 工具把非跨域当跨域 → 大批假违例）
  ├─ 异步时钟组声明了吗？（没声明 = 工具按同步处理，反而漏报）
  └─ 复位定义/同步器命名给了吗？
  → 这一步没做，后面的所有数字都没意义

第 2 步：把违例分成三类
  ├─ ① 真问题：确实是跨域，且没有正确的同步结构
  ├─ ② 结构对但工具没认出：两级 FF 被工具当成普通逻辑
  └─ ③ 无意义：被工具误判为跨域的路径（如静态配置寄存器、常量、测试逻辑）

第 3 步：三类三种处理
  ├─ ① 改设计（去 design 侧那张卡看怎么做同步）
  ├─ ② 教工具（在约束里声明同步结构/命名），不是 waiver
  └─ ③ waiver（带理由：为什么这条路径不需要同步）
```

**判据一句话**：**同类违例大面积出现 → 先怀疑配置，不要怀疑设计。**
真问题通常是**零星、集中在某几个跨域信号**上的；配置没做对，才会**成片**报出来。

#### CDC 假违例的典型特征

| 现象 | 多半是 | 怎么确认 | 怎么办 |
|---|---|---|---|
| 同一个同步器第一级被报「缺少同步」 | 工具没认出这是同步器 | 看被报的信号是不是 `sync_*` 链条的第一级 | 在约束里声明同步结构/命名规则 |
| 整块报「跨时钟域」，但那块根本没有多时钟 | 时钟定义缺失或过宽 | 数一下工具认到的时钟列表对不对 | 补/修时钟定义 |
| 报的违例集中在**静态配置寄存器**上 | 配置寄存器只在复位后写一次，功能上不需要同步 | 确认该寄存器运行期不变 | waiver（带「运行期恒定」的理由） |
| 报的违例在**测试逻辑 / scan 路径**上 | 功能性路径，不在 CDC 关注范围 | 确认是 DFT/调试专用 | waiver（并说明是 DFT 逻辑） |
| 多比特总线被报「多位同时改变」 | **这可能是真问题**（逐位同步大忌） | 看接收侧是不是逐位同步的 | 改设计：格雷码/握手/FIFO |
| 握手信号被报「缺同步」 | 真问题（握手本身也是跨域信号） | 看请求/确认信号有没有各自的同步 | 改设计 |
| RDC 报「复位释放不同步」 | **基本是真问题** | 看释放路径有没有同步器 | 改设计（异步复位同步释放） |

#### 什么情况下 CDC 违例「不是真问题」

以下三类，**工具不理解你的意图**，属于可以 waiver 的（但都要带具体理由）：

- **静态常量 / 一次配置的寄存器**：复位后写完就不变，物理上不存在采样时刻竞争
- **伪路径**：功能上互斥、永远不同时使用的信号对
- **测试/DFT 专用信号**：只在测试模式下驱动，功能模式下不动

**注意**：这不是「难修的就 waive」。上面的三类有个共同点 —— **你能具体说明物理上为什么不会出问题**。
说不出来的，就是真问题。

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 不看时钟/复位定义就信报告数字 | 报告就在眼前 | 定义缺失时违例数量是噪声，改了半天改的是假的 |
| 按报告顺序一条条处理违例 | 「逐条清零最干净」 | 配置没修，处理完还会再生；且真正的问题被埋在噪声里 |
| 把「工具没认出同步器」当成 waiver | 「反正结构是对的」 | 下次改结构时约束还留着，同步器真没了也不报 —— **把真问题永久静音** |
| 大规模 waiver 让报告变绿 | 报告干净、进度好看 | waiver 变成「删掉问题」；CDC 的违例数量对签核失去意义 |
| CDC 只看「有几个违例」不看结构 | 数字最直观 | 数量为 0 也可能是同步器结构对但**约束过度**把真违例挡住了 |
| 拿仿真「跑通了」当 CDC 过的证据 | 仿真确实没报错 | 亚稳态在 RTL 仿真里**根本不建模**，跑通不构成任何 CDC 证据 |
| RDC 顺带 waive | 「复位应该没那么严重」 | 复位释放不同步是**概率性、难复现**的失效，比 CDC 更隐蔽 |
| 用 Lint 的「必须清零」标准要求 CDC | 报告零违例最省心 | CDC 天然有一批「合法的跨域」，全清零等于把约束配坏 |

> **最值钱的一条**：**CDC 报告的价值不在「违例数」，在你喂进去的约束里。**
> 约束写对，报告里剩下的违例才值得逐条判读；
> 约束没写，你看到的不是「设计的问题」，而是「工具对你不了解」。 ← 把这句话记住，比记住任何规则 ID 都有用。
