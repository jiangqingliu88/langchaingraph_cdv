# SDC 约束：怎么写全

> **一句话**：SDC 的作用是**告诉工具「真实的时序需求是什么」**。
> 写漏了，工具会按错误的默认去算（多半过度悲观）；写多了（滥用例外），
> 工具会**不检查本来就该检查的路径** —— 后者更危险，因为它让报告变好看。

## 适用场景

- 综合前要写或评审一份 SDC
- 报告里出现「这条路径根本不该被分析」或「这条路径怎么没约束」
- 时序违例收敛卡住，怀疑是约束问题（对应 KB-DV-SYN-001 第 2 步的类别 ①）

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 违例怎么分类、按什么顺序处理 | `时序收敛.md`（KB-DV-SYN-001） |
| 跨时钟域信号怎么同步（设计做法） | `../04_DFT_CDC_安全/CDC同步器处理.md`（KB-DV-DFT-001） |
| 测试模式（scan）下的时钟与例外 | `../04_DFT_CDC_安全/扫描链与DFT插入.md`（KB-DV-DFT-002） |
| 功耗/面积的约束 | 综合策略，不在 SDC 范围 |

## 五块约束，逐块写全

### 第 1 块：时钟定义

| 约束 | 用途 | 容易漏的点 |
|---|---|---|
| `create_clock` | 定义所有**源时钟**（含外部输入时钟、PLL 输入） | 别只定义主时钟，外部接口的时钟也要定义 |
| `create_generated_clock` | 定义**衍生时钟**（分频、倍频、门控后、MUX 后） | **最常漏的一块**：分频器的输出、门控时钟的输出都要定义，否则工具按源时钟分析 |
| `set_clock_uncertainty` | 抖动 + 裕量 | 分 setup / hold，别只设一个 |
| `set_clock_latency` | 时钟树延迟（综合阶段用估计值） | 综合时留裕量，CTS 后回填真实值 |
| `set_clock_transition` | 时钟边沿斜率 | 影响时序计算，别用默认 |

**生成时钟的判据**：问「这个时钟的边沿，与源时钟是**每个沿都对齐**的吗」。
不是（分频、门控、MUX 切换）→ 必须 `create_generated_clock` 显式定义。

### 第 2 块：I/O 延迟

| 约束 | 对象 | 怎么写 |
|---|---|---|
| `set_input_delay` | 输入端口 | 相对**哪个时钟**、多少 ns（外部器件到端口的延迟） |
| `set_output_delay` | 输出端口 | 同理，端口到外部器件的延迟 |
| `set_driving_cell` | 输入端口的驱动能力 | 不设则默认理想驱动，过于乐观 |
| `set_load` | 输出端口的负载 | 不设则默认空载，过于乐观 |

**判据来源**：I/O 延迟的值来自**接口协议 / 板级时序**，不是拍的。
虚设的 I/O 延迟会让接口时序在硅上直接不合格 —— 这是芯片级最常见的失败原因之一。

### 第 3 块：时钟组

| 约束 | 用途 |
|---|---|
| `set_clock_groups -asynchronous` | 声明两组时钟**异步**，它们之间不做时序分析 |
| `set_clock_groups -physically_exclusive` | 两组时钟**物理上不会同时存在**（如测试时钟与功能时钟） |
| `set_clock_groups -logically_exclusive` | 逻辑上互斥（如 MUX 的两个输入在同一时刻只有一个有效） |

**为什么必须显式设**：不设 `set_clock_groups`，工具会**默认所有时钟相关**，
对异步时钟做无意义的时序分析，报出成千上万条假违例，把真违例淹没。

> **注意**：`set_clock_groups -asynchronous` 与逐条 `set_false_path` 效果类似，
> 但**时钟组更不容易漏**（一次覆盖两组间所有路径）。同步器路径推荐的是
> `set_max_delay -datapath_only`（见 KB-DV-DFT-001），它保留数据路径延迟约束，
> 比纯 `false_path` 好 —— 别用时钟组把同步器第一级前的路径也一起免掉。

### 第 4 块：假路径（false path）

**除了异步跨域和物理不可能的路径，`set_false_path` 不应该出现。**

| 合法的 false path | 理由 |
|---|---|
| 异步时钟域之间 | 本来就不做时序保证，靠同步器保证正确性 |
| 配置寄存器 → 功能逻辑（静态配置，运行中不变） | 只在上电时写，不参与运行时时序 |
| 测试逻辑路径（在功能模式下不使用） | 见 KB-DV-DFT-002 |

**每一条例外都必须写理由**（注释或例外表）。**没有理由的 false path 是掩盖问题** ——
它让一条真实的时序违例从报告里消失，而问题还在硅上。

### 第 5 块：多周期路径（multicycle path）

| 约束 | 用于 |
|---|---|
| `set_multicycle_path N -setup` | 该路径有 N 个周期完成（放宽 setup） |
| `set_multicycle_path N-1 -hold` | **配套的 hold 设置** |

**最经典的坑**：只设 setup 不设 hold。默认 hold 检查会在**错误的边沿**做，
导致多出一条 hold 违例 —— 比不设还糟。

**判据**：多周期路径必须有**功能上的理由**（如「该路径由慢速使能控制，
只在每 N 个周期被采样一次」），并写进例外表。

## 例外表（必须维护）

每条例外一行，这是 SDC 可评审的前提：

| 约束 | 类型 | 路径/对象 | 理由 | 负责人 |
|---|---|---|---|---|
| `set_false_path` | 假路径 | `clk_a` → `clk_b` | 异步域，靠 2-FF 同步器 | 张三 |
| `set_multicycle_path 4 -setup` | 多周期 | `u_mul/*` | 慢速使能，4 周期一采 | 李四 |
| `set_clock_groups` | 时钟组 | `clk_func` / `clk_scan` | 物理互斥 | 王五 |

## 检查清单

| 检查项 | 问题 |
|---|---|
| 源时钟 | 所有时钟（含外部接口时钟）都有 `create_clock` 吗？ |
| 生成时钟 | 分频/门控/MUX 后的时钟都有 `create_generated_clock` 吗？ |
| 不确定性 | setup/hold 的 uncertainty 都设了吗？ |
| I/O | 每个端口的 input/output delay 都来自协议，不是拍的？ |
| 驱动/负载 | 驱动单元与负载设了吗？（不设过于乐观） |
| 时钟组 | 异步时钟组都设了 `set_clock_groups` 了吗？ |
| 例外理由 | 每条例外都能说出「功能上为什么」吗？ |
| 多周期配对 | 每个多周期 setup 都有配套 hold 吗？ |
| 例外表 | 例外表是最新的吗？与 SDC 一一对应吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 用 `set_false_path` 消违例 | 一条约束违例就没了，报告立刻好看 | 声明该路径不需时序保证，真实违例被藏起来 |
| 忘了生成时钟 | 「源时钟定义了就够了」 | 分频/门控时钟的输出按源时钟被分析，全面假违例或漏检 |
| 多周期只设 setup | 忘了还有 hold | 多出 hold 违例，且更隐蔽 |
| 不设 `set_clock_groups` | 「同步器都写了，不用再声明」 | 异步域被逐个做时序分析，几千条假违例淹没真问题 |
| I/O delay 拍脑袋 | 「先设 0 跑通再说」 | 接口时序在硅上不合格，返工代价极高 |
| 存在多个 SDC 版本，不合并 | 各模块各写一份 | 例外互相冲突，谁生效说不清 |
| 例外不带理由 | 「反正不会有人问」 | 下次没人敢删，例外只增不减，逐步失去约束作用 |

> **一句判断**：审 SDC 时，**先数例外条款，再问每条的出处**。
> 例外越多、出处越模糊，这份约束越不可信 —— 它多半在用例外掩盖真实的时序问题。
