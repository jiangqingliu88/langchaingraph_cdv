# 微架构分解与接口定义

> **一句话**：模块边界不是「代码写起来方便的地方」，是**时钟域边界、数据流边界、复用边界**。
> 划错了，时序会在综合时爆、验证会在集成时爆、复用会在下个项目爆 —— 三者代价都远高于一次想清楚。

## 适用场景

- 拿到功能规格（文字 / 框图 / 算法描述），要出微架构
- 现有划分让时序或验证很难做，怀疑边界划错了
- 想把一块逻辑做成可复用 IP，需要定「切到哪一层为止」

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 模块切好了，检查 RTL 编码质量 | `可综合RTL编码清单.md`（KB-DV-RTL-001） |
| 跨时钟域信号怎么同步 | `../04_DFT_CDC_安全/CDC同步器处理.md`（KB-DV-DFT-001） |
| 接口协议的时序合法性 | 协议域（`verify/05_协议与VIP/`） |
| 综合后时序违例怎么收 | `../02_综合_时序_PPA/时序收敛.md`（KB-DV-SYN-001） |

## 步骤

### 第 1 步：先定切分判据，再画框图

**按顺序用四条判据扫一遍**，先满足的优先切：

| 判据 | 切在哪 | 为什么 |
|---|---|---|
| **① 时钟域** | 跨时钟域处必须切 | 同步器要放在**明确的一侧**，混在一个模块里无法约束、无法做 CDC 检查 |
| **② 数据流** | 生产与消费速率不一致处 | 速率不匹配要用 FIFO / 握手隔离，边界即缓冲 |
| **③ 复位域** | 复位策略不同处必须切 | 一个模块两套复位释放策略会出微观竞态 |
| **④ 复用** | 需要被多处实例化处 | 复用的粒度决定参数化接口，越早定越省事 |

**判据顺序不能乱**：时钟域和复位域是**物理约束**，数据流是**性能约束**，
复用是**工程约束**。前一类的约束是硬的，后一类可以让步。

### 第 2 步：定接口握手约定

**先决定这个接口是哪种握手，它决定两侧的状态机写法**：

| 约定 | 语义 | 什么时候用 |
|---|---|---|
| **valid/ready** | 数据 + 双向流控，双方都可反压 | 数据流密集、需要吞吐与反压 |
| **req/ack** | 请求 + 确认，一次一事务 | 控制路径、事务语义清晰 |
| **脉冲 + 状态** | 单周期脉冲触发，无握手 | 低延迟、无背压需求的简单控制 |
| **共享状态（不握手）** | 一方写寄存器，另一方读 | 配置寄存器，跨域时必须同步 |

**valid/ready 的硬约定（不遵守就是错的）**：

- 源侧：`valid` 拉高后，**数据必须保持到 `ready` 拉高**才允许变 —— 这是本卡最常被破坏的一条
- 源侧：`valid` 一旦拉高，**不许撤回**（除非复位）
- 宿侧：`ready` 不许依赖 `valid`（否则组合环）
- 传输发生在 **`valid && ready` 同时为高的那个周期**

> `valid` 依赖 `ready`、或数据在等 `ready` 期间变化，是集成阶段最常见的一类 bug，
> 而且是**间歇性**的 —— 单模块验证全绿，一集成换时序就炸。

### 第 3 步：定接口的方向与命名

- 每个端口在模块接口表里写清：**方向 / 位宽 / 时钟域 / 复位域 / 有效语义**
- 命名能读出方向和域（`*_i` / `*_o`、`*_clk` 前缀）—— 见 KB-DV-RTL-001 的命名要求
- 跨模块的组合路径**默认不允许**；确实要穿透的，在接口表里显式标注（否则时序约束必漏）

### 第 4 步：判断「什么时候不该拆」

**拆分不是免费的**。以下情况**反而不要拆**：

| 不要拆的情况 | 理由 |
|---|---|
| 两个功能**总是同时使用**、从不同时独立 | 拆了要加一层握手，时序更差，验证更碎 |
| 拆开处是**组合逻辑中间点** | 制造了跨模块组合路径，时序约束的噩梦 |
| 拆开后子模块**只有一个使用者**且无复用计划 | 多一层层次只增加 reader 的理解成本 |
| 拆分会把**一个状态机劈成两半** | 状态编码跨模块传递，验证和形式都变难 |

**判据**：如果拆分带来的唯一好处是「文件短一点」，就不要拆。
模块层次是给**时序、验证、复用**服务的，不是给代码美观服务的。

### 第 5 步：产出接口表（交给下游）

| 端口 | 方向 | 位宽 | 时钟域 | 复位域 | 有效语义 | 备注 |
|---|---|---|---|---|---|---|
| `req_valid_i` | in | 1 | `clk_core` | `rst_core_n` | 高有效 | 拉高后保持到 ack |
| `req_data_i` | in | 64 | `clk_core` | — | — | 与 valid 同步 |
| `resp_ready_o` | out | 1 | `clk_core` | `rst_core_n` | 高有效 | 不依赖 valid |

**这张表是验证侧写 coverage 和 driver 的输入**，也是时序约束（SDC）的输入 ——
接口表里标注的时钟域，直接决定 `set_clock_groups` 与 I/O delay 怎么写。

## 检查清单

| 检查项 | 问题 |
|---|---|
| 时钟域 | 每个跨时钟域处都是一个模块边界吗？ |
| 复位域 | 有没有一个模块里混了两套复位释放策略？ |
| 握手 | 每个接口的握手类型明确了吗？（valid/ready 还是 req/ack） |
| valid 保持 | `valid` 拉高后数据保持到 `ready` 这条约定，接口表里写了吗？ |
| ready 依赖 | 宿侧 `ready` 有没有依赖 `valid`（组合环）？ |
| 组合穿透 | 有没有跨模块组合路径？在接口表里标注了吗？ |
| 复用 | 声称可复用的模块，接口是否已参数化、无硬编码？ |
| 不拆判断 | 每个拆分都过了一遍「不该拆」的四条吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 按「代码行数均衡」切模块 | 看起来两个模块一样重，很「公平」 | 切开处落在组合逻辑中间，制造跨模块组合路径，时序必爆 |
| 把一个 FSM 劈成两个模块 | 各管一半，看着清晰 | 状态跨模块传递，验证要同时驱动两个，形式几乎无法证明 |
| `valid` 拉高后数据可变 | 「反正 ready 还没来」 | 宿侧采到旧值/中间值，集成后间歇性错，单模块验证抓不到 |
| `ready` 依赖 `valid` | 简化握手逻辑 | 组合环，综合报环或时序无法分析 |
| 拆分只为了复用「可能将来有用」 | 提前抽象显得有远见 | 参数化接口成本高，实际没人复用，白付成本 |
| 接口不标时钟域 | 「一看就知道」 | 下游写 SDC 时漏掉跨域，时序约束静默缺失 |
| 跨模块组合穿透不标注 | 省一拍延迟，看起来更快 | 约束漏掉，时序分析看不见这条路径（同 KB-DV-RTL-001 的坑） |

> **一条经验**：微架构评审时，**先看接口表，再看框图**。接口表里握手指令不清、
> 时钟域没标的，框图一定也划不清 —— 因为边界问题本质都从接口上暴露。
