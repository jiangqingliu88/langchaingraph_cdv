# 可综合 RTL 编码清单

> **一句话**：这份清单里**没有一条是关于「写得好不好看」的** ——
> 每条都对应一个「综合器会做出你不想要的东西」或「验证会看不见你埋的雷」的具体后果。

## 适用场景

- 一段 RTL 写完了，交出去之前自己过一遍
- 评审别人的 RTL
- 事后复盘：为什么这段 RTL 到了后端才炸

## 不适用

| 你实际想干的事 | 该去哪 |
|---|---|
| 违例收不收敛 | `../02_综合_时序_PPA/` |
| CDC 怎么同步 | `../04_DFT_CDC_安全/` |
| 这段 RTL 的行为对不对 | `verify/`（那是验证要回答的，不是本条清单能答的） |

## 步骤

### 第 1 步：可综合性红线（四条，任一不过就别往下走）

| 红线 | 表现 | 后果 |
|---|---|---|
| **无 latch 推断** | `always_comb`/`always @(*)` 里条件不完整 | 综合器补一个 latch，仿真时看不出来，时序分析时多一条你没写过的路径 |
| **无组合环** | 组合逻辑输出经路径绕回自己的输入 | 综合报环；若不报，仿真会随工具挂死 |
| **无不定态传播** | 复位后未初始化就参与运算 | X 传播到输出，验证报一堆假错，真正的问题被埋掉 |
| **无异步逻辑**（除同步器） | 用 `always @(a or b)` 做功能逻辑 | 无法做时序分析，等于放弃时序 |

**为什么单列成红线**：这四条的共同点是**仿真能过**。它们不产生功能错误，
产生的是「后端或硅上才出现」的错误 —— 代价高一个数量级。

### 第 2 步：时钟与复位策略

- **每个寄存器只属于一个时钟域**，跨域只经同步器（见 `../04_DFT_CDC_安全/`）
- **异步复位、同步释放**（默认策略）—— 异步释放在不同触发器上可能差一个周期
- 复位作用域写清楚：哪些寄存器被哪个复位控制，同一个复位域内不要混
- **不要用复位初始化数据通路寄存器** —— 复位树扇出会爆，数据通路复位靠有效信号

### 第 3 步：「组合还是时序」的判据

一段逻辑该放组合还是打一拍，判据不是习惯，是**它到下一级寄存器的路径能否满足时钟周期**：

| 情况 | 放哪 |
|---|---|
| 纯译码、简单选择 | 组合 |
| 算术运算且处于关键路径 | 打拍（流水线） |
| 需要跨模块组合穿透 | **不打拍，但必须记进时序约束** —— 这是最容易被漏的一类 |

### 第 4 步：层次与命名

- 模块边界**对齐微架构的功能边界**，不要对齐「代码写起来方便」
- 信号命名能读出**方向与域**：`*_i` / `*_o`、`*_clk` 前缀区分时钟域
- 参数（`parameter`/`localparam`）而不是魔数；宽度相关的量一律从参数推

### 第 5 步：参数化与复用

- 位宽、深度这类只在**编译期知道**的量走 `parameter`
- **不要在参数化模块里写依赖具体位宽的魔数** —— 换位宽时静默错

## 检查清单

| 检查项 | 问题 |
|---|---|
| latch | 每个 `always` 块的每个分支都赋值了吗？ |
| 复位 | 复位释放是同步的吗？复位域划分清楚了吗？ |
| 时钟域 | 每个寄存器都明确属于某一个时钟域吗？ |
| 组合穿透 | 有没有跨模块的组合路径没记进约束？ |
| 宽度 | 所有赋值两边位宽一致吗？截断是有意的吗？ |
| 默认分支 | `case` 有 `default` 吗？（无 `default` 的 `case` 是 latch 和 X 的温床） |
| 参数 | 有没有该参数化的魔数？ |
| 命名 | 只看信号名能判断方向和时钟域吗？ |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| `case` 不加 `default` | 少写一行，且「枚举已穷举」听着合理 | 未覆盖值推 latch 或 X |
| 用 `initial` 给寄存器赋初值 | 仿真能跑通，省掉复位逻辑 | 综合忽略，硅上未初始化 |
| 复位所有数据通路寄存器 | 「复位了就干净了」 | 复位树扇出爆，时序过不去 |
| 跨模块组合穿透 | 省一拍延迟，看起来更快 | 约束漏掉，时序分析看不见这条路径 |
| 位宽不一致静默截断 | 工具只给 warning | 高位静默丢弃，仿真与综合一致但都是错的 |
