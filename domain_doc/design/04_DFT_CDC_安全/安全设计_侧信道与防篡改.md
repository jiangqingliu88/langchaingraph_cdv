# 安全设计：侧信道与防篡改

> **一句话**：安全设计的对手是**有智能、有物理接触、能反复测量**的攻击者。
> 它关心的不是「芯片会不会坏」，而是「**芯片会不会被利用**」—— 这与功能安全的目标正好相反。

## 定义

**硬件安全设计**：让隐藏在芯片里的秘密（密钥、认证凭据、随机数状态）**不能通过
物理或旁路手段被推导出来**，同时让攻击者**无法篡改芯片的正常运行**使其进入有利状态。

它防御两类威胁：

| 威胁 | 攻击者做什么 | 设计要防的是 |
|---|---|---|
| **侧信道（Side-Channel）** | 不破解算法，而是**测量物理量**（执行时间、功耗、电磁辐射）反推密钥 | 泄露与秘密相关的物理特征 |
| **故障注入（Fault Injection）** | 用**电压/时钟毛刺、激光、温度**故意制造错误 | 错误导致的安全绕过（跳过校验、走错分支） |

## 边界（不是什么）

| 它**不是** | 归属 |
|---|---|
| 防失效（芯片会不会坏） | **功能安全**，ISO 26262 —— 目标相反，见下 |
| 加密算法的数学强度 | 算法本身；本卡管的是**实现**怎么不泄露 |
| 纯软件安全（栈溢出、权限） | 软件安全 |
| 抗攻击的合规评级 | 标准合规域 |

**关键区分**：**功能安全要的是「不失效」，信息安全要的是「不被利用」。**
一个安全芯片可以既是功能安全的、又是信息安全的，但两者的手段常常**互相冲突**。

## 两类威胁与设计手法

### 一类：侧信道

| 侧信道 | 攻击者测什么 | 设计手法 |
|---|---|---|
| **时序侧信道** | 执行时间随密钥数据变化 | **恒时设计（constant-time）**：执行路径与周期数不依赖秘密 |
| **功耗侧信道** | 每个周期的功耗痕迹与运算数据相关 | **掩码（masking）**：把秘密拆成随机份额，单点功耗与秘密无关 |
| **功耗侧信道** | 上述 | **隐藏（hiding）**：随机插入操作 / 双轨逻辑，打乱功耗时间分布 |
| **电磁侧信道** | 电磁辐射 | 同功耗手法（本质是功耗的另一种观测） |

**恒时设计的难点**：分支和提前退出是最常见的时序泄露源。
「密钥对就早返回、错就晚返回」—— 这个差别直接泄露信息。
所以安全比较要用**恒时比较**（全字节无分支比较），不能用 `memcmp` 之类会提前退出的实现。

**掩码的代价**：面积、功耗、随机数消耗都显著上升。**不是所有安全模块都要做掩码** ——
按威胁模型决定（攻击者是否有物理接触、能否多次测量）。

### 二类：故障注入

| 攻击 | 攻击者做什么 | 设计手法 |
|---|---|---|
| **故障注入** | 电压/时钟毛刺让某级寄存器出错 | **冗余校验**：关键状态/结果算两遍（或编码冗余），不一致就报错 |
| **故障注入** | 激光/电磁翻转某几位 | **错误检测码 / 双轨逻辑**：让单点翻转可被发现 |
| **故障注入** | 制造错误跳过校验分支 | **条件分支加固**：分支判定用冗余（避免单点翻转翻转判定结果） |
| **故障注入** | 制造错误绕过复位/看门狗 | **传感器**：电压、时钟、温度、光照传感器，异常即触发保护 |
| **故障注入** | 让状态机进入非法态 | **状态编码加固**：非法态能被检测并强制回到安全态 |

**传感器是最后一道**：它不能阻止故障注入，只能**检测到异常并触发保护动作**
（擦除密钥、复位、锁死）。所以传感器本身也要防「被一起干掉」。

### 设计侧 checklist（手法层）

| 项 | 检查 |
|---|---|
| 恒时 | 所有依赖秘密的路径，执行时间与周期数一致吗？ |
| 比较 | 密钥比较是恒时的吗（无提前退出）？ |
| 掩码 | 需要掩码的地方做了吗？随机数质量够吗？ |
| 冗余 | 关键校验/状态有无单点故障点？ |
| 分支 | 安全判定的分支能不能被单点翻转改变？ |
| 传感器 | 有哪些传感器？检测到异常的动作是什么？ |
| 降级 | 检测到攻击后，密钥/状态能否安全擦除或锁死？ |

## 与功能安全（ISO 26262）的区别

**两者目标相反，混用会出事。**

| 维度 | 信息安全（本卡） | 功能安全（ISO 26262） |
|---|---|---|
| 防的是什么 | **恶意**攻击者 | **随机**失效、系统性失效 |
| 对手 | 有智能、会适应 | 无意志（物理随机） |
| 典型手法 | 恒时、掩码、防篡改传感器 | 冗余、安全机制、故障树分析 |
| 冗余的用法 | 防**刻意**注入的单点故障 | 防**随机**单点失效 |
| 度量 | 抗攻击强度（多少次测量内不泄露） | ASIL 等级、SPFM / LFM 指标 |
| 冲突点 | 掩码增加面积功耗 → 可能**拉低**功能安全的时序裕量 | 要求低复杂度、可分析 |

**为什么说目标相反**：功能安全希望系统**行为可预测、可分析**；
信息安全希望**行为对攻击者不可预测**。同一块逻辑，一个要「越规整越好」，
一个要「越不可猜越好」—— 所以**两套要求要分开评审，不要一张表打勾**。

> **判据**：如果你的芯片既要过 ISO 26262 又要防攻击（如车规安全芯片），
> **分别建两张需求表**，在「冗余」「传感器」这类交叉点上显式评审冲突，
> 而不是把两套要求混成一张 checklist。

## 容易搞混的概念

| 概念 | 与本卡的关系 |
|---|---|
| **PUF**（物理不可克隆函数） | 一种**密钥来源**机制（利用工艺变化生成唯一密钥），不是防侧信道手段 |
| **TRNG**（真随机数） | 掩码的随机数来源；质量不够会直接削弱掩码强度 |
| **安全启动** | 系统的信任根；靠签名验证，属于系统层，本卡管底下的硬件基元 |
| **DFT / scan** | **是安全的一个泄露面** —— scan 能让内部状态被移出，安全芯片常要限制 debug 口访问 |

> **最后一条要注意**：**DFT 的扫描链本身可能成为攻击入口**（攻击者通过 debug 口
> 移出内部状态，或控制内部状态）。安全设计里，**调试/测试通路必须受保护** ——
> 生产后关断、或用密钥认证后才能开启。这属于「设计面 + 安全需求」的交叉点。
