# IEEE 语言标准

> **一句话**：这份文档不是「学 SystemVerilog 的教材」，是「六个标准号各自圈了哪块地」的
> 地图 —— 读懂它的用处是：语法被工具拒的时候，能判断是**我写错了**还是**工具版本不够**。

## 定义

IEEE 语言标准是一系列**规范性文件**，规定特定设计/验证语言的语法、语义、
预处理方式与标准库行为。它们是**语言的定义**，不是工具的实现 —— 仿真器/综合工具
可以只实现标准的一个子集，也可以在某版标准之外再提供私有扩展。

| 标准号 | 名字 | 管什么 |
|---|---|---|
| **IEEE 1364** | Verilog HDL | Verilog 语法与语义。1364-1995 是原始版；1364-2001 加了 generate / 多维数组；1364-2005 加了 `uwire` 等。**已被 1800 吸收**，不再单独演进 |
| **IEEE 1800** | SystemVerilog | 1364 + 1800 的合并与扩展：`logic`、`always_ff/comb/latch`、struct/union/enum、interface、类、随机约束、断言、覆盖率、program/clocking block。**验证语言的主战场** |
| **IEEE 1800.2** | UVM | 把 UVM 类库**标准化**：`uvm_component`、`uvm_sequence`、factory、config_db、phase、report 等的**标准类名与方法签名**。注意：它规定的是**库的接口**，不是某家 vendor 的实现 |
| **IEEE 1076** | VHDL | VHDL 语言本体（1987/1993/2000/2008/2019 等修订）。与 Verilog 平行的另一条设计语言线 |
| **IEEE 1801** | UPF | 低功耗**意图**的表达：电源域、电源开关、隔离、电平转换、保持、电源状态表。描述「功耗结构长什么样」 |
| **IEEE 1850** | PSL | Property Specification Language：属性/断言的语言（与 SVA 平行的一条断言语言线，形式工具里常见） |

> 表里故意**不写版本号到具体年份之外**：每个标准的修订年份和新增特性以标准正文为准，
> 本卡只固定「它管哪块地」这件事。要引某个特性的确切引入版本，查标准前言的 revision history。

## 边界（不是什么）

| 它**是** | 它**不是** |
|---|---|
| 语言语法/语义的**规范定义** | 某家工具（VCS / Xcelium / Questa / Verilator）的**实现与开关** |
| 一个可以引用的**版本基线** | 「最新版就是我要用的版」——工具支持度才是约束 |
| 关于**语言能表达什么** | 关于**方法学该怎么组织**（UVM 方法学 ≠ 1800.2 库） |
| UPF 里**功耗意图怎么写** | 电源域**该怎么划分**（那是设计决策，→ `design/03_低功耗与UPF/`） |

**最关键的一条边界**：标准规定「这样一个程序在语义上做什么」，
不规定「你要装上哪个 license、加哪个编译选项才跑得动」。后者是工具的问题。

## 为什么要关心版本

这是这张卡真正想说的：**语法可用性 = min(你写的写法, 工具支持的上限)**。

| 现象 | 真正的原因 | 该怎么查 |
|---|---|---|
| `always_comb` 报错、被当普通 always | 工具按 Verilog 模式编译 | 查工具的 `-sv` / `-sv09` / `-sv12` 开关与默认语言模式 |
| 约束里某个分布写法不被接受 | 工具只实现 1800 的旧修订 | 查工具 release note 里「支持到 1800-XXXX」的声明 |
| `uvm_component` 方法签名对不上书上的例子 | 1800.2 版本与工具自带 UVM 库版本不一致 | 查工具内置 UVM 库的版本号和它对应哪版 1800.2 |
| UPF 某条命令被拒 | 支持 1801 的版本不同（1.0 / 2.0 / 2.1 / 3.0） | 查工具 UPF 命令支持矩阵 |
| 形式工具不认某条 SVA | SVA 支持是工具子集，不一定是语言问题 | 查形式工具的 SVA 支持清单 |

**实务结论**：
- 项目开始就**写死语言基线**（例如「SystemVerilog per IEEE 1800-2017」「UVM per IEEE 1800.2-2020」），
  写进验证计划，别等到交接时才发现两边版本不同。
- 遇到语法被拒，**先在工具文档里确认支持版本**，再去改代码 —— 反过来会白改。
- 「标准里有」≠「工具支持」；「工具支持」≠「你的项目允许用」。

## 与其他易混概念的区别

| 易混对 | 区别 |
|---|---|
| **IEEE 1800 vs 1800.2** | 1800 是**语言**（你能写什么语法）；1800.2 是**库**（UVM 的类与方法签名）。两者常被笼统叫「SystemVerilog/UVM 标准」 |
| **1800 vs 1364** | 1800 **包含** 1364（Verilog 是 SystemVerilog 的子集）；写纯 Verilog 也可以用 1800 编译器编 |
| **1800.2 vs UVM 方法学** | 1800.2 标准化的是**类库接口**；「sequence 驱动、phase 执行顺序、factory override 的用法」是**方法学**（→ `verify/02_验证方法学/UVM/`） |
| **IEEE 1801 (UPF) vs UPF 供给格式** | 1801 是语言与语义；工具间交换用的 UPF 文件具体方言可能带 vendor 扩展 |
| **IEEE 1850 (PSL) vs SVA** | 两条并行的断言语言线。SVA 在 1800 里，PSL 在 1850 里；形式工具常同时支持，综合/仿真里的偏好不同 |
| **语言标准 vs 功能安全标准** | 1800/1364 说「代码怎么写」；ISO 26262 / DO-254（见 `KB-DV-STD-002` / `KB-DV-STD-003`）说「过程与证据要怎样」 |

## 六个标准的分工一览

把六个标准按「它在地图上的位置」排一遍，比逐个背定义有用：

| 标准 | 管设计侧还是验证侧 | 一句话定位 |
|---|---|---|
| **1364** | 设计为主 | 老 Verilog 的母语；今天几乎只在「工具只认 Verilog 模式」时才单独被提起 |
| **1800** | 两侧都要 | 设计能写接口/枚举/断言，验证能写类/约束/覆盖率 —— **一份标准养两翼** |
| **1800.2** | 验证 | UVM 的「类名与方法签名」字典；不是方法学教材 |
| **1076** | 设计为主 | VHDL 线；在部分高可靠/航空项目里仍是主力语言 |
| **1801** | 设计（低功耗）+ 验证（低功耗相关） | 把「电源域 / 隔离 / 保持」的**意图**写成可被工具读的格式 |
| **1850** | 验证（形式/断言） | PSL 断言语言；与 SVA 平行，形式工具圈更常见 |

**两条语言线**：Verilog/SystemVerilog（1364 → 1800）与 VHDL（1076）。
选哪条通常是**团队/项目历史**决定的，不是技术优劣 —— 但**版本**这件事两条线都躲不掉。

**两条断言线**：SVA（在 1800 内）与 PSL（1850）。写断言前先确认目标工具认哪条、
认到什么程度；形式工具对两者的支持深度往往不同。

## 工具版本怎么影响你能写的语法

举几个「同一个写法，换个工具版本就翻脸」的典型，帮助建立判断直觉
（**不写具体版本号年份 —— 那要查工具 release note**）：

| 写法类别 | 版本敏感点 |
|---|---|
| `always_comb / always_ff / always_latch` | 需要编译器处于 SV 模式；纯 Verilog 模式下未定义 |
| 类 / 随机约束 `/` 覆盖率 | SV 的强项，Verilog 模式基本不可用 |
| interface / modport | 同上；老工具可能只部分支持 |
| 断言（SVA）在综合流程里 | 综合工具对 SVA 的支持是**子集**，且综合与仿真语义有差异 |
| UVM 库 API | 受工具内置 UVM 库版本影响，不一定等于你要的 1800.2 修订 |
| UPF 命令 | 支持 1801 的修订不同，命令集与开关都不同 |

**判断顺序**（遇到语法报错时照这个走）：

1. 确认工具当前编译模式（Verilog 还是 SV，哪一版）—— 这是最常见的元凶。
2. 查工具文档里的**语言支持矩阵**，看这个特性支不支持。
3. 支持的前提下，再回头怀疑自己的写法。
4. 都不通，再考虑换写法或换工具版本 —— 但换版本要评估全项目的兼容性。

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 把「书上的写法」当语言标准 | 教材例子随手可抄 | 书可能基于新版语法，工具版本不到 → 报错还以为是笔误 |
| 默认工具支持最新标准 | 装的工具是新的 | 编译器**默认语言模式**常常不是最新 SV；要显式开 |
| 把 UVM 方法学当成 1800.2 标准 | 两者都叫「UVM 标准」 | 拿标准号去解释「该不该用 virtual sequence」—— 标准不管这个 |
| 交接时不约定语言基线 | 「反正都是 SystemVerilog」 | 一方用 1800-2017 语法，另一方工具只到 1800-2012，收编时集体报错 |
| 语法被拒就改代码 | 「肯定是写错了」 | 可能是工具版本问题；改完在另一台机器上又不对 |
| 以为「标准里有 = 可综合」 | 1800 里什么都有 | 仿真语法和可综合子集是两回事，综合工具只吃子集 |

## 出处

- **IEEE 1800**（SystemVerilog 语言）
- **IEEE 1800.2**（UVM 标准类库）
- **IEEE 1364**（Verilog HDL，已并入 1800）
- **IEEE 1076**（VHDL）
- **IEEE 1801**（UPF 低功耗意图）
- **IEEE 1850**（PSL 属性规范语言）

> 具体条款、修订年份与新增特性请查各标准的正文与前言；
> 工具实际支持到哪一版，查**工具自己的 release note / 用户指南的语言支持章节**（→ `verify/04_工具与脚本/`）。
