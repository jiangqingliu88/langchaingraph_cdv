# ISO/SAE 21434 汽车信息安全

> **一句话**：ISO/SAE 21434 防的是**有人故意搞你**（攻击），
> ISO 26262 防的是**东西自己坏**（失效）。两条线并行，接口处要对接。

## 定义

ISO/SAE 21434 是**道路车辆网络安全工程**国际标准（与 SAE 联合发布）。
它规定车辆电子电气系统在**全生命周期**内的网络安全工程要求：
从概念阶段的威胁分析，到开发、生产、运行、维护、直到报废的**网络安全活动与证据**。

它不规定「用哪种加密算法」，规定的是**过程与方法**：
你要**系统地找出威胁、评估风险、给出对策、并把这一切留下证据**。

三个支柱：

| 支柱 | 含义 |
|---|---|
| **网络安全生命周期** | 从概念到退役，每阶段有网络安全活动与工作产物 |
| **TARA** | 威胁分析与风险评估 —— 找出资产、威胁、攻击路径，评风险，定对策 |
| **网络安全目标与需求** | 由 TARA 导出，向下传导到软硬件设计，并被验证覆盖 |

## 三个关键点

### 1. 网络安全生命周期

| 阶段（语义） | 谁做 | 关键产物（语义） |
|---|---|---|
| 概念 | 系统 + 安全 | 资产识别、TARA、网络安全目标、网络安全概念 |
| 产品开发 | 设计 + 验证 | 网络安全需求、架构与实现对策、验证证据 |
| 生产 | 制造 | 生产阶段的安全控制（如刷写、密钥注入） |
| 运行与维护 | 运营 | 监控、漏洞/事件响应、更新机制 |
| 报废 | 运营 | 数据与密钥的安全清除 |

**核心要求**：威胁 → 目标 → 需求 → 实现 → 验证，可追溯；
且运行阶段要有**持续监控与响应**（漏洞是会随时间出现的，不是一次分析就完）。

### 2. TARA（威胁分析与风险评估）

TARA 是这张卡最核心的方法概念。它的目的：**把「可能被怎样攻击、后果多严重、
值不值得防」变成可排序的清单**。

| 步骤（语义） | 做什么 |
|---|---|
| 资产识别 | 找出有价值的资产（密钥、控制指令、固件、隐私数据） |
| 威胁场景 | 对每个资产列出可能被怎样攻击 |
| 影响评估 | 攻击成功会造成什么（安全、财务、隐私、操作性） |
| 攻击路径分析 | 攻击者可能的入口与路径 |
| 攻击可行性评估 | 综合攻击者的资源、时间、能力等维度，评估可行性 |
| 风险值确定 | 影响 × 可行性，得到风险等级 |
| 风险处置 | 每条风险决定：规避 / 缓解 / 分担 / 接受，并导出网络安全目标与需求 |

> **不要凭记忆写攻击可行性的具体维度与打分表**：它在标准正文的威胁分析部分有正式定义，
> 且业界有大量不同解读。本卡只保留「有这几步、每步产出什么」。
> 反过来，**你做的对策（如安全启动、认证、加密）不是标准规定的** —— 标准管评估与过程。

### 3. 对设计与验证的要求（追溯到「标准要求什么」）

| 要求 | 语义 |
|---|---|
| **需求追溯** | 网络安全目标 → 需求 → 实现 → 验证结果，可追溯 |
| **对策落地要可验证** | 「我们加了认证」不够，要有能证明它生效的验证证据 |
| **接口要与功能安全对齐** | 一个机制可能同时服务「防攻击」和「防失效」，要双方都认账 |
| **供应链** | 第三方 IP/软件也纳入网络安全要求，不能只要求自家代码 |
| **持续监控** | 运行阶段要能发现新威胁并响应，不是出厂即完 |

## 边界（不是什么）

| 它**是** | 它**不是** |
|---|---|
| 车辆**网络安全**的**过程**标准 | 某个密码算法/协议的**技术规范**（那在别的标准里） |
| 要求你**做 TARA 并留证据** | 一份现成的威胁库或攻击用例集 |
| 覆盖产品**全生命周期** | 只管设计阶段 —— 运行/维护是硬要求 |
| 与 ISO 26262 **并行**的一条线 | ISO 26262 的**子章节**，也不能替代 26262 |

**最关键的边界**：本卡回答「网络安全标准要求什么」，
**不回答**「你要设计什么安保机制」（→ `design/`）与「你怎么验证它有效」（→ `verify/`）。

## 与 ISO 26262 的区别与交叉

这是这张卡真正要讲清的部分 —— 两个标准经常被混成一件事。

| 维度 | ISO 26262（功能安全） | ISO/SAE 21434（信息安全） |
|---|---|---|
| 防的是什么 | **失效**：随机/系统性故障导致危害 | **攻击**：恶意的、有意图的行为 |
| 触发者 | 无意图（器件老化、设计缺陷、干扰） | **有意图的攻击者** |
| 核心分析 | HARA（危害分析与风险评估） | **TARA**（威胁分析与风险评估） |
| 分级术语 | **ASIL** | 网络安全风险等级（不叫 ASIL） |
| 要不要考虑「人」 | 可控性指驾驶员/乘员能否处置 | 攻击可行性指攻击者的能力与代价 |
| 时间维度 | 失效概率随寿命变化 | 威胁随时间**演化**（新漏洞不断出现），需持续监控 |

**交叉（必须对齐的接口）**：

| 交叉点 | 说明 |
|---|---|
| 同一机制双责 | 一条保护（如校验、冗余）可能同时是「失效对策」和「攻击对策」，两边证据要能互为支撑 |
| 攻击导致失效 | 攻击成功可能**引发**功能安全危害 —— 这类失效在 26262 里也要分析 |
| 安全与安保冲突 | 可用性与安全性可能打架（例如为防攻击而限制功能），需要在两个标准间权衡并记录 |
| 证据可复用 | 追溯矩阵、独立性论证、工具评估等过程性证据，两个标准有形式相似处，但**不能直接互套**，各自要对上自己的条款 |

> 一句话记法：**26262 问「它会不会自己坏」，21434 问「有没有人来弄坏它」。**

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 把网络安全当功能安全做 | 两个都在汽车里、都叫「安全」 | 用 ASIL 那套去解释攻击风险，TARA 缺位，评审直接不通过 |
| 拿「加了加密」当合规 | 技术手段看起来到位 | 标准要的是**TARA 导出需求 → 验证证据**的过程，不是技术清单 |
| TARA 只做一次 | 「分析完了」 | 威胁随时间演化，运行阶段要持续监控与响应 |
| 忽略供应链 | 「我们只负责自家 IP」 | 第三方 IP/固件的漏洞同样算在整车风险里 |
| 追溯断链 | 「对策文档里有就行」 | 要能逐条从威胁追到验证结果，两者都要挂得上 |
| 与功能安全各写各的 | 两个团队各做一套 | 交叉机制两边证据对不上，接口处出风险 |
| 凭记忆写攻击可行性打分表 | 想显得专业 | **本卡最忌讳的错**：标准内容写错比留白更糟 —— 一律查标准正文 |
