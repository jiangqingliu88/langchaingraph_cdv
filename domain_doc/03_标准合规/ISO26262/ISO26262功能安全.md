# ISO 26262 功能安全

> **一句话**：ISO 26262 不是教你怎么设计芯片，而是**按危害程度给「设计活动和验证活动」
> 分层加码** —— 危害越大，要求越严、证据越多、独立性越高。

## 定义

ISO 26262 是**道路车辆功能安全**国际标准（现行主版本 2018 年发布，含多部分）。
它把「由于电子电气系统失效而导致的人身伤害风险」降到可接受水平，方式是
**给安全相关活动的严格程度分级，并要求留下可核查的证据**。

它的三个支柱：

| 支柱 | 含义 |
|---|---|
| **ASIL 等级** | 按危害（严重度 × 暴露率 × 可控性）给安全目标分级，等级越高要求越严 |
| **安全生命周期** | 从概念阶段到运行/退役，每个阶段有输入、活动、输出（工作产物） |
| **证据与追溯** | 需求 → 设计 → 验证 → 结果，每一环可双向追到；验证要有独立性 |

## 三个关键点

### 1. ASIL 等级

ASIL（Automotive Safety Integrity Level）是**严格度分级**。
等级越高，标准对该功能相关活动提的要求越严格；最低一档之上还有一个「不构成
安全目标」的档。

| 要点 | 说明 |
|---|---|
| 怎么定级 | 由**危害分析（HARA）**得出：严重度 × 暴露率 × 可控性三个维度组合 |
| 等级之间差什么 | 不是「多测几条」，而是**方法要求更硬、证据更多、独立性更高** |
| 谁定 | 系统/安全团队定安全目标与 ASIL，设计/验证团队按等级落实 |
| 不是唯一维度 | 同一芯片不同功能可有不同 ASIL，甚至同一功能分解成不同 ASIL 的子目标 |

> **本卡不写各档的具体方法论名称与量化门槛** —— 严重度/暴露率/可控性到等级的
> 映射表在标准正文的**危害分析**部分，请查标准，别凭记忆。

### 2. 安全生命周期

标准把「一个安全相关产品的一生」切成若干阶段，每个阶段要求**工作产物（evidence）**。
对设计与验证直接相关的是：

| 阶段（语义） | 谁做 | 关键产物（语义） |
|---|---|---|
| 概念 | 系统/安全 | 危害分析与风险评估、安全目标、功能安全概念 |
| 系统设计 | 系统 | 技术安全需求（TSR）、安全机制 |
| **硬件设计** | **设计** | 硬件安全需求、硬件架构设计、安全机制实现证据 |
| **硬件验证/集成** | **设计 + 验证** | 验证计划、验证结果、覆盖率证据、缺陷记录 |
| 运行/维护 | 运营 | 安全手册、现场监控 |

**核心要求**：每个阶段的输出 = 下一个阶段的输入，且**需求到验证结果可双向追溯**。

### 3. 对验证的具体要求（追溯到「标准要求什么」）

| 要求 | 语义（不写条款号与数字） |
|---|---|
| **需求追溯** | 每条安全需求能追到验证它的一条或多条验证活动；反向也成立 |
| **验证独立性** | 较高等级要求**执行验证的人/团队与设计者分离**；等级再高还要求更强的独立性（如独立评审、独立方法）——独立性具体到哪一档，查标准的**验证**部分 |
| **方法要求** | 标准对「用什么验证方法」有推荐/高度推荐的分档；等级越高，可接受的方法越受限 |
| **覆盖率证据** | 覆盖率不是「到某条线就算够」，而是**要有证据支撑「够」**；覆盖不到的要能解释并记录 |
| **工具置信度（TCL）** | 见下 |
| **缺陷/失效管理** | 验证发现的缺陷要记录、归因、闭环 |

### 4. 工具置信度（Tool Confidence Level）

**要解决的问题**：验证结果的正确性依赖工具。如果工具本身错了，结果就不可信。
ISO 26262 要求评估「这个工具出的错会不会影响安全目标」，据此决定工具输出
**能否被直接采信**，或需要**额外的验证/佐证措施**。

| 概念 | 语义 |
|---|---|
| **工具影响** | 工具输出错误时，会不会破坏安全目标（会不会漏掉/掩盖失效） |
| **工具错误检测能力** | 工具自身错误被发现有几分把握 |
| **置信等级** | 由上面两者组合决定；等级不同，允许的采信方式不同 |
| **最高档的后果** | 工具输出**不能单独作为证据**，需要交叉验证（如另一工具/独立方法佐证） |

> **不要凭记忆写 TCL 的等级定义与判定表**：等级怎么组合、每档允许什么采信方式，
> 在标准的**软件工具置信度**部分有正式定义，且各家咨询/工具厂商有大量解读。
> 引擎用到的形式/仿真/静态工具，其 TCL 论证属于**合规证据**，归 `verify/07_度量与报告/`。

## 边界（不是什么）

| 它**是** | 它**不是** |
|---|---|
| 汽车功能安全的**要求定义** | **通信信息安全**（那是 ISO/SAE 21434，见 `KB-DV-STD-004`） |
| 一套**过程与证据**的要求 | 一套**测试用例库**或验证模板 |
| 覆盖「硬件 + 软件 + 系统」 | 教你怎么写 SVA 或怎么搭 UVM 环境 |
| 要求「你留证据」 | 「证据怎么组织成报告」的格式规范（那在 `verify/07_度量与报告/`） |

**最关键的边界**：ISO 26262 说「要达到什么、要被记录什么」，
不规定「RTL 写几个状态机」或「用哪条 coverpoint」。

## 与易混概念的区别

| 易混对 | 区别 |
|---|---|
| **ISO 26262 vs ISO/SAE 21434** | 26262 防**随机失效/系统性失效**造成的功能安全风险；21434 防**恶意攻击**（网络安全）。两者在汽车上并行，接口见 `KB-DV-STD-004` |
| **ISO 26262 vs DO-254** | 前者面向**道路车辆**，用 ASIL 分级；后者面向**航空电子硬件**，用 DAL 分级（`KB-DV-STD-003`）。分级思路相似，具体表格与术语不同 |
| **ASIL vs SIL** | ASIL 是汽车语境的等级；SIL 是工业功能安全的等级（IEC 61508 体系）。**别混用** |
| **TCL vs 覆盖率** | TCL 论证的是「**工具**可信吗」；覆盖率说明「**测试**测到了多少」。两者都是证据，但回答不同问题 |
| **安全需求 vs 功能需求** | 安全需求是「为避免危害而额外加的要求」；不是所有功能需求都是安全需求，别一股脑全按 ASIL 处理 |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 把认证当成最后一道工序 | 「先做完，最后送去认证」 | 追溯链、独立性、TCL 论证都是**过程性**的，事后补不出（补出来也是假的） |
| 拿别人的 ASIL 等级直接用 | 同款芯片/同款 ECU | ASIL 由本国市场的 HARA 决定，暴露率/可控性一变等级就变 |
| 追溯到「文件夹」而非「需求项」 | 「验证计划里都列了」 | 审计要看的是**需求→验证**的逐条双向链路，不是有没有文档 |
| 独立性理解成「换个人签字」 | 读起来像走形式 | 独立性要求的是**执行与判断分离**，等级越高要求越强 —— 分界线查标准 |
| 假设工具输出天然可信 | 「仿真器不会错」 | TCL 就是冲这个假设来的；高档位要求交叉佐证 |
| 把功能安全和信息安全当一件事 | 都在汽车里 | 威胁模型与失效模型不同，交期一到会露馅 |
| 凭记忆写 ASIL/TCL 的具体数值 | 想显得专业 | **本卡最忌讳的错**：写错标准内容比不写更糟 —— 一律查标准正文 |

## 出处

- **ISO 26262:2018**《道路车辆 —— 功能安全》（多部分）。
  - ASIL 定级与危害分析 → 概念阶段相关部分
  - 硬件设计与验证要求 → 硬件层面相关部分
  - 工具置信度（TCL）→ 软件工具置信度相关部分
- 具体条款号、量化门槛、方法论名称一律以标准正文为准；本卡只保留语义。
