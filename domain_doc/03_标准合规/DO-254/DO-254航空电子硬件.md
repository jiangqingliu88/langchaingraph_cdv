# DO-254 航空电子硬件

> **一句话**：DO-254 是航空硬件的「设计保证」指南 —— 它按**失效后果的严重性（DAL）**
> 决定这套硬件需要多严的保证过程、多少证据、多高的验证独立性。

## 定义

RTCA DO-254（欧洲对应 EUROCAE ED-80）是**机载电子硬件设计保证**的行业指南，
被适航当局引用为符合性方法。它为「含可编程逻辑（如 FPGA/ASIC）或复杂电子硬件的
机载设备」规定了从需求到验证的**生命周期过程与工作产物**。

三个支柱：

| 支柱 | 含义 |
|---|---|
| **DAL 等级** | 按硬件失效对飞机/乘员安全的后果，给设计保证严格度分级 |
| **设计保证过程** | 需求捕获 → 概念设计 → 详细设计 → 实现 → 验证，各环节有产物 |
| **验证独立性** | 等级越高，验证越要由**独立于设计者**的角色执行 |

## 三个关键点

### 1. DAL 等级

DAL（Design Assurance Level）是**严格度分级**，
由「硬件功能失效对飞机的影响严重性」推导而来（从最严重的灾难性到无安全影响，
分成若干档，最高档要求最严）。

| 要点 | 说明 |
|---|---|
| 怎么定 | 由**安全性评估过程**（FHA / 系统安全评估）把失效后果映射到 DAL |
| 等级差什么 | 不是「多测几条」，而是**生命周期活动的严格度、独立性的档位、证据的完备度**不同 |
| 谁定 | 系统/安全性团队定 DAL；硬件设计/验证按等级落实过程与证据 |
| 最低档的后果 | 低档仍要走设计保证过程，只是活动形式与独立性要求放宽 |

> **本卡不写各档 DAL 对应的具体活动表格与独立性档位** —— 这些映射在标准的
> 附录/表格里，请查标准正文，别凭记忆。

### 2. 设计保证生命周期

标准把硬件的一生切成阶段，每阶段规定**输入、活动、输出（工作产物）**：

| 阶段（语义） | 谁做 | 关键产物（语义） |
|---|---|---|
| 需求捕获 | 系统 + 硬件 | 硬件需求（含派生需求）、需求可追溯性 |
| 概念设计 | 硬件设计 | 架构、接口定义、与需求的对应 |
| 详细设计 | 硬件设计 | 详细设计数据、实现方案 |
| 实现 | 硬件设计 | 可编程器件的实现/综合产物、配置管理记录 |
| **验证** | **验证（等级高时需独立）** | 验证计划/程序/结果、覆盖率分析、追溯矩阵 |
| 支持过程 | 各方 | 配置管理、过程保证、**需求追溯**、确认 |

### 3. 对验证的具体要求

| 要求 | 语义（不写条款号与数字） |
|---|---|
| **需求追溯** | 需求 ↔ 实现 ↔ 验证结果**双向可追**，是适航审查的第一顺位证据 |
| **验证独立性** | 较高 DAL 要求验证活动由**独立于设计者**的一方执行；独立到什么程度随 DAL 上升 —— 具体档位查标准 |
| **验证方法** | 标准区分**需求驱动验证**与**实现驱动（鲁棒性）验证**：不仅证明「该做的做了」，还要检查「不该发生的没发生」 |
| **覆盖率** | 覆盖率分析是**要求项**：要说明哪些需求/结构被覆盖、未覆盖的如何处置 |
| 简单 vs 复杂硬件 | 标准对「简单硬件」给出**可省略部分过程**的路径，但判据严格（功能单纯、可穷举、经验充分）；**别把「觉得简单」当简单** |
| 工具与器件数据 | 用到的综合/仿真工具、器件厂商数据，其采信需论证（与功能安全里的工具评估思路类似） |

## 边界（不是什么）

| 它**是** | 它**不是** |
|---|---|
| 机载**硬件**（含 FPGA/ASIC）的设计保证指南 | 机载**软件**的指南 —— 那是 DO-178 系列（别混） |
| 一套**过程与证据**要求 | 一套现成的测试集或验证环境 |
| 按 **DAL** 分层 | 按 ASIL 分层（那是 ISO 26262，见 `KB-DV-STD-002`） |
| 要求「留适航可审查的证据」 | 「证据怎么写成报告」的格式（那在 `verify/07_度量与报告/`） |

**最关键的边界**：DO-254 管**硬件**；同机型的软件走 **DO-178**。
把两者的证据要求混在一份计划里，是适航审查里最常见的返工点。

## 与易混概念的区别

| 易混对 | 区别 |
|---|---|
| **DO-254 vs DO-178** | 254 是硬件（FPGA/ASIC/板）；178 是机载软件。名字像、对象不同 |
| **DO-254 vs ISO 26262** | 前者用 **DAL**、面向航空；后者用 **ASIL**、面向道路车辆。分级逻辑相似，表格与术语不同，**不要交叉套用** |
| **DAL vs 功能安全 ASIL** | 都是「按后果分级」，但一个源自飞机安全性评估，一个源自汽车 HARA |
| **设计保证 vs 认证** | 设计保证是**过程**；适航审查/认证是对过程的**符合性判定**。做了设计保证不等于自动过审 |
| **简单硬件 vs 复杂硬件** | 是标准里的**正式分类**（决定能否简化过程），不是「我觉得它简单」 |

## 坑

| 坑 | 为什么诱人 | 后果 |
|---|---|---|
| 把认证当最后一道工序 | 「先做完再送审」 | 追溯矩阵、独立性、配置管理是**过程性**产物，事后补不真 |
| 拿软件那套（DO-178）套硬件 | 团队里有软件背景的人 | 证据结构与独立性档位对不上，审查返工 |
| 自判「这是简单硬件」 | 想省掉一大半过程 | 简单硬件的判据严格（可穷举、功能单纯），自判往往站不住 |
| 只做需求驱动验证 | 「需求都测了」 | 漏掉**鲁棒性/实现驱动验证** —— 标准明确要求两边都做 |
| 独立性理解成换人签个字 | 走形式最省事 | 要求的是执行与判断分离，DAL 越高越硬 |
| 追溯矩阵事后拼 | 「拿需求表对一下就行」 | 真正的双向追溯要求实现与验证结果都挂到同一条需求上 |
| 凭记忆写 DAL 具体门槛 | 想显得专业 | **本卡最忌讳的错**：标准内容写错比留白更糟 —— 一律查标准正文 |

## 出处

- **RTCA DO-254 / EUROCAE ED-80**《机载电子硬件设计保证指南》
  - DAL 分级与活动映射 → 标准正文与附录表格
  - 验证过程（需求驱动 / 实现驱动）与独立性 → 验证相关章节
  - 简单/复杂硬件判据 → 标准相应章节
- **RTCA DO-178 系列**（对比参照，机载软件）
- 具体条款号与量化门槛以标准正文为准；本卡只保留语义。
