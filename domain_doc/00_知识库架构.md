# 知识库架构：共用四域 + 两翼 + 五层 + 三体系

## 1. 定位与原则

- **方法论优先，工具其次** —— 工具三年一换，方法十年不变。工具卡可以有，但它得说清
  "这条知识在换工具之后还成不成立"。
- **设计与验证并重** —— 两翼不是「验证为主、设计为辅」。签核那条线上，RTL Freeze
  在验证签核**之前**；只写验证一侧，签核就是断头的。
- 按「角色 + 任务 + 流程 + 技术 + 工具 + 协议」多维检索
- 每个知识点尽量包含：概念、适用场景、步骤、模板、代码、检查清单、案例、坑点
- 所有条目版本化、可评审、可追溯

### 三条不做什么

| 不做 | 为什么 |
|---|---|
| 不做「大而全的 wiki」 | 域是**检索骨架**，不是要求每个格子都填满。宁可 3 个域有 20 张扎实的卡，不要 15 个域各挂 2 篇空话 |
| 不做「知识的搬运」 | 抄一遍厂商文档没有价值 —— 价值在**你踩过的坑**和**你做的取舍**。引用原文用链接 |
| 不做「唯一真相的副本」 | 一条知识一个家（见根 README 的铁律）。两翼结构下这条最容易被违反 |

## 2. 结构

### 2.1 共用四域（两翼都引用）

`01_术语与索引` · `02_流程与签核` · `03_标准合规` · `04_治理运营`

**为什么提上来**：这四类知识两翼都要用（术语表、签核门、ISO 26262、写卡规范）。
放进任何一翼，另一翼要么复制一份（漂移），要么写一个跨翼的相对路径（脆弱）。

`02_流程与签核` 里躺着**两个出档门**：

| 门 | 谁放行 | 判据在哪 |
|---|---|---|
| **RTL Freeze** | 设计负责人 | `02_流程与签核/` 的 RTL Freeze 卡 |
| **验证签核** | 验证负责人 | `02_流程与签核/` 的签核卡 + `verify/07_度量与报告/` |

两张门**共用同一套骨架**（触发条件 → 准入/准出 → 制品 → 谁放行），判据不同。
这不是巧合 —— 签核流程本来就同构，分开定义会得到两份迟早不一致的清单。

### 2.2 两翼

| 翼 | 回答的问题 | 域 |
|---|---|---|
| `design/` | **RTL 该怎么写** | 微架构与RTL编码 / 综合·时序·PPA / 低功耗与UPF / DFT·CDC·安全设计 |
| `verify/` | **怎么证明 RTL 对** | 基础理论 / 验证方法学 / 技术与组件 / 工具与脚本 / 协议与VIP / 项目案例 / 度量与报告 |

**归翼判据**：问「这条知识是让你把 RTL 写得不同，还是让你把测试写得不同？」

**跨翼话题怎么办**：CDC、低功耗、安全、DFT 都是跨翼的。规则是**按面拆卡**
（设计侧怎么处理 / 验证侧怎么验），互相链接，不互相抄。根 README 有 CDC 的例子。

### 2.3 域码

id 形如 `KB-DV-<域码>-<序号>`；**DV = Design & Verification**。
完整对照表见 `04_治理运营/卡片模板.md`。

## 3. 五层

同一件事，深度不同的人要的东西不同 —— 五层就是给这个用的。

| 层 | 是什么 | 典型读者 | 落在哪 |
|---|---|---|---|
| **资源层** | 标准、论文、书籍、厂商文档、课程、博客的统一入口 | 想找原始出处的人 | 03（标准）、其余各域末尾的「参考」段 |
| **知识层** | 术语、概念、协议、语言、工具基础 | 刚接触的人 | 01、两翼各自的基础域（`design/01`、`verify/01`、`verify/03`、`verify/05`） |
| **方法层** | UVM、形式、CDV、验证计划、覆盖率收敛、低功耗、综合时序、DFT | 要做这件事的人 | `design/01`–`04`、`verify/02`、02（签核） |
| **实践层** | 项目案例、代码模板、脚本、检查清单、FAQ、调试记录 | 正在做的人 | `verify/06`、各域的模板卡 |
| **洞察层** | 最佳实践、反模式、趋势、方法论演进 | 定方向的人 | 各域的反模式卡、`verify/06` 的复盘 |

**判据**：一张卡**只属于一层**。「AXI 是什么」（知识层）、「AXI 握手怎么验」（方法层）、
「我在某项目里踩过的 AXI 坑」（实践层）是**三张卡**，不是一张大文章。

## 4. 三体系

### 4.1 分类标签体系 —— `04_治理运营/标签字典.md`

标签是**受控词表**，不是自由词：写卡的时候从字典里挑，不在字典里的先讨论再补。
自由标签的结局是「AXI」「axi」「AXI4」「amba-axi」四个同义标签并存，检索时谁都搜不全。

### 4.2 知识卡片模板体系 —— `04_治理运营/卡片模板.md`

十种卡片（概念 / 方法 / 流程 / 工具 / 协议 / 组件 / 案例 / 模板 / FAQ / 反模式），
共用一套 frontmatter 字段。**字段是契约**：写卡的工具、查卡的脚本、评审的人都按它走。

### 4.3 治理运营体系 —— `04_治理运营/`

| 文件 | 管什么 |
|---|---|
| `贡献指南.md` | 加一条知识的完整动作 |
| `评审流程.md` | 草稿 → 评审中 → 已验证 的状态机 |
| `版本规范.md` | 条目级版本与过期标记 |
| `标签字典.md` | 受控词表 |
| `卡片模板.md` | 十种卡的结构与域码 |

## 5. 卡片粒度

**一张卡 = 一个能独立回答的问题。**

太小（「`uvm_config_db` 的第二个参数是什么」）→ 卡的数量爆炸，检索变成翻字典；
太大（「UVM 完全指南」）→ 没人读得完，改一处不知道影响哪里。

判断方法：**如果一句话说不清这张卡回答什么，它就该拆。**

**跨翼话题是这条最常被违反的地方**：一张「CDC 完全指南」同时讲设计怎么同步、
验证怎么打、工具怎么报错 —— 它该拆成三张，各归各家。

## 6. 索引

两个索引，读的人不同：

| 索引 | 读者 | 形态 |
|---|---|---|
| `01_术语与索引/索引.csv` | 脚本 / 搜全库的人 | 机器读，一行一条；`path` 从 `domain_doc/` 根算 |
| 各域 `_index.md` 的表格 | 逛到那个域的人 | 人读，只列本域 |

**两边都要更新**，否则「域索引里没有、总索引里有」这种不一致会让人不再信任任何一个。
