# 设计/验证工程师的思维方式 vs SignOffAI 的 12-Agent 架构：匹配度分析

> **核心问题**：12 个 Agent 串成一条流水线，跟真实 IC 工程师的日常工作思维模式，到底对不对得上？
>
> 日期：2026-08-10

---

## 一、先搞清楚两个角色的思维方式

设计工程师（DE）和验证工程师（VE）虽然看同一份 Spec，但大脑里跑的是**完全不同的两套逻辑**。

### 1.1 设计工程师的日常思维链

```
拿到 Spec
  ↓
"这个模块要做什么？输入输出是什么？"
  ↓
"我拆成哪几个子模块？寄存器怎么排？状态机跳什么？"
  ↓
"开始写 RTL，先把接口和骨架搭出来"
  ↓
"关键路径的逻辑写对没有？波形上看一下"
  ↓
"编译过了，几个简单用例跑通了，交给验证的同事"
```

**设计工程师关心的东西：**

| 关注点 | 内心独白 |
|--------|---------|
| 功能正确性 | "我这块逻辑跟 Spec 说的是一回事吗？" |
| 接口协议 | "APB 的 ready/valid 握手我对齐了吗？" |
| 时序/面积 | "这个乘加器会不会成为关键路径？" |
| 可综合性 | "这个写法综合工具认不认？" |
| 边界条件 | "FIFO 空的时候读了会怎样？" |

**设计工程师不关心的东西（通常）：**
- UVM driver/monitor 怎么写
- 功能覆盖率怎么建模
- 回归测试怎么编排
- 签核检查清单

### 1.2 验证工程师的日常思维链

```
拿到 Spec（同一份）
  ↓
"这个模块有哪些功能点可能出错？我要测什么？"
  ↓
"验证环境怎么搭？几个 Agent？Scoreboard 怎么比？"
  ↓
"测试用例怎么覆盖所有场景？约束怎么设？"
  ↓
"断言加在哪些关键接口上？"
  ↓
"跑回归 → 看覆盖率 → 分析 gap → 补用例 → 再跑"
  ↓
"所有测试通过 + 覆盖率达到目标 → 签核"
```

**验证工程师关心的东西：**

| 关注点 | 内心独白 |
|--------|---------|
| 测试完备性 | "有没有一个合法场景我没测到？" |
| 检查器正确性 | "Scoreboard 的预期值算对了吗？" |
| 随机约束有效性 | "这个约束会不会永远也随机不到那个 corner？" |
| 覆盖率缺口 | "covergroup 100% 了但 cross-coverage 才 60%，还差什么？" |
| 失败根因 | "这个 case 挂了是因为 RTL 有 bug 还是环境有问题？" |
| 签核信心 | "现在这个状态，我敢签吗？" |

**验证工程师不关心的东西（通常）：**
- RTL 怎么实现状态机
- 寄存器地址怎么分配
- 综合约束怎么设

## 二、12 个 Agent 逐一映射：谁对上了，谁没对上

### 2.1 总体映射表

```
12-Agent 流水线
    │
    ├── spec_planner        ← 【双角色共用】
    ├── design_architect    ← 【设计专属】
    ├── verify_architect    ← 【验证专属】
    ├── model_agent         ← 【设计为主，验证借力】
    ├── write_rtl           ← 【设计专属】
    ├── test_engineer       ← 【验证专属】
    ├── assertion_engineer  ← 【验证为主，好设计师也写】
    ├── coverage_manager    ← 【验证专属】
    ├── regression_manager  ← 【验证专属】
    ├── debug_engineer      ← 【双角色共用】
    ├── quality_assurance   ← 【双角色共用】
    └── report_generator    ← 【验证专属（签核）】
```

### 2.2 逐 Agent 深度分析

---

#### Agent 1：`spec_planner`（规格分析 → 测试计划）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ✅ 会。拿到 Spec 第一件事就是理解功能、提取关键参数 |
| **VE 会做吗？** | ✅ 会。同一个 Spec，VE 读的时候脑子里已经开始列测试点了 |
| **匹配度** | ⭐⭐⭐⭐⭐ **完美匹配** |
| **关键差异** | DE 和 VE 看同一份 Spec 的角度不同：DE 关注"我要实现什么"，VE 关注"什么情况下会出错"。当前 Agent 用同一份输出同时服务两端，**需要明确区分两类产物** |

**建议：** `spec_planner` 应该输出两份东西——`design_view`（功能分解、接口契约、寄存器列表）和 `verification_view`（测试点、风险点、corner case 清单）。

---

#### Agent 2：`design_architect`（模块层次 + 寄存器映射）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ✅ 这是 DE 的**核心工作**。拿到需求后第一件事就是画模块框图、定义接口、排寄存器 |
| **VE 会做吗？** | ❌ VE 不会主动做模块分解。VE 理解模块层次只是为了搭建验证环境，不是创造性的设计活动 |
| **匹配度** | ⭐⭐⭐⭐⭐ **跟 DE 完美匹配**，⭐ **跟 VE 几乎无关** |

**没问题。** 这个 Agent 就是为设计工程师设计的。

---

#### Agent 3：`verify_architect`（UVM 验证环境架构）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ❌ 绝大多数 DE 不写 UVM，不知道 driver/monitor/scoreboard 怎么组织 |
| **VE 会做吗？** | ✅ 这是 VE 的**核心工作**。拿到设计后第一件事就是规划验证环境：几个 agent、scoreboard 怎么比、reference model 怎么接 |
| **匹配度** | ⭐⭐⭐⭐⭐ **跟 VE 完美匹配**，❌ **跟 DE 无关** |

**没问题。** 这个 Agent 就是为验证工程师设计的。

---

#### Agent 4：`model_agent`（C++ 参考模型）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ⚠️ 部分 DE 会写简单的算法模型来验证自己的逻辑，但不是标配 |
| **VE 会做吗？** | ✅ VE 经常需要参考模型来算预期值（尤其是算法密集型模块） |
| **匹配度** | ⭐⭐⭐ **跟两者都有关系但不核心** |

**微妙之处：** 参考模型的"作者"应该是 DE（因为它体现设计意图），但"使用者"是 VE（用它来算 scoreboard 预期值）。当前放在流水线里作为独立步骤是对的，但 **它的输入应该是 `design_architect` 的输出，而不是等 `verify_architect` 跑完才跑**。

---

#### Agent 5：`write_rtl`（写可综合 RTL）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ✅ 这是 DE 的**根本工作**。整个职业生涯都在干这个 |
| **VE 会做吗？** | ❌ VE 不写 RTL。VE 写的是 testbench，不是设计 |
| **匹配度** | ⭐⭐⭐⭐⭐ **纯粹的设计工程师活动** |

**没问题。** 这是设计流水线的终点。

---

#### Agent 6：`test_engineer`（写测试用例）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ⚠️ DE 会写几个简单的定向测试确认自己的 RTL 能跑，但不会写完整的 constrained-random 测试套件 |
| **VE 会做吗？** | ✅ 这是 VE 的**日常工作**。写 sequence、配约束、构造场景 |
| **匹配度** | ⭐⭐⭐⭐⭐ **跟 VE 完美匹配** |

**没问题。** 但这里有一个**关键架构问题**：在真实工作流里，VE 写测试的时候 RTL 已经存在了——VE 是针对一个 **已知的 DUT** 写测试。但在 AI 流水线里，如果 LLM 同时生成 RTL 和测试，**测试的预期值从哪来？** 这就是为什么 `model_agent` 必须跑在 `write_rtl` 和 `test_engineer` 之前。

---

#### Agent 7：`assertion_engineer`（SVA 断言）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ⚠️ 好的 DE 会在关键接口上写断言（尤其是 assume 性质的），但大多数 DE 不写 |
| **VE 会做吗？** | ✅ VE 写断言来检查协议合规和功能正确性（assert 性质） |
| **匹配度** | ⭐⭐⭐⭐ **以 VE 为主，DE 参与** |

**微妙之处：** 断言分两种——**设计假设**（assume，DE 写）和**验证检查**（assert，VE 写）。当前 Agent 把两者混在一起。理想情况是 DE 输出"我认为这些条件永远成立"→ 生成 assume assertion；VE 输出"如果这些条件不成立就是 bug"→ 生成 assert assertion。**一个 agent 两套 prompt。**

---

#### Agent 8：`coverage_manager`（覆盖率收集与分析）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ❌ 设计工程师不看覆盖率。那是验证工程师的指标 |
| **VE 会做吗？** | ✅ 这是 VE 的核心 KPI。覆盖率不达标 = 验证没做完 |
| **匹配度** | ⭐⭐⭐⭐⭐ **纯粹的验证活动** |

**没问题，但流程位置值得商榷：** 在真实项目中，覆盖率分析不是一次性活动——它是一个**循环**：

```
跑回归 → 看覆盖率 → 补用例 → 再跑 → 再看 → ...直到达标
```

当前把它建模成流水线上的一个"阶段"，意味着只跑一次。这在 AI 场景下可能不够。**覆盖率应该是一个"门控"（gate），不达标就回到 test_engineer 重新生成用例。**

---

#### Agent 9：`regression_manager`（回归执行与结果分析）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ❌ DE 不管理回归。最多跑几个用例确认自己的改动没破坏功能 |
| **VE 会做吗？** | ✅ VE 的日常：提交回归、第二天来看结果、分析失败 |
| **匹配度** | ⭐⭐⭐⭐⭐ **纯粹的验证活动** |

**没问题。** 这是验证流水线的执行引擎。

---

#### Agent 10：`debug_engineer`（失败分析 + 根因定位）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ✅ 波形上发现 RTL 行为不对，DE 自己定位修改 |
| **VE 会做吗？** | ✅ 仿真失败后 VE 先判是环境 bug 还是 RTL bug |
| **匹配度** | ⭐⭐⭐⭐⭐ **双角色共用，且协作最密集的环节** |

**这是当前架构最有价值的 Agent 之一。** 真实项目中，DE 和 VE 在 debug 阶段沟通最频繁：

```
VE: "这个 case 挂了，波形显示 FIFO 满了还在写，是不是 RTL 的 full 标志算错了？"
DE: "我看了波形，full 标志是对的。是你 sequence 在 full 之后没等就发了下一拍？"
VE: "...让我再看一下"
```

当前 `debug_engineer` 的定位是"分析失败、给出路由建议"，这是对的。但它的输出应该能驱动一个**自动化回路**：如果是环境 bug → 回 `verify_architect` 修；如果是 RTL bug → 回 `write_rtl` 修；如果是测试约束不对 → 回 `test_engineer` 修。

---

#### Agent 11：`quality_assurance`（代码审查 + 质量评分）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ✅ Code review 是 DE 的日常 |
| **VE 会做吗？** | ✅ VE 也要 review testbench 代码质量、可维护性 |
| **匹配度** | ⭐⭐⭐⭐ **双角色共用，但评价标准完全不同** |

**微妙之处：** DE 的 QA 标准是"代码可读性、可综合性、命名规范、有没有 latch"；VE 的 QA 标准是"testbench 可复用性、有没有 hard-coded 延迟、随机约束的合法性"。同样的"QA"动作，评分维度和权重完全不同。当前 Agent 能否区分？

---

#### Agent 12：`report_generator`（签核报告）

| 维度 | 分析 |
|------|------|
| **DE 会做吗？** | ❌ DE 不写签核报告 |
| **VE 会做吗？** | ✅ 签核是验证工程师的最终交付物 |
| **匹配度** | ⭐⭐⭐⭐⭐ **纯粹的验证收尾活动** |

**没问题。** 这是你产品愿景的核心——"签核证据包"。

## 三、全局视角：架构图 vs 真实工作流

### 3.1 当前 12-Agent 架构的本质

```
[Spec] → A1 → A2 → A3 → A4 → A5 → A6 → A7 → A8 → A9 → A10 → A11 → A12 → [Signoff]
         ↑    ↑    ↑    ↑    ↑    ↑    ↑    ↑    ↑    ↑     ↑     ↑     ↑
         规格  设计  验证  参考  写   写   断言  覆盖  回归  调试  质量  签核
         分析  架构  架构  模型  RTL  测试       率    管理        审查  报告
```

这是一条**单向线性流水线**——像芯片制造的光刻步骤，一个接一个。

### 3.2 真实工程师的思维模型

真实工程师的思维是**有分支、有循环、有协作点**的：

```
                    ┌─────────────────────┐
                    │       Spec          │
                    └──────┬──────────────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            │
    ┌─────────────┐  ┌───────────┐     │
    │ 设计工程师   │  │ 验证工程师 │     │
    │ 的脑回路    │  │ 的脑回路  │     │
    └──────┬──────┘  └─────┬─────┘     │
           │               │           │
    1. 理解功能       1. 理解功能      │
    2. 模块划分       2. 列测试点      │
    3. 接口设计       3. 搭验证环境    │
    4. 写RTL     ──┬── 4. 写测试 ──┐   │
    5. 自测        │   5. 跑回归   │   │
       │           │   6. 看覆盖率 │   │
       │           │   7. 分析gap  │   │
       │           │   8. 补用例 ──┘   │
       │           │       ↑           │
       │           │       │ (循环)    │
       │           │   9. 签核         │
       │           │                   │
       └──── Debug 协作点 ─────────────┘
                    │
                    ▼
               [最终交付]
```

### 3.3 关键差异总结

| 维度 | 当前 12-Agent 架构 | 真实工程师思维 |
|------|-------------------|---------------|
| **结构** | 单向线性管道 | 分叉 + 循环 + 汇合 |
| **角色** | 所有 Agent 平权，不区分 DE/VE | DE 和 VE 是两条独立的职业路径 |
| **迭代** | 每个阶段执行一次 | 写测试→跑→看覆盖率→补用例，反复多轮 |
| **协作** | 只有数据传递，没有"协商" | Debug 阶段 DE 和 VE 高频互动 |
| **门控** | 没有质量门控 | "覆盖率达不达标？不达标不许签" |
| **终态** | 12 步全跑完 = 结束 | 覆盖率达标 + 所有 test pass + 已知 bug 已处理 = 结束 |

## 四、哪些地方"对上了"，哪些地方"跑偏了"

### ✅ 做得好的地方（4 处完美对齐）

| Agent | 对齐原因 |
|-------|---------|
| `design_architect` | 设计工程师每天就在做模块分解和寄存器规划——**名字都不需要改** |
| `verify_architect` | 验证工程师拿到 DUT 后第一件事就是搭 UVM 环境架构——**业界标准动作** |
| `test_engineer` | 写测试用例是 VE 的日常——**完美匹配** |
| `spec_planner` | 无论 DE 还是 VE，工作起点都是读 Spec——**放第一个位置完全正确** |

### ⚠️ 需要微调的地方（3 处）

| Agent | 问题 | 建议 |
|-------|------|------|
| `model_agent` | 放在 `verify_architect` 之后不合理——参考模型体现的是**设计意图**，应该在 `write_rtl` 之前 | 挪到 `design_architect` 和 `write_rtl` 之间 |
| `assertion_engineer` | 把 assume（设计假设）和 assert（验证检查）混在一起 | 拆两套 prompt，DE 侧生成 assume，VE 侧生成 assert |
| `quality_assurance` | DE 的代码审查标准和 VE 的完全不同 | 拆成两个 gate：`design_review`（检查 RTL 质量）+ `tb_review`（检查 testbench 质量） |

### ❌ 跑偏的地方（2 处）

| 问题 | 为什么跑偏 | 影响 |
|------|-----------|------|
| **单向流水线 vs 验证循环** | 覆盖率和回归建模成了"一步做完"，但真实项目里它们跟 test_engineer 之间有多次往返 | AI 生成的用例可能不够，但没有机制自动触发"再生成一轮" |
| **缺少"协商点"** | `debug_engineer` 输出"可能是 RTL bug 也可能是环境 bug"，但在流水线里没有回路让这个判断驱动修复 | 发现 bug 后流水线无法自我修复，只能报告然后停在那里 |

## 五、架构演进建议

### 5.1 短期（不改架构，补配置）

在现有 12-Agent 线性结构上增加：

1. **工作流模板**——不是所有模块都需要 12 个全跑：
   ```
   workflow "simple_reg_module":   [spec, design, write_rtl, test, QA]
   workflow "complex_comm_module": [spec, design, verify, model, write_rtl, 
                                     test, assertion, regression, coverage, 
                                     debug, QA, report]
   ```

2. **覆盖率回路标记**——`coverage_manager` 输出里加一个 `needs_more_tests: true/false`，如果为 true，自动调度一轮 `test_engineer` 重新生成

### 5.2 中期（轻量重构）

把 12 个 Agent 按角色重新分组：

```
Design 流：  spec → design_architect → model_agent → write_rtl → [design_QA]
                                                                      │
                                                                      ▼
                                                              [Debug 协作区]
                                                                      │
                                                                      ▼
Verification 流： spec → verify_architect → test_engineer → assertion   │
                       → regression ←→ coverage (循环)                 │
                       → [verification_QA] → report                    │
```

**核心变化：**
- 两条流可以**独立运行**（设计工程师单独用 Design 流，验证工程师单独用 Verification 流）
- 也可以**串联运行**（完整自动化产出）
- `debug_engineer` 变成两条流的**交汇点**，而不是流水线上的一个步骤

### 5.3 长期（对标 CLAUDE.md 路线图 Phase 4）

在 Phase 4（签核决策引擎）阶段，引入**多轮迭代**机制：

```
verification_loop:
    while coverage < target and pass_rate < 100%:
        test_engineer.generate_missing_tests(coverage_gaps)
        regression_manager.run()
        coverage_manager.analyze()
        debug_engineer.triage_failures()
    
    report_generator.signoff()
```

这正是你的 `src/core/execution.py` 里 `_WORKFLOW_PHASE_MAP` 能支撑的——**回路控制不是新引擎，是现有引擎的新编排模式**。

## 六、结论

### 一句话回答你的问题

> **12-Agent 架构的 70% 跟真实工程师思维匹配。但剩下 30%——尤其是"验证是循环不是直线"和"DE/VE 是两个角色而不是流水线工人"——是你下一阶段架构演进要解决的核心问题。**
