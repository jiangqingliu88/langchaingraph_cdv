### 🛠️ 工程上怎么破局？

**答案：分阶段渐进验证，而不是"全有或全无"。**

---

## 阶段0：冒烟测试（Sanity Check）

**目的**：不做验证，只是确认"能跑起来"。

| 检查项 | 怎么做 | 判断标准 |
|--------|--------|----------|
| 编译通过 | `vlogan +v2k ...` | 0 errors |
| 仿真启动 | `vcs -R` | 不崩溃，跑到`$finish` |
| 时钟复位 | 看波形 | pclk有翻转，preset_n正常释放 |
| 最少操作 | APB写1个寄存器 | 波形有pclk/psel/penable动作 |

**结论**：如果这步都过不了，后面全部白搭。

---

## 阶段1：单Agent单用例验证

**目的**：**逐一确认每个Agent和每个基本功能是对的**，而不是一上来就全并发。

```
┌─────────────────────────────────────────────────────────────────┐
│  阶段1-1：验证 APB Agent 自身                                  │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  只测 APB Agent，DUT 用 APB Slave Model 代替           │    │
│  │  目的：确认 APB Agent 发的时序符合协议规范              │    │
│  └─────────────────────────────────────────────────────────┘    │
│                              ▼                                  │
│  阶段1-2：验证 DUT APB 接口 (DUT + APB Agent)                  │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  只做 APB 读写寄存器，不使能 UART 收发                  │    │
│  │  期望：写什么读什么                                     │    │
│  └─────────────────────────────────────────────────────────┘    │
│                              ▼                                  │
│  阶段1-3：验证 UART Agent 自身                                 │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  只测 UART Agent，DUT 用 UART Loopback Model 代替       │    │
│  │  目的：确认 UART Agent 发的串行波形符合协议              │    │
│  └─────────────────────────────────────────────────────────┘    │
│                              ▼                                  │
│  阶段1-4：验证 DUT UART 接口 (DUT + UART Agent)                │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  只做 UART 数据收发，验证帧格式                        │    │
│  │  期望：发送数据 = 接收数据                             │    │
│  └─────────────────────────────────────────────────────────┘    │
│                              ▼                                  │
│  阶段1-5：全链路验证 (APB Agent + DUT + UART Agent)            │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  通过 APB 配寄存器，UART Agent 发包，DUT 收发           │    │
│  │  期望：tx = rx，寄存器和状态机符合预期                  │    │
│  └─────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────┘
```

**这个阶段的目标**：确认**基础功能链路上没有明显Bug**，而不是"验证全部正确"。

---

## 阶段2：定向用例测试

**目的**：**用"确定性"的输入，验证"确定性"的输出**。

| 测试点 | 输入 | 期望输出 | 验证方法 |
|--------|------|----------|----------|
| 寄存器复位值 | 复位释放后读所有寄存器 | 等于复位值 | 自动比较 |
| APB写后读 | 写0x5A5A_5A5A到每个寄存器 | 读回相同值 | 自动比较 |
| 发送1字节 | 写0x55到TX_FIFO | tx波形产生0x55帧 | 波形检查 |
| 环回模式 | 发送0xAA，环回使能 | rx接收到0xAA | 自动比较 |

**关键区别**：

```
❌ 随机约束测试：谁也不知道输入是什么，输出对了也不知道对不对
✅ 定向用例测试：输入是已知的，输出是确定的，一目了然
```

**这个阶段的目标**：**确认DUT在"常见简单场景"下的行为符合预期**。如果定向用例都过不了，RTL肯定有问题。

## 🎯 核心策略：先Debug，后回归

在芯片验证中，本质上有两件事：

| | **Debug模式** | **回归模式** |
|--|--------------|-------------|
| **目标** | 找Bug | 刷覆盖率 |
| **用例** | 定向、小规模 | 大规模随机并发 |
| **环境** | 调试工具全开（波形、日志） | 只留必要日志，节省资源 |
| **种子** | 固定种子 | 海量随机种子 |
| **分析** | 逐个波形查看 | 自动比较 + 覆盖率报告 |
| **阶段** | 验证初期 | 验证中后期 |

**你的问题本质是**：**你还在"Debug模式"阶段，却在想"回归模式"的并发跑。**

正确做法：

```
验证流程：
   定向用例 → 发现Bug → 修复 → 定向用例通过 → 加入回归集
   (Debug)     (修复)   (确认)    (Debug通过)   (积累)
        ↓
   积累足够多的"回归用例集"
        ↓
   并发跑回归集 ← 这才是刷覆盖率的时候
```

## ✅ 一句话总结

> **"不确定对不对"是正常的，所有验证一开始都不确定对不对。**
>
> **正确的策略是：从"确定性"开始验证（定向用例），逐步建立信心。当所有定向用例都通过后，你才获得了"并发随机"的入场券。**
>
> **不要用并发随机来"探索"有没有Bug，要用定向用例来"证明"功能是正确的。并发随机是用来"寻找"边界Bug和"冲刺"覆盖率的。**

用打仗来比喻：
- **定向用例** = 侦察兵，把地形摸清楚（确认基本功能）
- **并发随机** = 大部队火力覆盖，清扫剩余死角（冲刺覆盖率）

**先派侦察兵，再上大部队。顺序不能反。**
