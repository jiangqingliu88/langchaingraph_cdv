你现在的 **SignOffAI Architecture 4.0 / Verification Agentic System**，本质上是在构建一个：

**能够理解芯片验证任务、自主规划验证工作、生成验证资产、调用 EDA 工具执行、分析结果、修复问题，并通过确定性证据完成 Signoff 的 AI 验证系统。**

它不是简单地让多个 LLM Agent 互相聊天，也不是一个自动生成 UVM 的工具。

它的核心工作原理是：

> **AI 负责思考和提出方案，Engine 负责执行和控制，IR 负责统一描述，Runtime 负责连接真实 EDA 环境，Evidence 负责证明结果。**

我从一个实际的 IC 验证任务出发，解释整个系统怎么运转。

# **一、先看整体工作原理**

**Engine — 确定性执行与裁决层**

这套架构最重要的地方，是把过去由一个人完成的验证工作拆成了不同职责。

# **二、用一个真实任务解释它怎么工作**

假设你要验证一个 DMA 模块。

RTL 有一个 DMA，支持：

- 多个 DMA Channel。
- 不同长度的数据搬运。
- 地址随机化。
- 与 GEMM 计算单元并发。
- DMA 之间存在地址冲突风险。
- 需要 UVM 验证和覆盖率闭合。

你向 SignOffAI 输入：

> 验证 DMA 和 GEMM 并发访问时的地址冲突，确保不存在非法地址重叠，并生成 UVM 测试环境。

接下来系统怎么做？

## **第一步：Agent 理解任务**

Planner Agent 首先分析验证目标。

它不会直接写一大堆 SystemVerilog，而是把任务拆解为：

1. 分析 DMA RTL 接口。
2. 提取 DMA 描述符结构。
3. 提取 GEMM 访问地址范围。
4. 建立资源模型。
5. 定义冲突判定规则。
6. 生成随机约束。
7. 生成 UVM Sequence。
8. 编译和仿真。
9. 检查覆盖率。

这里 LLM 的作用是理解、推理和提出验证方案。

它可以生成错误的方案，所以不能直接信任它。

## **第二步：IR 建立统一模型**

这是整个架构非常关键的地方。

例如，Agent 分析出两个 DMA 任务：

**DMA 任务 A**

地址区间

# **0x1000–0x1FFF**

**GEMM 任务 B**

地址区间

# **0x3000–0x3FFF**

**地址是否重叠？**

NO

这是一个简化的 Resource IR 示例，实际还需要记录地址空间、访问生命周期、任务依赖等信息。

IR 不只是保存数据，而是表达验证语义。

比如：

- 谁在访问资源？
- 访问什么地址？
- 访问范围多大？
- 哪些操作可以并发？
- 什么情况属于冲突？
- 什么情况属于合法行为？

这样，后续生成 UVM、约束、检查器时，就不需要每个 Agent 自己重新理解一遍需求。

## **第三步：Agent 生成验证资产**

Verification Agent 根据 IR 生成：

- UVM Agent。
- UVM Environment。
- UVM Sequence。
- SystemVerilog Constraint。
- Scoreboard。
- Assertions。
- Coverage Model。

例如地址冲突约束：

```
constraint no_overlap_c {
  if (enable_conflict == 0) {
    !(dma_start < gemm_end &&
      gemm_start < dma_end);
  }
}
```

这里要注意：

LLM 只是生成代码。

代码是否正确，需要后续编译、规则检查和仿真验证。

## **第四步：Engine 接管执行**

这一步是 Agent 和 Engine 的关键分界线。

Agent 提交任务：

```
Task:
  compile_uvm
  run_regression
  analyze_coverage
```

Engine 负责：

1. 检查输入是否合法。
2. 检查依赖是否满足。
3. 检查工具是否可用。
4. 调用编译器。
5. 调用仿真器。
6. 记录运行状态。
7. 收集日志和结果。

例如：

```
compile
  |
  +-- PASS
       |
       v
regression
  |
  +-- PASS
       |
       v
coverage
  |
  +-- INCOMPLETE
```

Engine 不需要 LLM 来判断编译是否成功。

编译器返回值、日志、仿真退出状态、覆盖率数据库，才是执行判据。

## **第五步：发现问题后，Agent 进入闭环**

假设仿真结果发现：

```
TEST: dma_gemm_parallel_test

ERROR:
DMA0 address range overlaps GEMM0

SEED:
102938

SIMULATION:
FAIL
```

这时候系统不会简单地宣布任务结束。

它会启动 Debug Agent：

1. 分析失败日志。
2. 定位失败的 Sequence。
3. 检查 DMA 和 GEMM 的地址范围。
4. 判断是 RTL Bug、Testbench Bug，还是约束模型错误。
5. 给出修复建议。

如果需要修改代码，Repair Agent 提出修改方案。

Engine 再执行：

```
修改代码
   |
   v
静态检查
   |
   v
重新编译
   |
   v
重新仿真
   |
   v
重新分析覆盖率
   |
   v
证据重新归档
```

这就形成了一个自主迭代闭环。

## **Agentic Verification Loop**

1. **Understand**

   理解验证目标和设计意图
2. **Plan**

   分解任务、建立执行计划
3. **Generate**

   生成 UVM、约束、Checker、测试场景
4. **Execute**

   Engine 调用真实 EDA 工具
5. **Analyze**

   分析失败、覆盖率和验证缺口
6. **Repair**

   提出修改并重新验证
7. **Signoff**

   确定性规则检查，生成可追溯签核证据

持续迭代，直到满足签核条件

# **三、为什么一定要把 Agent 和 Engine 分开？**

这是整个架构最核心的设计哲学。

假设让 LLM 同时负责生成代码、运行仿真和判断是否通过，会有什么问题？

| 工作        | LLM 直接负责 | SignOffAI 的设计            |
| --------- | -------- | ------------------------ |
| 理解验证需求    | 可以       | Agent                    |
| 制定验证计划    | 可以       | Agent                    |
| 生成 UVM    | 可以       | Agent                    |
| 判断代码能否编译  | 不可靠      | Compiler + Engine        |
| 判断仿真是否通过  | 不可靠      | Simulator + Engine       |
| 判断覆盖率是否达标 | 不可靠      | Coverage Engine          |
| 决定是否签核    | 不允许自行决定  | Policy + Decision Engine |

举个例子：

LLM 说：

> DMA 的地址冲突已经解决，验证通过。

但是实际上：

- 仿真只跑了一个 Seed。
- 关键 Corner Case 没有覆盖。
- 某个 Assertion 被 Disable。
- 覆盖率没有达到目标。

如果把签核权交给 LLM，就可能产生虚假的 PASS。

所以 SignOffAI 的设计是：

**Agent 可以提出 PASS 的理由，但只有确定性裁决系统能够根据签核规则和证据决定 PASS。**

# **四、Evidence 为什么这么重要？**

Evidence 不应该只是保存几个日志文件。

它要记录一项验证结论是如何产生的。

例如：

**DMA/GEMM 地址冲突验证证据链**

1. **输入证据**

   RTL 版本、Spec 版本、验证需求、约束配置
2. **生成证据**

   IR 版本、Agent 生成代码、人工修改记录
3. **执行证据**

   编译日志、仿真日志、Seed、工具版本、退出状态
4. **分析证据**

   Assertion 结果、Functional Coverage、失败归因
5. **裁决证据**

   签核规则、规则检查结果、豁免记录、最终结论

**最终结论**

可追溯的 PASS / FAIL

这样，别人问你：

> 为什么这个 DMA 模块可以签核？

你不需要让 Agent 再解释一遍，而是可以直接追溯：

- 用了哪个 RTL 版本？
- 跑了哪些测试？
- 跑了多少个 Seed？
- 覆盖率是多少？
- 哪些 Assertion 通过？
- 是否存在 Waiver？
- 签核规则是什么？

这才是工程级验证系统和普通 AI 代码生成器的区别。

# **五、Architecture 4.0 的各个子系统分别做什么？**

结合你之前提供的 Architecture 4.0 迁移情况，可以把它们理解为以下职责：

| 子系统         | 核心职责              | 解决的问题          |
| ----------- | ----------------- | -------------- |
| Agent Plane | 智能体编排与推理          | 谁来思考、规划、分析     |
| Engine      | 确定性流程控制           | 如何执行、检查、裁决     |
| IR          | 统一语义模型            | 如何描述验证任务       |
| Runtime     | EDA 工具运行环境        | 如何真正跑起来        |
| Generation  | 验证资产生成            | 如何生成 UVM、SVA 等 |
| Knowledge   | 验证知识管理            | 如何复用协议和设计知识    |
| Experience  | 历史经验积累            | 如何利用过去的失败与修复   |
| Interfaces  | CLI、Workbench 等入口 | 工程师如何使用系统      |

这里有一个容易混淆的地方：

**Generation 不是 Agent，Engine 也不是 Agent。**

例如 UVM Generation 是一项能力，可以由 Agent 提出生成需求，再由生成模块执行。Engine 管理执行流程，最终验证生成结果。

同样，Knowledge 不是简单的 RAG，Experience 也不应该只是聊天历史。它们应当逐步形成可检索、可验证、可复用的工程知识和经验。

# **六、它和 Claude Code + Skills 有什么区别？**

这是你之前一直比较关心的问题。

## **Claude Code + Skills**

**Claude Code**

通用智能编码 Agent

**CLAUDE.md / Skills / MCP**

提供 IC 验证知识、工具和工作流程

**文件、Shell、EDA 工具**

执行验证任务

优势：轻量、灵活、开发成本低，通用编码能力强。

## **SignOffAI**

**Agent Plane**

专用 IC 验证智能能力

**IR + Engine**

统一验证语义、确定性控制和裁决

**Runtime + EDA**

真实编译、仿真、回归和覆盖率

**Evidence + Signoff**

可追溯、可审计、可复现的验证结论

优势目标：将验证任务变成标准化、可执行、可审计的工程闭环。

两者并不是完全竞争关系。

Claude Code 可以作为 SignOffAI 的一种开发和智能执行工具，Skills 可以成为 Knowledge 的知识载体，MCP 可以成为 Runtime 的工具接入方式。

真正的区别不是谁调用了哪个模型，而是：

- Claude Code 更偏向通用 Agent 执行环境。
- SignOffAI 更偏向专用 IC 验证工程系统。

但是有一点必须客观说明：**架构更复杂不代表验证效果一定更好。** 如果 SignOffAI 没有更好的验证质量、更低的人工成本、更可靠的证据链，那么它就没有实际优势。

# **七、我认为你应该重点理解的三个核心**

**1. Agentic：让验证工作具备自主性**

从人工提出一个个命令，转变为 AI 理解目标、自主拆解、选择工具和持续迭代。

**2. Compilation：把验证意图转成机器执行任务**

这就是你之前提出的 Verification Compilation Methodology。把人类想验证什么，转换成 IR、约束、UVM、Checker 和执行计划。

**3. Signoff：让验证结果有可信依据**

不允许 AI 自己宣布验证成功。所有结论都必须能够追溯到真实执行结果和明确的签核规则。

# **八、我的建议：不要继续急着增加架构层**

你现在已经完成了 Architecture 4.0 的大规模物理迁移。下一阶段最重要的不是再设计 Architecture 5.0，而是证明这套系统真的能完成一个完整的 IC 验证任务。

我建议用一个 DMA 模块作为端到端验收对象：

| 验收项目       | 目标                        |
| ---------- | ------------------------- |
| RTL 理解     | 自动提取接口和关键行为               |
| 验证规划       | 自动生成验证计划                  |
| IR         | 建立 DMA Resource / Case IR |
| UVM        | 生成可编译的验证环境                |
| 约束         | 自动生成地址冲突随机约束              |
| 仿真         | 自动调用真实仿真器                 |
| Debug      | 能分析失败并提出修复                |
| Regression | 修复后自动重新回归                 |
| Evidence   | 完整记录每次执行                  |
| Signoff    | 根据确定性规则判定结果               |

**最终要验证的不是 Architecture 4.0 有多少模块，而是：给它一个 DMA 验证目标，它能不能自己完成从需求到证据、从失败到修复、从回归到签核的完整闭环。**

这才是 SignOffAI 真正应该追求的能力。
