# SignOffAI 12-Agent 架构：LLM 干了什么，传统工具该干什么

> **核心问题**：12 个 Agent 里，哪些是真正需要 LLM 的"智能判断"，哪些是把 LLM 当确定性计算工具用（杀鸡用牛刀）？每条流水线的 LLM / 传统工具分工是否合理？
>
> 日期：2026-08-10

---

## 一、先划定 LLM 和传统工具的边界

这不是哲学问题，是工程问题。LLM 调用 = 延迟 + Token 费用 + 不确定性。每一处 LLM 使用都必须有明确理由。

| | LLM 擅长 | 传统工具/脚本擅长 |
|------|----------|------------------|
| **自然语言理解** | ✅ 读 Spec、理解需求意图 | ❌ 只能做关键词匹配 |
| **结构化推理** | ✅ "这个场景会出什么问题？" | ❌ 无法处理未建模场景 |
| **代码生成** | ✅ 从自然语言描述生成代码 | ⚠️ 模板渲染可以做，但缺乏灵活性 |
| **总结/翻译** | ✅ 数据→报告、规格→结构化JSON | ❌ 只能做格式化输出 |
| **确定性计算** | ❌ 覆盖率 = hit/total，不需要 LLM 算 | ✅ 数学运算、数据聚合 |
| **大规模数据处理** | ❌ 几千行 log，LLM context 装不下 | ✅ grep/awk/Python pandas |
| **工具调用** | ❌ LLM 不会自己调 VCS/Questa | ✅ subprocess、CI runner、EDA CLI |
| **可复现性** | ❌ 同样输入跑两次结果不同 | ✅ 确定性输出 |
| **速度** | ❌ 秒到分钟级延迟 | ✅ 毫秒到秒级 |

**判断标准：**
> **如果一个 Agent 的核心逻辑可以用 100 行 Python + 一个 Jinja2 模板替代，那就不该用 LLM。**
>
> **反过来，如果 Agent 需要理解歧义、做创造性决策、处理未建模情况，LLM 是唯一选择。**

## 二、逐 Agent 分析：LLM 干了什么、传统工具干了什么

### Agent 1：`spec_planner` — 规格分析 → 测试计划

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 阅读 Spec 理解功能意图           ○ Markdown 解析   │
│  ● 识别隐含约束和 corner case       ○ 关键词提取      │
│  ● 生成测试点列表                   ○ 结构化JSON存储  │
│  ● 判断"最难验证的是什么"          ○ 去重/排序       │
│  ● 从自然语言提取接口时序           ○ YAML schema校验 │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦🟦🟦🟦⬜  ~90%
工具占比：🟩⬜⬜⬜⬜⬜⬜⬜⬜⬜  ~10%
```

**LLM 用得对不对：✅ 完全正确。** Spec 是自然语言文档，有歧义、有不完整、有隐含假设。解析 Spec 是整个流水线里**最需要 LLM 的环节**。传统工具只能做关键词匹配，无法理解"这个配置位在低功耗模式下必须保持"的语义。

**风险点：** LLM 可能遗漏测试点（false negative），也可能编造不存在的功能（hallucination）。需要 `tool_find_spec_yaml` 做 schema 校验兜底。

### Agent 2：`design_architect` — 模块层次 + 寄存器映射

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 从功能描述推导模块划分            ○ 接口类型检查   │
│  ● 决定"哪些功能放一个模块"         ○ 寄存器地址分配  │
│  ● 设计寄存器字段语义               ○ 地址冲突检查   │
│  ● 评估设计折中（面积vs灵活性）     ○ SystemRDL生成  │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦🟦⬜⬜⬜  ~70%
工具占比：🟩🟩🟩⬜⬜⬜⬜⬜⬜⬜  ~30%
```

**LLM 用得对不对：✅ 对。** 模块划分是创造性设计决策——没有"唯一正确答案"。LLM 需要理解功能内聚性、接口复杂度、时序约束才能做合理拆分。传统工具做不了这件事。

**但这里有 LLM 过度使用的风险：** 寄存器地址分配是确定性的——给定寄存器列表，地址从基地址开始对齐排列。用 LLM 生成可能产生地址冲突或非对齐。应该由 `design_architect` 的 LLM 输出**寄存器字段语义**（名称、位宽、访问类型、描述），然后由传统工具做**地址自动分配 + SystemRDL 模板渲染**。

### Agent 3：`verify_architect` — UVM 验证环境架构

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 决定需要几个 UVM Agent           ○ Jinja2渲染UVM骨架│
│  ● 设计 Scoreboard 比对策略         ○ 编译检查(vlog)  │
│  ● 选择 reference model 接入方式    ○ 文件写入        │
│  ● 生成 UVM 组件代码                ○ 静态结构校验    │
│  ● 质量自检                         ○ 健康检查(loopback)│
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦⬜⬜⬜⬜⬜  ~50%
工具占比：🟩🟩🟩🟩🟩⬜⬜⬜⬜⬜  ~50%
```

**LLM 用得对不对：⚠️ 对了一半。** 架构决策（几个 agent、scoreboard 怎么比）需要 LLM。但 UVM 代码生成已经有成熟的 Jinja2 模板方案（`tool_jinja_render`）——`uvm_driver.sv`、`uvm_monitor.sv` 这些文件是高度模板化的。

**当前问题：** `verify_architect` 的 LLM 既做架构决策，又写具体 UVM 代码。正确的分工应该是：
- LLM 输出：架构描述（组件列表 + 连接关系 + 比对策略）——这是一个 ~500 字的自然语言描述
- 传统工具执行：`tool_jinja_render` 把架构描述 + YAML 配置 → 渲染成完整的 UVM 代码
- 传统工具验证：`tool_check_compile` + `tool_check_loopback` 做编译和闭环检查

**这不是"少用 LLM"，而是"让 LLM 做决策、让工具做执行"——跟你的 `tool_protocol.py` 设计理念完全一致。**

### Agent 4：`model_agent` — C++ 参考模型

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 从功能描述推导算法行为           ○ C++编译(g++)   │
│  ● 生成 C++ 参考模型代码            ○ 自测向量验证   │
│  ● 处理 corner case 逻辑            ○ DPI-C 集成     │
│  ● 生成自测验证向量                 ○ Makefile生成   │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦🟦🟦⬜⬜  ~80%
工具占比：🟩🟩⬜⬜⬜⬜⬜⬜⬜⬜  ~20%
```

**LLM 用得对不对：✅ 对。** 从自然语言 Spec 生成算法实现是 LLM 的核心优势。传统工具无法完成这个任务。DPI-C wrapper 的生成在 `src/tools/cmodel_tools/dpi_compile.py` 里已经是传统工具在做。

**注意：** 参考模型的正确性**不能靠 LLM 保证**。自测向量验证是关键的兜底机制——如果 LLM 生成的模型算错了，自测向量应该能抓到。

### Agent 5：`write_rtl` — 写可综合 RTL

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 从功能描述 + 接口契约生成RTL     ○ 综合检查       │
│  ● 状态机设计                       ○ lint (verilator)│
│  ● 数据路径实现                     ○ 编译 (vlog/vcs)│
│  ● 时序逻辑编写                     ○ CDC检查         │
│  ● 模块集成（顶层连线）             ○ 网表比对       │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦🟦🟦⬜⬜  ~80%
工具占比：🟩🟩⬜⬜⬜⬜⬜⬜⬜⬜  ~20%
```

**LLM 用得对不对：✅ 对。** RTL 代码生成是整个流水线的核心价值——SignOffAI 的差异化就在于此。通用 Copilot/Cursor 也能写 RTL，但 SignOffAI 的不同在于：

1. **输入是结构化的**（不是随便说"帮我写个 UART"，而是有 `design_architect` 提供的完整接口契约和寄存器表）
2. **输出经过验证**（不是生成完就完事了，后面有 `test_engineer` + `regression` + `coverage` + `debug` 的完整闭环）
3. **可复现**（配合 `vagent dump` 和 manifest）

**这是一个"LLM 做填空题"的经典案例：** 骨架（接口、寄存器、模块层次）由前面的 Agent 确定，LLM 只填充模块内部逻辑。这种"约束输入 → 限定输出"的模式大幅降低了 LLM 的幻觉风险。

### Agent 6：`test_engineer` — 写测试用例

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 从测试点生成测试场景              ○ 约束求解      │
│  ● 设计随机约束策略                  ○ SV编译        │
│  ● 编写 sequence/scenario 代码       ○ 种子管理      │
│  ● 决定"什么场景最可能抓bug"        ○ 波形比对      │
│  ● 仿真参数配置                     ○ 回归调度      │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦🟦⬜⬜⬜  ~70%
工具占比：🟩🟩🟩⬜⬜⬜⬜⬜⬜⬜  ~30%
```

**LLM 用得对不对：✅ 基本正确，但有改进空间。** 生成测试场景是 LLM 的强项——"对于这个 FIFO，最容易出 bug 的是满/空边界、同时读写、reset 期间写入"这种推理传统工具做不了。

**但有一个关键问题：** 约束随机策略的一部分是**数学问题**。比如"确保 1000 次随机中有至少 50 次覆盖到 full→read→empty 这个序列"，LLM 可能给出不合理的约束从而导致覆盖率永远达不到。这方面应该有一个**约束合法性检查器**（传统工具），在 LLM 生成约束后做静态分析。

### Agent 7：`assertion_engineer` — SVA 断言生成

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 识别关键断言点                   ○ 协议模板填充   │
│  ● 推理时序关系                     ○ 断言语法检查   │
│  ● 编写 SVA 属性                    ○ 形式验证集成   │
│  ● 区分 assume vs assert            ○ 断言覆盖率     │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦⬜⬜⬜⬜  ~60%
工具占比：🟩🟩🟩🟩⬜⬜⬜⬜⬜⬜  ~40%
```

**LLM 用得对不对：⚠️ 部分合理。** 断言可以分两类：

| 断言类别 | 谁来生成 | 为什么 |
|---------|---------|--------|
| **协议断言**（APB ready/valid 握手、UART 起始位/停止位） | **传统工具**（模板填充） | 这是标准协议，不需要 LLM。一个 YAML 配置 + Jinja2 模板就够了 |
| **功能断言**（"FIFO 满时 wr_en 必须为 0"、"状态机不会卡在某个状态"） | **LLM** | 这需要理解设计意图，传统工具做不到 |

**当前问题：** `assertion_engineer` 把所有断言都丢给 LLM 生成，这会导致两个问题：
1. 协议断言可能产生细微语法错误（LLM 不保证 SVA 语法正确）
2. 浪费 Token——标准协议断言用模板一秒生成，LLM 要几秒还消耗 Token

**建议：** 先跑传统工具的协议断言模板（覆盖 80% 的机械断言），再让 LLM 补充功能断言（覆盖剩余 20% 需要推理的）。

### Agent 8：`coverage_manager` — 覆盖率收集与分析

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 解释覆盖率缺口的"语义"           ○ 收集覆盖率数据 │
│     "这 30% 没覆盖到是因为..."      ○ URG/IMC merge │
│  ● 建议补充什么测试                 ○ 生成覆盖率报告 │
│                                     ○ 覆盖率趋势图   │
│                                     ○ 按 test 分组   │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦⬜⬜⬜⬜⬜⬜⬜  ~30%
工具占比：🟩🟩🟩🟩🟩🟩🟩⬜⬜⬜  ~70%
```

**LLM 用得对不对：⚠️ LLM 是配角，传统工具是主角。** 覆盖率数据收集是纯确定性计算——URG 已经做好了，不需要 LLM 参与。LLM **只在最后一步有用：** 读覆盖率报告，用自然语言解释"为什么这些点没覆盖到"，并建议补充什么测试。

**当前最可能的问题：** `coverage_manager` 可能把 LLM 用在了不该用的地方——比如让 LLM 去"分析覆盖率数据"。覆盖率数据是数字（`85.3%`），不需要 LLM 来"分析"；需要 LLM 的是把这个数字翻译成工程师能行动的建议："line coverage 85% 是因为 FIFO 的 overflow 路径没被测到，加一个 full+write 的 test case。"

**建议：** 把 `coverage_manager` 拆成两个部分：
```
coverage_collector  → 传统工具（URG merge + 报告生成）
coverage_analyst    → LLM（读报告 + 自然语言解释 + 补测建议）
```

### Agent 9：`regression_manager` — 回归执行与结果分析

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 分析失败测试的聚类               ○ 提交/调度任务  │
│  ● 判断"回归能不能通过"            ○ dvsim 执行     │
│  ● 评估失败严重程度                 ○ 收集 pass/fail │
│                                     ○ 生成 JUnit XML │
│                                     ○ 失败趋势图     │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦⬜⬜⬜⬜⬜⬜⬜⬜  ~20%
工具占比：🟩🟩🟩🟩🟩🟩🟩🟩⬜⬜  ~80%
```

**LLM 用得对不对：⚠️ LLM 是极轻量的配角。** 回归管理本质上是**工程基础设施**——任务调度、资源管理、结果收集。你的项目已经集成了 dvsim（独立子仓库），dvsim 本身就是成熟的回归框架。

LLM 只在两件事上有价值：
1. **失败聚类分析**："这 50 个失败其实都是同一个根因——APB 接口时序不对"
2. **通过/不通过建议**："虽然 3 个 test 失败，但都是已知的 FIFO corner case，不是新引入的 bug，建议通过"

**`regression_manager` 的主体代码应该是调用 dvsim API + 结果解析，不应该有大量 LLM prompt 调优代码。** 如果这个 Agent 的 `main.py` 里满屏的 system prompt 和 langchain chain，那就是架构出了问题。

### Agent 10：`debug_engineer` — 失败分析 + 根因定位

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 读 log 定位失败原因               ○ log 解析/过滤 │
│  ● 判断是 RTL bug 还是环境 bug      ○ 波形提取      │
│  ● 关联多个失败找共同根因            ○ 错误签名匹配  │
│  ● 建议修复方向                     ○ delta-debug    │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦🟦⬜⬜⬜  ~70%
工具占比：🟩🟩🟩⬜⬜⬜⬜⬜⬜⬜  ~30%
```

**LLM 用得对不对：✅ 对。这是 LLM 最有价值的应用场景之一。** Debug 本质上是模式匹配 + 因果推理——从大量 log 中找出异常模式，然后推理根本原因。这恰恰是 LLM 擅长而传统工具做不好的。

**但有一个前提：** LLM 不应该直接读原始仿真 log（可能几十万行，塞不进 context）。正确做法是：
```
传统工具先做预处理：
  1. grep 提取 ERROR/WARNING/FAIL 行
  2. 按时间窗聚合相关事件
  3. 生成一个 ~500 行的"错误摘要"
  
LLM 再做推理：
  1. 读错误摘要
  2. 模式匹配（"这个 FAIL 和上个月的 bug #1234 一模一样"）
  3. 根因推理（"FIFO full 标志在数据写入后才更新，晚了一拍"）
  4. 路由决策（"这是 RTL bug，发给 write_rtl 修复"）
```

这正是 `src/tools/lib/sim_log.py` 该干的事——**log 预处理是传统工具的活。**

### Agent 11：`quality_assurance` — 代码审查 + 质量评分

```
┌─────────────────────────────────────────────────────┐
│  LLM 干的                           传统工具干的      │
│  ─────────                          ───────────      │
│  ● 语义级代码审查                   ○ Lint(verilator)│
│  ● 设计意图一致性检查               ○ 命名规范检查   │
│  ● 可维护性评价                     ○ 代码行数统计   │
│  ● 潜在 bug 检测                    ○ 圈复杂度       │
│                                     ○ 综合检查       │
└─────────────────────────────────────────────────────┘

LLM 占比：🟦🟦🟦🟦🟦🟦⬜⬜⬜⬜  ~60%
工具占比：🟩🟩🟩🟩⬜⬜⬜⬜⬜⬜  ~40%
```

**LLM 用得对不对：✅ 对，但需要和传统工具互补。** LLM 的代码审查能力和传统 lint 工具是互补的：

| 检查类型 | 谁来查 | 例子 |
|---------|--------|------|
| **语法/风格** | 传统 lint | 未连接的端口、非阻塞赋值用在组合逻辑、always_comb vs always_latch |
| **语义/意图** | LLM | "这个状态机少了一个状态"、"这个计数器溢出条件不对" |
| **设计规范** | 传统工具 | 命名规范、文件头注释格式 |
| **设计质量** | LLM | "这段代码嵌套太深，应该拆成子模块" |

**当前关键问题：** `quality_assurance` 是否**在 LLM 之前先跑了 lint**？如果不是，那就是让 LLM 做了传统工具该做的事。正确的顺序是：
```
Lint first → 过滤掉机械问题 → LLM 只看语义级问题 + 设计质量
```

## 五、LLM 调用的"成本账"

假设每个 LLM 调用消耗 ~2000-4000 tokens（输入+输出），DeepSeek 当前定价：

| 场景 | Agent 数 × 调用次数 | Token 估算 | 每轮成本 |
|------|---------------------|-----------|---------|
| 全量 12 Agent（无回路） | 12 × 1 | ~30K tokens | 低 |
| 带 3 轮覆盖率回路 | 12 + 3×(test+regress+cov) = 21 | ~55K tokens | 中 |
| 带 debug 修复回路 | 21 + 2×(debug+write_rtl/verify_arch) = 25 | ~65K tokens | 中高 |

**减少 LLM 调用的正确方式不是减少 Agent 数量，而是让传统工具承担更多执行工作：**
- Jinja2 模板替代 LLM 生成 UVM 骨架
- dvsim API 替代 LLM 管理回归
- URG merge 替代 LLM 计算覆盖率
- Lint 工具替代 LLM 检查语法

**这些已经在你的 `src/tools/` 里了——关键是让 Agent 的主循环把这些工具用起来，而不是绕过去。**

## 八、深层分析：哪些 LLM 任务需要"迭代收敛"、值得单开 Agent

> **核心问题**：上一章划分了"LLM 干什么 / 传统工具干什么"。但更进一步：**在 LLM 负责的那些事里，哪些是 LLM 自己也没法一次搞定的？** 哪些任务天然需要多轮迭代、验证反馈、逐步逼近正确答案？这些就是应该**单开专门 Agent** 的高难度点。

---

### 8.1 判断框架：什么任务对 LLM 来说"难"

LLM 的困难不是"概率低"，而是**当前输出的正确性无法在单次生成中自证**。一个任务如果满足以下任一条件，就属于"需要迭代收敛"的高难度任务：

| 维度 | 困难信号 | 为什么单次 LLM 搞不定 |
|------|---------|----------------------|
| **因果链长度** | 从 symptom → root cause 需要 ≥3 跳推理 | LLM 在长链推理中容易"跳步"，中间环节出错累积 |
| **正确性验证成本** | 输出正确与否不能靠"读一遍"判断，必须编译/仿真/形式验证 | LLM 无法自我验证——它不知道生成的 RTL 能不能综合 |
| **精确性要求** | 一个 bit 的偏差导致功能错误（SVA 时序、RTL 状态机、约束表达式） | LLM 对精确语法/时序的建模是模糊的，token 级别精度 ≠ bit 级别精度 |
| **搜索空间** | 问题有多个可行解，但质量差异巨大（设计架构、测试策略） | LLM 单次输出是"一个合理答案"，不是"最优答案" |
| **反馈信号稀疏** | 需要外部工具（仿真器、综合器、形式工具）才能判断对错 | 没有反馈时 LLM 对错误"浑然不觉" |
| **组合爆炸** | 需要同时满足多个约束（时序 + 面积 + 功耗 + 可测性） | LLM 没有"约束求解器"，无法保证多约束同时满足 |

**对照这个框架，就能找出真正"需要迭代收敛"的难点了。**

---

### 8.2 逐 Agent 深度拆解：难度分级 + 迭代收敛需求

#### 🔴 Tier 1：极难——必须单开 Agent，需要 3+ 轮迭代收敛

##### 1. `debug_engineer` — 根因定位 **（难度：🔴🔴🔴🔴🔴 最高）**

```
因果链长度：    ████████████████████ 5/5（symptom → error → root cause → fix direction）
正确性验证成本：████████████████████ 5/5（必须回仿真验证修复是否有效）
精确性要求：    ████████████████      4/5（时序级别的精确）
搜索空间：      ████████████████████ 5/5（根因可能在任何一层：RTL/环境/约束/时序）
反馈信号稀疏：  ████████████████████ 5/5（需要仿真器反馈）
组合爆炸：      ██████████████        3/5
```

**为什么单次 LLM 搞不定：**

```
典型 debug 链（单次 LLM 调用看看会发生什么）：

仿真 log： "UVM_ERROR @ 12345ns: data mismatch, expected=0x3F, got=0x00"

LLM 第一反应 → "可能是 FIFO 读出来的是空数据"
                ↓ 但在没有波形/信号追踪的情况下，这只是瞎猜

正确的 debug 链需要多跳推理：
  symptom: data mismatch @ 12345ns
    ↓ 跳1: 追溯写入侧——这个地址什么时候写的？
    ↓ 跳2: 写入时 addr=0x10, data=0x3F → 确认写入正确
    ↓ 跳3: 读出时 addr=0x10, data=0x00 → 写入和读出之间发生了什么？
    ↓ 跳4: 检查 memory 模型——write enable 在 clk 上升沿拉高，但地址已经变了
    ↓ 跳5: 根因定位——"地址应该在写使能之前稳定，但 RTL 把 addr 和 wr_en 同时切换了"
    ↓ fix: 在写操作时把 addr 锁存一拍
```

**为什么必须单开 Agent + 迭代收敛：**

| 迭代轮 | 动作 | LLM 的认知状态 |
|:---:|------|---------------|
| Round 1 | 读 log 摘要，提假设 | "可能是 A/B/C 三个方向之一" |
| Round 2 | 请求仿真器 dump 关键信号波形 | "A 方向排除了，B 方向有线索" |
| Round 3 | 关联多个失败的共同模式 | "50 个失败都是同一个根因" |
| Round 4 | 生成 fix，回仿真验证 | "修了之后 47/50 pass，还有 3 个是新问题" |
| Round 5 | 写 debug report，标记根因已确认 | 收敛 ✅ |

**Agent 设计要点：**
- 需要 `tool_sim_wave_dump`（信号追踪工具）
- 需要 `tool_diff_failures`（失败聚类工具）——这是传统工具的活
- LLM 只做假设生成 + 因果推理，不直接读原始 log
- 每轮迭代的假设必须可验证——"如果是 X，那么 Y 信号应该等于 Z"

##### 2. `write_rtl` — 可综合 RTL 生成 **（难度：🔴🔴🔴🔴）**

```
因果链长度：    ████████████          3/5（spec → design intent → RTL implementation）
正确性验证成本：████████████████████ 5/5（必须综合 + lint + 仿真验证）
精确性要求：    ████████████████████ 5/5（一个 always_comb vs always_latch 就决定能不能综合）
搜索空间：      ████████████████      4/5（同一功能有多种 RTL 写法）
反馈信号稀疏：  ████████████████      4/5（综合器/lint 反馈）
组合爆炸：      ████████████          3/5（面积+时序+功耗 tradeoff）
```

**为什么单次 LLM 搞不定：**

```verilog
// LLM 第一次生成的"FIFO"：
always_ff @(posedge clk) begin
    if (wr_en) mem[wr_ptr] <= wr_data;  // ← 这能综合吗？能
    if (rd_en) rd_data <= mem[rd_ptr];  // ← 但 wr_ptr==rd_ptr 时呢？
end
// → lint 报：可能的读写冲突
// → 仿真报：full 标志位晚一拍
// → 综合报：mem 被推断成分布式 RAM 而不是 block RAM（面积爆炸）
```

**迭代收敛路径：**

```
Round 1: LLM 生成初版 RTL
  ↓ lint 反馈: 3 个 warning（未连接的端口、锁存器推断）
Round 2: LLM 修 lint → 再 lint
  ↓ 综合反馈: timing violation on read path
Round 3: LLM 加流水线 → 再综合
  ↓ 仿真反馈: full flag 晚一拍，数据溢出
Round 4: LLM 修 full 逻辑 → 再仿真
  ↓ 代码审查反馈: 状态机缺了 reset 恢复状态
Round 5: LLM 补全 → 通过 ✅
```

**Agent 设计要点：**
- **关键是"约束输入"**：给 LLM 的不是"写个 FIFO"，而是 design_architect 输出的完整接口契约 + 寄存器表 + 时序图
- **反馈循环自动化**：lint→fix→relint 应该是一个自动循环，不需要人工介入
- **"填空题模式"**：模块接口、寄存器、时钟域由模板生成，LLM 只填内部逻辑
- 这个 Agent 的核心竞争力不是 LLM 好，而是**工具链的反馈速度**——lint 能在 2 秒内返回结果，LLM 就能快速迭代

##### 3. `spec_planner` — 规格分析 → 测试计划 **（难度：🔴🔴🔴🔴）**

```
因果链长度：    ████████████████      4/5（spec → 功能点 → 测试点 → corner case → 风险判断）
正确性验证成本：████████████████      4/5（测试点是否覆盖了所有功能？只能靠 review）
精确性要求：    ██████████            2/5（自然语言输出，容错性高）
搜索空间：      ████████████████      4/5（corner case 空间无限）
反馈信号稀疏：  ████████████████████ 5/5（几乎零反馈——除非后面覆盖率阶段发现有 gap）
组合爆炸：      ██████████            2/5
```

**为什么单次 LLM 搞不定：**

这是整个流水线里**反馈信号最稀疏**的环节。LLM 读完 spec 生成 50 个测试点——你怎么知道有没有漏？唯一的验证方式是到后面覆盖率阶段才发现"咦，这个功能没人测"，但那时已经太晚了。

```
单次 LLM 的典型遗漏模式：
  Spec: "ADC 支持单端和差分两种输入模式，通过寄存器 adc_mode 切换"

  LLM 生成的测试点：
    ✅ test_adc_single_ended_mode
    ✅ test_adc_differential_mode
    ❌ test_adc_mode_switch_during_conversion  ← 漏了！
    ❌ test_adc_mode_switch_glitch_protection   ← 也漏了！
    ❌ test_adc_power_cycle_retains_mode         ← 根本没想到

  后面 debug_engineer 发现 bug 时：
  "这个 corner case 在 spec 里有提到但 spec_planner 没生成测试点"
```

**为什么必须迭代收敛：**

| 迭代轮 | 触发 | 做什么 |
|:---:|------|--------|
| Round 1 | 初始读取 spec | 生成基础测试点列表 |
| Round 2 | design_architect 输出寄存器表 | 补充寄存器相关的测试点（field-level） |
| Round 3 | assertion_engineer 输出断言列表 | 交叉检查：断言覆盖了哪些测试点？还缺什么？ |
| Round 4 | coverage_manager 报覆盖率缺口 | 补充漏掉的测试点 |
| Round 5 | report_generator 阶段 | 最终 review：所有 spec 功能点都覆盖了吗？ |

**Agent 设计要点：**
- **多轮交叉验证**：spec_planner 的测试点需要跟 assert、cover、design 三个维度的输出做交叉检查
- **"反向追溯"机制**：从覆盖率缺口反向追踪到 spec 里的哪个功能点没被测
- **对抗性 review**：用一个独立的 LLM 角色来"挑战"测试点列表——"如果我想让这个设计出 bug，哪里是最薄弱的？"

##### 4. `assertion_engineer` — 功能断言生成 **（难度：🟡🟡🟡）**

```
因果链长度：    ████████████          3/5（设计意图 → 时序关系 → SVA property）
正确性验证成本：████████████████      4/5（必须形式验证或仿真才能确认断言正确）
精确性要求：    ████████████████████ 5/5（SVA 语法极其精确，时钟偏差一个 cycle 断言就误报或漏报）
搜索空间：      ██████████            2/5（断言点由设计结构决定）
反馈信号稀疏：  ██████████████        3/5（形式工具可以给 counterexample）
组合爆炸：      ██████████            2/5
```

**为什么单次 LLM 搞不定——SVA 的"精确性陷阱"：**

```systemverilog
// 设计意图："request 发出后，必须在 5 个周期内收到 grant"
// LLM 第一次写的断言：
property req_grant;
    @(posedge clk) req |-> ##[1:5] grant;  // ← 这是对的吗？
endproperty
// 问题：如果 req 持续为高，每个周期都会启动一个新的 assertion thread
//       → 可能在仿真中产生几百个活跃 thread，拖慢仿真
// 正确写法需要考虑 "req 上升沿" 而不是 "req 为高"

// LLM 第二次修正：
property req_grant;
    @(posedge clk) $rose(req) |-> ##[1:5] grant;  // ← 好了很多
endproperty
// 问题：如果 grant 在 req 之前就为高呢？pass 了但其实不该 pass
// 需要加 antecedent condition

// LLM 第三次修正：
property req_grant;
    @(posedge clk) $rose(req) && !grant |-> ##[1:5] grant;  // ← 接近正确
endproperty
// 问题：reset 期间不应该检查
// LLM 第四次修正：
property req_grant;
    @(posedge clk) disable iff (rst_n) $rose(req) && !grant |-> ##[1:5] grant;
endproperty
// → 这才是一个"对"的断言，经历了 4 轮迭代
```

**迭代收敛路径：**

```
Round 1: LLM 从 design/spec 推断断言点 + 生成初版 SVA
  ↓ 形式工具反馈: 3 个 assertion 有 counterexample
Round 2: LLM 读 counterexample → 修断言（加前置条件、改时序窗口）
  ↓ 形式工具再跑: 1 个 assertion 仍然有 counterexample，2 个 pass
Round 3: LLM 精修最后一个断言 → 全 pass ✅
  ↓ 同时，仿真中跑这些断言 → 发现 1 个 assertion 产生大量 vacuous pass
Round 4: LLM 加覆盖检查 → assertion 不仅要 pass，还要有意义的 pass
```

**Agent 设计要点：**
- 协议断言（APB/UART/SPI 标准握手）走模板，这部分不需要迭代
- 功能断言才是需要迭代的——每轮迭代必须有**形式工具 counterexample** 作为反馈
- "vacuous pass" 检测很重要——断言 pass 了不代表断言写对了

##### 5. `verify_architect` — UVM 环境架构 **（难度：🟡🟡🟡）**

```
因果链长度：    ████████████          3/5（DUT 接口 → 组件分解 → 连接拓扑 → 比对策略）
正确性验证成本：████████████████      4/5（必须编译 + loopback 测试）
精确性要求：    ████████████          3/5（SystemVerilog 语法 + UVM 宏精确）
搜索空间：      ████████████████      4/5（同一 DUT 的验证环境有 N 种架构）
反馈信号稀疏：  ██████████            2/5（编译器和 loopback 反馈明确）
组合爆炸：      ██████████            2/5
```

**迭代收敛需求在于"架构决策 → 编译验证"循环：**

```
Round 1: LLM 输出架构 → 传统工具 Jinja2 渲染 UVM 骨架
  ↓ 编译失败: agent_apb 的 monitor 端口和 interface 信号名不匹配
Round 2: LLM 修正接口连接 → 重新渲染 → 再编译
  ↓ 编译通过但 loopback 失败: scoreboard 的 expected 永远为空
Round 3: LLM 修 scoreboard 连接 → 重新渲染 → loopback pass ✅
```

**但文档前面也说了——代码渲染应该走 Jinja2。** 所以这个 Agent 的迭代不是"LLM 反复生成代码"，而是：
- **LLM 输出架构描述（自然语言 JSON）** → 这需要 1-2 轮 review
- **传统工具渲染代码** → 这需要 2-3 轮 compile→fix 循环，但 fix 的是模板参数，不是 LLM

##### 6. `test_engineer` — 测试用例生成 **（难度：🟡🟡🟡）**

LLM 占比 70%，但真正难的部分不是"写测试"，而是**约束随机策略 + 覆盖率驱动的迭代**。

**迭代收敛路径：**

```
Round 1: LLM 从测试点生成基础 sequence + 随机约束
  ↓ 仿真: 覆盖率 60%
Round 2: LLM 读覆盖率缺口 → 调整约束（拓宽/收窄） → 加定向 test
  ↓ 仿真: 覆盖率 85%
Round 3: LLM 读剩余缺口 → 调整随机种子策略 → 补充 corner case sequence
  ↓ 仿真: 覆盖率 92%（接近收敛）
Round 4: LLM 分析剩余 8% → 判断哪些是无法覆盖的（dead code）vs 需要更多仿真时间
```

**真正的难点是"约束设计"——这是数学问题，不是语言问题：**
- "确保在 1000 次随机中至少有 50 次覆盖 full→read→empty 序列" → 这是**概率约束**，LLM 可能写出永远达不到这个分布的约束
- 需要传统工具的约束求解器做验证，LLM 只负责"语义翻译"（测试意图 → 约束表达式）

---

#### 🟢 Tier 3：中等——1-2 轮即可收敛，不需要独立 Agent

##### 7. `design_architect` — 模块层次 + 寄存器映射 **（难度：🟢🟢）**

```
因果链长度：    ██████████            2/5（功能 → 模块划分 → 接口定义）
正确性验证成本：████████              2/5（接口冲突检查是传统工具的活）
精确性要求：    ██████████            2/5（寄存器字段定义）
搜索空间：      ██████████████        3/5（架构选择空间大但收敛快）
```

**收敛容易的原因：** 设计架构的"好坏"主要靠人 review 判断，不是靠工具迭代。LLM 出 2-3 个候选方案 → 工程师选一个 → 一次调整就收敛了。

**不需要单开 Agent**——放在 spec_planner 的下游作为子步骤即可。

##### 8. `model_agent` — C++ 参考模型 **（难度：🟢🟢🟡）**

```
因果链长度：    ██████████            2/5（功能描述 → 算法实现）
正确性验证成本：████████████          3/5（自测向量验证）
精确性要求：    ██████████████        3/5（算法正确性比 bit 级别精确性重要）
搜索空间：      ██████                1/5（算法实现比较确定）
```

**收敛容易的原因：** 自测向量能很快判断正确性——如果 LLM 生成的模型跑自测向量 pass，基本就对了。如果 fail，LLM 看 mismatch 就知道哪里错了。

**迭代次数通常 1-2 轮。** 不需要独立 Agent——可以和 write_rtl 共享一个"代码生成+自测"循环。

##### 9. `quality_assurance` — 代码审查 **（难度：🟢🟢）**

因果链短、反馈明确（lint 先过一遍）、搜索空间小（代码已经写好了，只做审查）。

**不需要迭代收敛——单次 LLM 审查 + lint 前置过滤足够。**

---

##### 10. `coverage_manager`（analyst 部分）— 覆盖率缺口解释 **（难度：🟢🟢）**

文档前面已经说了要拆成 collector + analyst。Analyst 部分是单次 LLM 调用——"这 15% 没覆盖到是因为 XXX，建议加 YYY 测试"。

**不需要迭代。但需要触发下游迭代**——analyst 的输出不是"答案"而是"action"（触发 test_engineer 的下一轮迭代）。

---

##### 11. `regression_manager` — 回归分析 **（难度：🟢🟢）**

主体是 dvsim 传统工具。LLM 只在失败聚类这一个点上有价值。因果链短（失败 log → 聚类 → 共同根因假设），1-2 轮即可。

---

##### 12. `report_generator` — 签核报告 **（难度：🟢）**

纯聚合 + 自然语言翻译。**全流水线最容易的任务。** 不需要迭代。

### 8.4 关键结论：6 个点需要单开 Agent + 迭代收敛

按优先级排列：

| 优先级 | Agent | 为什么单开 | 迭代收敛的核心机制 | 预估开发复杂度 |
|:---:|------|-----------|-------------------|:---:|
| **P0** | `debug_engineer` | 流水线里最难的任务，因果链 5 跳以上，没有迭代就是瞎猜 | 假设生成→仿真验证→排除/确认→下一轮假设 | 🔴 最高 |
| **P1** | `write_rtl` | 单次 LLM 生成的 RTL 基本不可能一次过 lint+综合+仿真 | lint→fix→relint→synth→fix→resynth→sim | 🔴 高 |
| **P1** | `spec_planner` | 反馈信号极度稀疏——漏了测试点要到 cover 阶段才发现 | 多阶段交叉验证（spec×design×assert×cover） | 🟡 中高 |
| **P2** | `assertion_engineer` | SVA 精确性要求极高，一个 cycle 偏差断言就废了 | 形式验证 counterexample → 修断言 → 再验证 | 🟡 中 |
| **P2** | `test_engineer` | 约束设计是数学问题，LLM 天然不擅长 | 覆盖率反馈 → 调约束 → 补定向 test → 再覆盖 | 🟡 中 |
| **P3** | `verify_architect` | UVM 编译循环，但代码渲染走模板后迭代需求下降 | 编译失败 → 修模板参数/Jinja2 上下文 | 🟢 中低 |

### 8.5 设计范式：迭代收敛 Agent 的通用架构

上面 6 个需要迭代的 Agent 共享同一个设计模式——**"生成-验证-修复"循环**：

```
┌─────────────────────────────────────────────────────────────┐
│                    迭代收敛 Agent 通用架构                     │
│                                                               │
│   ┌──────────┐     ┌──────────┐     ┌──────────┐             │
│   │  LLM     │────▶│ 传统工具  │────▶│ 判断     │             │
│   │  生成    │     │  验证    │     │ 收敛?    │             │
│   │ (决策层) │     │ (执行层) │     │          │             │
│   └──────────┘     └──────────┘     └────┬─────┘             │
│        ▲                                 │                    │
│        │          ┌──────────┐           │ No                 │
│        └──────────│ 反馈摘要  │◀──────────┘                   │
│                   │ (传统工具)│                               │
│                   └──────────┘                                │
│                                                               │
│   关键设计原则：                                                │
│   1. LLM 只看"反馈摘要"（传统工具预处理后的结构化信息）          │
│   2. 每一轮迭代必须产生可验证的输出（编译/仿真/形式验证）        │
│   3. 收敛条件必须明确（"0 error + 0 warning + loopback pass"）  │
│   4. 最大迭代次数硬限制（防止无限循环烧 token）                 │
│   5. 每轮迭代记录 artifact manifest（可追溯"为什么改了三轮"）   │
└─────────────────────────────────────────────────────────────┘
```

**与文档第六章的呼应：**

> "我们不是把 LLM 当'万能生成器'用，而是把它嵌入到 **UVM 骨架 + Jinja2 渲染 + 契约校验** 的工程流程中。LLM 只做'完形填空'，不决定整体结构。"

**迭代收敛 Agent 就是这句话的工程实现：LLM 在每一轮里只做一次"完形填空"，填完立刻由传统工具验证。验证不过就把错误信息喂回去再填一次。** 这不是"让 LLM 更聪明"，而是"让反馈循环更短"。

### 8.6 行动路线图

| 阶段 | 做什么 | 预计工作量 |
|:---:|--------|:---------:|
| **Phase A** | 先加固 6 个传统工具（`sim_log` 预处理、lint 反馈、form 验证、约束检查器、编译反馈、覆盖率 merge）——没有好工具就没有好反馈，没有好反馈 LLM 迭代就是瞎迭代 | 2-3 周 |
| **Phase B** | 实现"生成-验证-修复"循环框架（`src/core/iterative_loop.py`）——所有需要迭代的 Agent 都用同一个循环框架 | 1 周 |
| **Phase C** | 按 P0→P1→P2→P3 顺序，逐个 Agent 接入迭代循环 | 每个 Agent 2-5 天 |
| **Phase D** | 收敛条件可观测化——dashboard 上能看到每个 Agent 迭代了几轮、每轮的 diff 是什么 | 1 周 |

**最核心的一句话：**
> **不是"让 LLM 一次生成对的"，而是"让 LLM 快速失败、快速修复"。迭代收敛的本质是缩短反馈循环——从"人工几小时"缩短到"自动化几秒"。**
