# 学习笔记：模型、Agent 与本项目的真实组合边界

## 1. 现有角色入口（正常 ReAct 执行方向）

```text
用户目标
  ↓
既有 orchestration / CLI / specialist 兼容入口（按具体模式而定）
  ↓
reaction.registry.create_agent：选择一个独立 Domain Agent
  ↓
agents.Agent + Runner（有界轮次）
  ↓
ProjectBudgetedModel：保留统一 LLM 预算、审计和决策校验
  ↓
未选择工具？ → 缺观察/无效决策 → INCOMPLETE，而不是宣称 Agent 已执行
选择工具？ → SDK FunctionTool 执行受限读取或复用既有生成器
  ↓
真实工具观察 → 下一轮模型推理（可继续、提问或形成候选）
  ↓
CANDIDATE / INCOMPLETE / PENDING_HUMAN / NOT_RUN
  ↓
确定性 Engine / 人工复核；Agent 文本不能自我签署 PASS
```

`Runner` 是真正的 SDK ReAct 循环承载者，**不是所有任务都先经过一个统一的
LangGraph 总路由器**，也不是每次都必须查询 Weaviate 或写 MongoDB。

## 2. 可选组合，不等于默认已启用的产品链路

- Weaviate client 已安装，但未有服务端连接验证；应按需求单独接检索 Tool。
- `pymongo==4.1.7.0` 在清单中保持注释；TinyMongo 安装不等于切换了项目记忆后端。
- 当前模型调用仍走项目的预算/审计出口与 SDK `Model` 适配层，不因安装了 LiteLLM
  就自动替换成另一条未审计的 Provider 通道。
- OpenTelemetry/Sentry 包可导入，不能仅凭安装宣称全程自动埋点或服务端上报。
- 缺 API key、缺 Spec、缺执行后端或审批挂起时，要如实保持未完成状态。

## 3. 模型的适用性与限制（教学讨论）

   好，直接说哪些场景不适合用 DeepSeek（或任何兼容 OpenAI 协议的第三方模型），按严重程度排。

一、硬伤级：完全不能用或风险极高的

1. 数据不能出公司的场景

• 金融核心交易逻辑

• 医疗患者数据

• 政府涉密/内部系统

• 未公开专利/商业机密

原因：把源码、日志或需求发给外部服务可能跨信任边界与组织授权范围。
是否允许必须依据数据分类、部署地域、供应商承诺和组织审查决定，不能默认放行。

解法：本地部署（Ollama/vLLM）+ 内网，或者根本不用外部模型。

2. 需要 100% 确定性输出的场景

• 编译器/解析器生成（要能编译过）

• 数学证明/形式验证断言

• 硬件描述语言（RTL）关键路径

• 税务/法律计算

原因：LLM 本质是概率生成，哪怕 99% 正确，剩下 1% 是灾难。

解法：模型只生成草稿 → 必须过编译器/验证工具/人工审核 → 模型不拍板。

3. 强实时/低延迟场景

• 高频交易决策

• 自动驾驶实时推理

• 工业控制闭环

• 在线游戏 AI

原因：LLM 推理延迟 200ms~数秒，而且波动大（思考模式更慢）。

解法：这类场景根本不该用 LLM，用规则引擎/传统 ML 模型。

二、会出大事级：能跑但风险大

4. 安全关键系统

• 航空航天控制逻辑

• 医疗设备控制

• 电力/交通信号

• 核电站监控

原因：模型幻觉 = 安全事故，没有"差不多就行"的余地。

解法：模型只能做"辅助文档查询/培训"，不能参与控制决策。

5. 需要严格结构化输出的场景

• 生成数据库 schema

• 生成 API 契约（OpenAPI spec）

• 生成配置文件（YAML/JSON 给程序直接消费）

不同提供方、模型和配置对结构化输出的支持不同。即使存在 JSON mode，也不能保证业务字段一定满足契约，必须解析、校验并采取回退策略。

解法：加 pydantic 校验 + retry 循环，或者换模型。

6. 多步工具调用链（每一步依赖上一步结果）

• 数据库迁移脚本生成+执行+验证

• 自动化运维（改配置→重启→检查→回滚）

• CI/CD 流水线自动修复

原因：第 3 步工具调用如果格式飘了，整个链断掉，而且可能产生破坏性副作用。

解法：每步人工确认，或只用确定性脚本。

7. 需要长程记忆/跨会话状态的场景

• 个人助理（记住你上个月说过啥）

• 长期项目跟踪

• 用户偏好学习

可用的模型协议接口不自动等价持久化记忆。调用方必须依据实际 SDK、会话和工作区策略管理上下文，并受模型窗口与项目预算限制。

解法：按需求接向量库和受控业务存储。项目虽有 weaviate-client 与 TinyMongo 包，但未启用原注释的 pymongo，也未证明数据库已连通。长期记忆需要显式会话、工作区和权限策略，不可由安装包保证。

三、性价比差级：能用但没必要

8. 简单规则就能搞定的事

• 表单校验

• 固定流程审批

• 定时任务

• 数据格式转换

原因：杀鸡用牛刀，LLM 又慢又贵又不稳定。

解法：写代码，别调模型。

9. 需要最新实时信息的场景

• 实时股价/汇率

• 今天的新闻/天气

• 实时交通

原因：模型知识有截止日期，不联网就没有实时数据。

解法：工具调用接实时 API，但这意味着你依赖工具稳定性，模型本身帮不上忙。

10. 需要精确计数的场景

• "这段代码的圈复杂度是多少"

• "这个文件有多少行"

• "这两个集合的交集"

原因：LLM 数数会错，哪怕你让它"仔细数"。

解法：写脚本/用工具，别让模型数。

四、EDA/ChipStack 专项（你之前提到的）

不能让模型单独干的：

环节 为什么不能只靠模型

综合约束（SDC） 时序约束错 = 芯片废了

布局布线策略 影响良率，不能靠"猜"

形式验证断言 模型生成的断言只能当提示，必须 Jasper 证明

电源/时钟树 物理层面，模型不懂寄生参数

签核（signoff） 任何 EDA 流程的最终签核必须工具+人工

模型能辅助但不能拍板的：

• RTL 初稿生成

• testbench 骨架

• 覆盖率点建议

• 日志/波形异常归类

• 文档问答

五、判断标准（一张表自查）

问自己三个问题：

1. 错了会怎样？
   • 重跑一下就行 → ✅ 可以用

   • 赔钱/出事故/芯片报废 → ❌ 不能用或只能辅助

2. 需要 100% 准确吗？
   • 大概对就行（摘要、建议、初稿） → ✅ 可以用

   • 必须精确（计算、控制、约束） → ❌ 不能单独用

3. 数据能出去吗？
   • 公开/脱敏数据 → ✅ 可以用

   • 涉密/合规限制 → ❌ 不能出公司

三个问题里有一个 ❌，就得加护栏或者换方案。

六、一句话总结

LLM 适合"生成初稿 + 辅助判断 + 信息整理"，不适合"精确计算 + 安全关键 + 数据敏感 + 实时控制"。

> 能用的场景：让它干活，人审核。

不能用的场景：别让它碰，写代码/用专业工具。
