一个 case 到底由哪些层次的属性组成，这些属性怎么分层、怎么正交、怎么组合。
一、case 不是一个点，是一个结构 
传统写法把 case 当成一个点：
tc_bp_tail_01
名字里塞了场景、条件、方法，信息密度高但无法检索、无法组合。
抽象后，一个 case 是若干属性的组合：
对象 + 条件 + 取值 + 方法 + 检查 + 环境
所以 case 的组织，本质上是属性分层与组合。
二、六个属性层 

层级
名称
作用
举例
L1
对象 Object
测什么主体
流控、调度、地址
L2
子对象 SubObject
主体的细分
接收流控、发射流控
L3
维度 Dimension
会变化的条件
指令长度、反压模式
L4

定向、随机、组合
L6
检查 Check
验证什么
功能、白盒、性能

一个 case 就是这六层的实例化。
三、L1 对象层：主体分类 
对象层回答“case 属于哪个主体”。
流控 FlowControl
调度 Schedule
地址 Address
错误 Error
复位 Reset
配置 Config
性能 Performance
注意对象的判断标准：
能否用外部行为描述
是否是验证主体
“流控”可以成为对象，因为它是外部可观察的行为类别。
四、L2 子对象层：对象的能力点 
对象下面继续切分能力点。
例如流控：
FC-01  接收侧流控
FC-02  发射侧流控
FC-03  跨端口流控
FC-04  流控恢复
FC-05  流控与资源联动
子对象不是“另一个 feature 类型”，而是对象的细分维度。
五、L3 维度层：会变化的条件的集合 
维度层就是你说的“流控有指令长度、反压模式”。
维度是一组相关字段的集合。
例如“流控维度”：
指令长度
反压模式
反压比例
反压持续时间
反压接口
反压与队列联动
维度的判定标准：
这些字段共同描述同一个变化因素
它们之间可以互相约束
它们通常一起随机
所以“维度”不是单个字段，而是一组语义相关的字段。
六、L4 字段层：真正有取值的东西 
字段 field 是最终承载取值的单元。
以流控维度为例：
field: 指令长度
  values: 1 / 8 / 64 / MAX

field: 反压模式
  values: 无 / 首拍 / 尾拍 / 持续 / 随机

field: 反压比例
  values: 0% / 10% / 50% / 100%

field: 反压持续时间
  values: 1拍 / 8拍 / 持续 / 超阈值
维度负责归类，字段负责取值。
很多 testplan 把维度当字段、把字段当 case，层级错位，最后必然重复。
七、维度的内部字段关系 
同一维度内的字段不是平铺的，常见三种关系：
并列 
反压接口：ld0 / ld1 / 两者独立
字段之间无依赖。
联动 
指令长度 与 反压持续时间 联动
长指令更容易触发长时反压。
互斥 
无反压 与 反压比例=100% 互斥
必须在约束里表达。
维度内部要维护一张字段关系表：
字段A × 字段B：独立 / 联动 / 互斥
否则约束写不清。
八、L5 方法层：生成方式 
方法层独立于对象和维度。
D    定向    固定取值
RND  随机    约束随机
G    组合    枚举笛卡尔积
RPLY 重放    失败 seed
SPCL 专项    针对性变异
同一个维度，三种方法都可以生成：
指令长度 = 1            → D
指令长度 随机 1~MAX      → RND
指令长度 × 反压模式 16组 → G
方法不是 case 类型，而是 case 的生成属性。
九、L6 检查层：一个 case 往往不止一种检查 
这是最容易漏的一层。
流控 case 可以同时有三种检查：
功能检查：指令是否完整
白盒检查：队列深度、资源计数
性能检查：反压解除后吞吐恢复
所以检查也是属性，不是 case 名的一部分。
CHECK-FUNC   功能正确
CHECK-WBOX   白盒状态
CHECK-PERF   性能指标
一个 case 可以同时挂多个检查标签。
十、环境属性：容易被遗漏 
除了上面六层，case 还受环境影响：
工具版本
RTL 版本
约束版本
接口版本
配置档位
seed
编译选项
这些不作为 case 主体，但要作为执行属性记录：
每个 case 执行时必须带环境指纹
失败 case 才能复现
十一、一个完整 case 的属性实例 
以“流控”为例：
Case ID        : TC-FC-RECV-BP-01
对象 L1        : FlowControl 流控
子对象 L2      : 接收侧流控
维度 L3        :
  - 指令长度
  - 反压模式
  - 反压比例
  - 反压持续时间
字段 L4        :
  指令长度     = MAX
  反压模式     = 尾拍
  反压比例     = 100%
  反压持续时间 = 超过阈值
方法 L5        : 组合 G
检查 L6        :
  - 功能：指令完整、无丢失
  - 白盒：队列不溢出、资源平衡
  - 性能：解除后恢复时间达标
环境           : 工具/RTL/约束版本
期望结果       : 不死锁、不丢数、可恢复
这个 case 的属性全部可检索、可组合、可扩展。
十二、属性分层带来的好处 
检索 
找“所有尾拍反压” → 筛 field:反压模式=尾拍
找“所有 MAX 指令” → 筛 field:指令长度=MAX
组合 
维度 A × 维度 B
就是两组字段的笛卡尔积
扩展 
新增一种反压模式
只需在“反压模式”字段加取值
去重 
两个 case 如果对象+子对象+字段取值相同
就是重复，只是方法不同
统计 
流控维度覆盖率 = 各字段取值命中数 / 总取值
十三、字段的类型化 
字段可以进一步类型化，方便自动化：
枚举型    反压模式：首拍/尾拍/持续
范围型    指令长度：1 ~ MAX
集合型    并发数：1 / 4 / 8
加权型    依赖类型：dist 加权
联动型    指令长度 ↔ 总元素数
类型决定：
如何生成
如何计算覆盖率
如何做边界分析
十四、一个对象多个维度时如何组织 
对象“流控”下面有维度：
D_length   指令长度
D_mode     反压模式
D_ratio    反压比例
D_dur      反压持续时间
D_if       反压接口
D_res      与资源联动
组织方式不是平铺 6 个维度，而是：
先建维度交叉矩阵
再按必交叉程度建交叉组
|          | 长度 | 模式 | 比例 | 时长 | 接口 | 资源 |
| 长度     |  —   |  ★   |  ✓   |  ★   |  ✓   |  ★   |
| 模式     |  ★   |  —   |  ★   |  ★   |  ✓   |  ✓   |
| ...      |      |      |      |      |      |      |
每个 ★ 就是一个交叉组，对应一组字段组合。
十五、case 命名如何体现属性 
传统命名塞属性：
tc_fc_recv_max_len_tail_bp_full_rnd_01
太长且属性边界不清。
建议用属性表，命名只保留必要层次：
TC-<对象>-<子对象>-<方法>-<NN>

TC-FC-RECV-G-01
其余属性放在 case 元数据里：
字段取值
环境信息
检查项
覆盖率映射
命名是人读的坐标，属性表是机器可检索的坐标。
十六、case 属性表的最小字段集 
case_id          唯一 ID
object           对象
sub_object       子对象
dimensions       涉及维度
fields           字段取值集合
method           生成方法
related_cases    关联 case
cross_group      所属交叉组
checks           检查项
cover_bins       覆盖仓映射
environment      环境指纹
expected_result  预期结果
这张表才是 case 的真正主体，文件名只是索引。
十七、从属性到组合生成 
有了属性分层，可以自动生成 case：
1. 选对象 + 子对象
2. 选维度集合
3. 取各维度字段取值
4. 选生成方法
5. 计算笛卡尔积
6. 输出 case 属性表
例如：
对象：流控
维度：指令长度 × 反压模式
字段取值：长度 4 种 × 模式 5 种 = 20 个 case
方法：组合
case 不再是手写，而是属性组合的产物。
十八、属性之间的正交性 
这套方法成立的前提是属性正交：
对象 / 子对象 / 维度 / 字段 / 方法 / 检查
如果正交被破坏，例如：
“尾拍”既是维度取值，又是 case 名前缀
“随机”既是方法，又是一种反压模式
就会出现重复和冲突。
判断标准：
同一个信息只能存在于一个层级。
 
十九、常见层级错位 
把字段当维度 
维度：尾拍反压
字段：无
正确做法：
维度：反压模式
字段：首拍 / 尾拍 / 持续
把维度当对象 
对象：反压比例
反压比例是流控维度下的字段，不是独立对象。
把方法当维度 
维度：随机反压
字段：各种比例
“随机”是方法，不是反压属性。
把检查当对象 
对象：白盒检查
白盒是检查属性，不是测试主体。
二十、抽象后的最小模型 
Object
  └─ SubObject
       └─ Dimension
            ├─ Field 1
            ├─ Field 2
            └─ Field N
                 └─ Values

Case = Object × SubObject × Dimensions × Methods × Checks
这就是 case 组织的完整属性模型。
二十一、一句话总结 
case 的组织不是“起个名字”，而是六个属性层的组合：
对象定义主体，子对象定义能力点，维度归字段，字段承载取值，方法决定生成，检查定义验证目标。
 
你举的例子正好是这个模型的核心：
流控是对象
指令长度是维度
反压模式也是维度
两者下面的取值才是字段
只要坚持“维度只归类、字段才取值、方法不混入对象”，case 的组织就会自然变得可检索、可组合、可扩展，覆盖率缺口也就能直接映射回某个字段的取值组合。
