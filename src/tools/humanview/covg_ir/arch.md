# 功能覆盖率纵横矩阵方法学

> 版本 V.1.0.0 ｜ 适用：NPU/SoC 模块级与子系统级功能覆盖率建模  
> 定位：定义"覆盖率组如何切分、如何交叉、如何采样、如何判定完备"的通用方法学，供 CMD_SCH 及其他模块复用。

---

## 1. 概述

### 1.1 目的

本文档定义功能覆盖率的**二维矩阵建模方法学**：纵向按功能契约切覆盖率组，横向按生命周期路径切覆盖序列，两者交叉成矩阵，配合约束、采样、证据链与收敛流程，形成"需求 → 覆盖点 → 约束 → 激励 → 覆盖率 → 证据 → 签核"的闭环。

解决的核心问题：

- 单一维度切覆盖率组，能证明"功能点打到了"，但**不能证明"功能路径走通了"**；
- 覆盖率报告只看 bin 命中率，**不能区分"场景发生过"和"功能被正确验证"**；
- 跨功能组的组合场景没有归属，容易在组与组之间漏掉；
- 覆盖率与需求追溯之间缺少可审计的映射。

### 1.2 适用范围

- 模块级功能覆盖率建模（如 CMD_SCH、DMA、仲裁器、队列管理）；
- 子系统级端到端覆盖率建模；
- 需要向评审、签核、回归管理提供可审计覆盖证据的项目。

不适用于：纯代码覆盖率（line/cond/fsm/toggle）的建模——代码覆盖率是另一套度量，本文档只在"功能覆盖率与代码覆盖率协同"一节简要引用。

### 1.3 术语

| 术语 | 含义 |
|---|---|
| **纵向维度（Column）** | 按功能契约切分的覆盖率组，回答"功能点是否打到" |
| **横向维度（Row）** | 按生命周期路径切分的覆盖序列，回答"路径是否走通" |
| **矩阵格子（Cell）** | 功能组 × 路径的交叉点，回答"该功能在该路径阶段是否正确" |
| **覆盖点（Coverpoint）** | 单个信号或表达式的取值覆盖 |
| **组内交叉（Intra-group Cross）** | 同一覆盖组内两个覆盖点的交叉 |
| **跨组交叉（Inter-group Cross）** | 跨越两个覆盖率组的交叉，需特殊实现架构 |
| **路径覆盖点（Path Coverpoint）** | 序列级覆盖点，覆盖生命周期阶段组合 |
| **证据链（Evidence Chain）** | 功能覆盖 + 时序断言 + 数据比对 + 路径覆盖四层证据 |
| **采样域（Sampling Domain）** | 按 monitor 侧划分的采样范围，决定 covergroup 的物理归属 |

## 2. 问题背景：为什么单一维度不够

### 2.1 纵向切组的价值

按功能契约切组（如 ITYPE / INSTB / DEP / UNIT / ISSUE / MEM / RSP / EXCP / PERF / CSR）有三个直接好处：

- **需求追溯清晰**：每个组对应一类 CDD 特性，Feat 到组的映射一目了然；
- **评审好分工**：每组独立定目标、独立评审、独立分配负责人；
- **批次好收敛**：覆盖率报告按组展示，缺口定位快。

### 2.2 纵向切组的盲区

但纵向切组只回答"功能点是否发生"，不回答"功能路径是否走通"。典型盲区：

- 乱序发射这条路径横跨 `INSTB → DEP → ISSUE → UNIT → RSP` 五组，每组只看自己那段，没有组对"完整路径"负责；
- 每组都 100%，但"依赖未解除不发射、解除后发射、反压恢复不丢不重"这条端到端路径可能从未被完整验证；
- 组与组之间的组合场景（如"ISTB 满 + RAW 依赖 + 反压"同时发生）没有归属，容易漏。

### 2.3 结论：需要两个正交维度

**纵向回答"功能点打没打到"，横向回答"路径通不通"，矩阵格子回答"功能在路径阶段是否正确"。** 三者缺一不可。

## 3. 覆盖率矩阵模型

### 3.1 两个正交维度

```
                横向：生命周期路径（Row）
                ┌─────────────────────────────────────┐
                │ 直发到done │ 存ISTB后发射 │ 反压恢复 │ ... │
   ┌────────────┼───────────┼─────────────┼─────────┼─────┤
纵 │ ITYPE      │     ●     │      ●      │    —    │     │
向 │ INSTB      │     —     │      ●      │    ●    │     │
： │ DEP        │     ●     │      ●      │    —    │     │
功 │ ISSUE      │     ●     │      ●      │    ●    │     │
能 │ UNIT       │     ●     │      ●      │    —    │     │
组 │ MEM        │     ●     │      ●      │    ●    │     │
   │ RSP        │     —     │      —      │    ●    │     │
   │ EXCP       │     —     │      —      │    —    │     │
   └────────────┴───────────┴─────────────┴─────────┴─────┘
```

- **列（纵向）**：`CG_<MODULE>_<CONTRACT>`，每列一个覆盖率组，管功能点与组内交叉；
- **行（横向）**：`CG_<MODULE>_PATH`，每行一条生命周期路径，管序列覆盖；
- **格子**：由跨组交叉 + SVA + scoreboard 负责，管"该功能在该路径阶段是否正确"。

### 3.2 纵向维度：功能契约切组

**切分原则**：

1. **一个组对应一类功能契约**，不按 RTL 子模块切，按"对外承诺的行为"切。例如 CMD_SCH 的 DEP 组对应"数据依赖处理契约"，不是"scoreboard 子模块"。
2. **组内覆盖点数量控制在 4~8 个**，超过则考虑拆分；少于 2 个则考虑合并。
3. **组间边界要写清楚**：重叠的覆盖点（如 DEP 和 ISSUE 都涉及 hazard）必须声明"主覆盖点归哪个组、交叉归哪个组"，避免重复统计。
4. **每组必须有独立的覆盖目标、约束映射、批次归属、签核条件**。

**纵向组的必备内容**：

| 项 | 说明 |
|---|---|
| CG ID / 名称 | 唯一标识 |
| 需求 ID | 映射到 Feat/规格条目 |
| 功能描述 | 一句话说清契约 |
| 覆盖点列表 | 每个覆盖点的采样信号、bin 数、非法 bin |
| 组内交叉 | 有意义的组合 |
| 约束映射 | 每个 bin 至少一个约束 |
| 采样位置 | 在哪个 monitor、什么 iff 条件 |
| 目标 | 覆盖点 100%、交叉 100%、非法 bin 0 命中 |

### 3.3 横向维度：生命周期路径切行

**路径枚举方法**（不穷举，按阶段 + 分支组合）：

1. **划阶段**：把指令/事务生命周期划成 6~8 个阶段，例如  
   `握手 → 译码 → 依赖判定 → 发射决策 → 执行 → 完成/释放 → 返回`
2. **列每阶段关键分支**：

   | 阶段 | 关键分支 |
   |---|---|
   | 握手 | 正常握手 / 反压保持 |
   | 依赖判定 | 无依赖 / RAW / WAW / WAR / 结构冲突 |
   | 发射决策 | 直发 / 存 ISTB / ISTB 发射 / 反压 |
   | 执行 | 单组件 / 2~5 组件并行 / 双槽 / TMU 竞争 |
   | 完成释放 | 正常 done / 提前 release / rls 与 done 同拍 |
   | 返回 | 无返回 / 状态返回 / 数值返回 / 乱序 tag |

3. **组合主路径**：从每阶段选一个分支，组合成 5~10 条主路径，覆盖正向、反压、异常三大类。
4. **不可达组合进 `ignore_bins`**，并记录理由。

**横向路径的必备内容**：

| 项 | 说明 |
|---|---|
| 路径 ID | 如 `P_DIRECT_FULL`、`P_STORED_ISSUED` |
| 阶段序列 | 如 `cmd_hs → no_dep → direct → start → done → rls` |
| 覆盖点 | 序列 coverpoint 或 `covergroup` 的序列采样 |
| 绑定 SVA | 该路径上的时序断言 |
| 绑定 scoreboard | 该路径上的数据/资源检查项 |
| 定向用例 | 构造该路径的 sequence |
| 状态 | 未覆盖 / 已覆盖 / 已签核 |

**建议的 5~8 条主路径模板**（以指令调度类模块为例）：

| 路径 ID | 阶段序列 |
|---|---|
| `P_DIRECT_FULL` | 握手 → 无依赖 → 直发 → start → done → rls |
| `P_STORED_ISSUED` | 握手 → 有依赖 → 存 ISTB → 依赖解除 → ISTB 发射 → start → done → rls |
| `P_BP_RECOVER` | ISTB 满 → 反压 → 释放 → refill → 发射 → done |
| `P_PARALLEL` | 多组件无依赖 → 同拍并行 → 各自 start/done |
| `P_OOO_RSP` | 多 xd=1 下发 → 乱序 done → 按 tag 返回 |
| `P_ILLEGAL_BLOCK` | 非法指令 → 中断 → block → 清中断 → 恢复 |
| `P_EARLY_RLS` | 发射 → rd/wr_release → 提前释放 → done |

### 3.4 交叉矩阵：格子语义

格子 = 功能组 × 路径，语义是**"该功能在该路径阶段被验证到"**。填充规则：

| 符号 | 含义 |
|---|---|
| 🟢 | 该功能在该路径阶段有覆盖点命中 + SVA 通过 + scoreboard 通过 |
| 🟡 | 部分证据缺失（如命中但 SVA 未触发，或 scoreboard 未实现） |
| 🔴 | 证据链不完整，不能签核 |
| — | 该功能与该路径无契约关系（不适用） |

**格子不是"必须全部 🟢"**。不适用的格子标 `—` 并记录理由；适用的格子必须 🟢 才能签核。

### 3.5 矩阵完备性判定

矩阵完备需同时满足：

1. **纵向完备**：每个覆盖组的覆盖点 100% 命中、组内交叉 100% 命中、非法 bin 0 命中；
2. **横向完备**：每条主路径的序列 coverpoint 100% 命中，且绑定 SVA 0 fail、绑定 scoreboard 0 fail；
3. **格子完备**：每个适用格子 🟢，🟡 必须转为 🟢 或走豁免流程；
4. **需求追溯完备**：每个 Feat 至少映射到一个功能组和一个路径，无孤立需求、无孤立覆盖点；
5. **豁免完备**：所有 `ignore_bins` 和豁免格子有理由、有审批、有记录。

## 4. 覆盖点分类学

### 4.1 五类覆盖点

| 类型 | 回答的问题 | 归属 | 实现位置 |
|---|---|---|---|
| **功能点覆盖点** | 单个信号/取值打到了吗 | 纵向组 | 对应采样域的 covergroup |
| **组内交叉** | 同组两个功能点的组合打到了吗 | 纵向组 | 同组 covergroup 内 `cross` |
| **跨组交叉** | 跨组组合打到了吗 | 矩阵格子 | 独立 `cross_cg` 或复制 coverpoint |
| **路径覆盖点** | 生命周期路径走通了吗 | 横向 PATH 组 | 序列采样 covergroup |
| **状态机覆盖点** | 关键 FSM 状态/转移覆盖了吗 | 纵横均可引用 | FSM 状态 coverpoint + 转移 coverpoint |

### 4.2 各类覆盖点的建模规则

**功能点覆盖点**：

- 采样信号必须来自 monitor，不来自 sequence；
- 用 `iff` 限定有效周期（如 `cmd_valid && cmd_ready`），避免空闲周期反复采样虚高；
- 显式写 bin，不用 auto-bin；长尾值单独成 bin，不糊成区间；
- 非法取值用 `illegal_bins`，命中即 fail。

**组内交叉**：

- 只做有意义组合，不做笛卡尔积；
- 无意义组合用 `ignore_bins`，必须写理由；
- 交叉 bin 数量控制在可审阅范围（建议 ≤ 20），超过则拆分成多个交叉。

**跨组交叉**：

- 实现方式见第 5 章；
- 每个跨组交叉必须有明确的"验证意图"（验证什么契约），不能为了交叉而交叉；
- 跨组交叉的 bin 数计入矩阵格子，不计入单个纵向组的目标。

**路径覆盖点**：

- 用序列采样或 `covergroup` 的 `sample` 配合路径状态机；
- 每个路径 bin 必须绑定至少一个 SVA 和一个 scoreboard 检查项；
- 路径 bin 未命中时，要能定位卡在哪个阶段（建议路径状态机每个阶段也做覆盖点）。

**状态机覆盖点**：

- 状态覆盖：每个合法状态至少一个 bin，非法状态 `illegal_bins`；
- 转移覆盖：每条合法转移至少一个 bin，非法转移 `illegal_bins` 或 SVA 卡住；
- 状态机覆盖与 PATH 组交叉，验证"状态转移正确"而非仅"状态到达过"。

### 4.3 覆盖点与矩阵格子的映射

每个覆盖点/交叉必须在矩阵里声明归属：

```yaml
coverage_point: cp_hazard_type
group: CG_DEP
matrix_rows: [P_DIRECT_FULL, P_STORED_ISSUED]
matrix_columns: [DEP]
evidence:
  sva: [SVA_DEP_NO_ISSUE_BEFORE_READY]
  scoreboard: [SB_HAZARD_ORDER]
```

没有矩阵归属的覆盖点是孤立覆盖点，评审时必须解释为什么存在。

## 5. 跨组交叉的实现架构

### 5.1 SystemVerilog 的硬约束

**IEEE 1800 明确规定：`cross` 只能在同一 `covergroup` 内的两个 `coverpoint` 之间定义，不支持跨 `covergroup` 的 `cross`。** 这意味着：

- 如果按 10 个纵向组实现为 10 个独立 `covergroup`，`X_ISSUE_DEP_PATH = cross(cp_hazard_type, cp_issue_path)` **编译不过**；
- 如果实现为一个大 `covergroup`，"10 个组"只是逻辑命名，不是物理分组。

### 5.2 三种实现方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 单一大 covergroup** | 所有 coverpoint 放一个 covergroup，跨组 cross 合法 | 实现简单，跨组 cross 直接可用 | 采样域混在一起，事件驱动采样难做；报告分组靠命名前缀，易混乱 | 小型模块、采样域单一 |
| **B. 复制 coverpoint** | 把跨组交叉需要的 coverpoint 复制到目标 covergroup，再做 cross | 各 covergroup 独立，跨组 cross 合法 | coverpoint 重复定义，维护成本高，覆盖率重复统计 | 交叉数量少、采样域清晰 |
| **C. 独立 cross collector（推荐）** | 纵向组各自独立 covergroup；建一个 `*_cross_cg`，从联合 item 采样所有需要交叉的信号 | 分组清晰、跨组 cross 合法、采样域可控 | 需要维护联合 item 和 cross collector | 中大型模块、跨组交叉多 |

### 5.3 推荐架构：逻辑分组 + 独立 cross collector

```
┌─────────────────────────────────────────────────────────┐
│                     cmdsched_monitor 层                   │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐ │
│  │ decode   │  │ scoreboard│ │ sp_inst  │  │ int_perf │ │
│  │ monitor  │  │ monitor   │ │ monitor  │  │ monitor  │ │
│  └────┬─────┘  └────┬─────┘  └────┬─────┘  └────┬─────┘ │
└───────┼─────────────┼─────────────┼─────────────┼───────┘
        │             │             │             │
        ▼             ▼             ▼             ▼
┌──────────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ itype_cg     │ │ dep_cg   │ │ rsp_cg   │ │ excp_cg  │
│ instb_cg     │ │ issue_cg │ │          │ │ perf_cg  │
│ unit_cg      │ │ mem_cg   │ │          │ │ csr_cg   │
│ (纵向组)      │ │ (纵向组) │ │ (纵向组) │ │ (纵向组) │
└──────────────┘ └──────────┘ └──────────┘ └──────────┘
        │             │             │             │
        └─────────────┴──────┬──────┴─────────────┘
                             ▼
                 ┌───────────────────────┐
                 │  cmdsched_cross_cg    │
                 │  (联合 item 采样)      │
                 │  X_ISSUE_DEP_PATH     │
                 │  X_MEM_OCC_MST        │
                 │  X_MEM_GRAN           │
                 │  X_CSR_EXCP           │
                 │  ...                  │
                 └───────────────────────┘
                             │
                             ▼
                 ┌───────────────────────┐
                 │  cmdsched_path_cg     │
                 │  (横向 PATH 组)        │
                 │  P_DIRECT_FULL        │
                 │  P_STORED_ISSUED      │
                 │  P_BP_RECOVER         │
                 │  ...                  │
                 └───────────────────────┘
```

**关键设计点**：

1. **纵向组各自独立 covergroup**，放在对应采样域的 `uvm_subscriber` 里，事件驱动采样；
2. **`cross_cg` 单独一个 covergroup**，从联合 `cmdsched_item` 采样，只包含跨组交叉需要的 coverpoint；
3. **`path_cg` 独立 covergroup**，用路径状态机 + 序列采样；
4. **联合 item 由 monitor 层统一发布**，各 collector 通过 `uvm_analysis_port` 订阅，避免信号重复采集；
5. **报告合并**：`urg` 支持多 covergroup 合并，报告里按 `option.name` 前缀分组展示纵向组、`cross`、`path` 三类。

### 5.4 跨组交叉的清单管理

跨组交叉必须单独维护一张表，不能散落在各组的文档里：

| 交叉 ID | 交叉对象 | 涉及组 | Bin 数 | 验证意图 | 绑定 SVA/SB |
|---|---|---|---|---|---|
| X_ISSUE_DEP_PATH | cp_hazard_type × cp_issue_path | DEP × ISSUE | 6 | 依赖判定与发射决策一致 | SVA_DEP_ISSUE |
| X_MEM_OCC_MST | cp_spad_tile_occ × cp_mst_id | MEM × UNIT | 20 | 各 MST 的 tile 占用释放 | SB_TILE_OCC |
| X_CSR_EXCP | cp_csr_excep_en × cp_int_type | CSR × EXCP | 4 | excep_en 屏蔽行为 | SVA_EXCEP_MASK |
| X_CSR_PERF | cp_csr_perf_en × cp_perf_paral | CSR × PERF | 4 | icg 开启后统计正确 | SB_PERF_CNT |

## 6. 约束与矩阵的对准

### 6.1 约束三维

| 维度 | 取值 | 说明 |
|---|---|---|
| **作用域** | 单指令 / 序列 / 场景 | 约束挂在哪个类上 |
| **目标** | 功能点 / 组内交叉 / 跨组交叉 / 路径 / 反压异常 / 参数 | 约束对准哪类覆盖 |
| **形态** | 随机分布 / 定向 / 禁止 / 参数遍历 | 约束在回归里怎么用 |

### 6.2 约束到矩阵的映射规则

**规则 1：一个 bin 至少一个约束**  
纵向功能点 bin 由单指令约束打，组内交叉 bin 由序列约束打，跨组交叉 bin 由序列或场景约束打，路径 bin 由场景约束打。

**规则 2：一个约束至少对准一个 bin**  
禁止写"为了随机而随机"的约束；每个约束必须在覆盖点映射表里有目标。

**规则 3：路径约束绑定 checker**  
每条路径的约束必须同时声明"构造什么路径 + 期望哪个 SVA 通过 + 期望哪个 scoreboard 检查通过"。只构造路径不检查，不算路径覆盖。

**规则 4：禁止约束有理由**  
`ignore_bins` 和禁止约束必须记录理由和审批，不能用来掩盖缺口。

**规则 5：参数约束分配置跑**  
编译参数类覆盖点（如 `P_INST_BUF_DP`）每个配置单独回归、单独合并覆盖率，不能混在一个 covergroup 里统计。

### 6.3 充分性准则

| 覆盖对象 | 充分性准则 |
|---|---|
| 每个 Feat | ≥1 正向用例 + ≥1 边界/反压用例 |
| 每个功能组的分支 bin | ≥1 用例命中 |
| 每个跨组交叉 | ≥1 场景约束 + 绑定 SVA/SB |
| 每条主路径 | ≥1 定向用例 + 绑定 SVA/SB |
| 每个异常类型 | ≥1 定向用例 |
| 每个反压源 | ≥1 用例 |
| 每个 CSR 配置组合 | ≥1 用例 |
| 每个状态机状态/转移 | ≥1 用例命中或 SVA 覆盖 |

## 7. 采样架构

### 7.1 事件驱动采样 vs 时钟采样

| 方式 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **时钟采样** | `@(posedge clk)` 每拍采 | 简单 | 空闲周期反复采同值，覆盖率虚高；难区分有效/无效周期 |
| **事件驱动采样（推荐）** | `write(item)` 在事务发生时采 | 反映真实场景；有效周期明确 | 需要 monitor 层发布 item |

**推荐**：纵向组和 cross 组用事件驱动采样；PATH 组用路径状态机触发采样；仅在无法定义"事务"的场景用时钟采样 + `iff` 限定。

### 7.2 按采样域拆分 collector

每个采样域一个 `uvm_subscriber` 派生类，只订阅该域的 item：

| 采样域 | 负责的组 | 采样时机 |
|---|---|---|
| decode-ISTB 侧 | ITYPE、INSTB、UNIT（部分） | 指令解码/入 ISTB 时 |
| scoreboard 侧 | DEP、ISSUE、MEM | 发射/占用/释放变化时 |
| sp_inst 侧 | RSP | 返回握手时 |
| int_perf 侧 | EXCP、PERF、CSR | 中断/性能/CSR 写时 |

### 7.3 `iff` 与有效周期

- `cmd_valid && cmd_ready`：指令握手成功才采指令类覆盖点；
- `rsp_valid && rsp_ready`：返回握手成功才采返回类覆盖点；
- `start_valid`：start 拉高才采 start 相关覆盖点；
- `perf_en`：性能统计使能才采性能覆盖点。

**复位、空闲、握手未成功周期不采样。**

### 7.4 `illegal_bins` / `ignore_bins` 策略

**`illegal_bins` 约束的是 DUT 输出/状态的非法，不是激励的非法。**

- 正确用法：`cp_int_type` 里 `illegal_bins int2 = {2'b11}` —— 中断编码 11 是非法状态，命中即 DUT bug；
- 错误用法：`cp_prim_type` 里把 `PRIM_RESERVED` 设为 `illegal_bins`，同时又有 `illegal_seq` 故意下发 `PRIM_RESERVED` 测中断 —— 这会直接冲突。

**处理"故意注入非法激励"的正确做法**：

- 方案 A：非法激励放在独立 covergroup 或 `option.weight = 0` 的实例里，不参与主覆盖率统计；
- 方案 B：把"非法激励被正确拦截"建模为 normal bin（如 `cmd_int0`），真正 `illegal_bins` 的是"拦截后 DUT 进入了非法状态"；
- 方案 C：异常定向测试单独跑、单独报告，不与主回归覆盖率合并。

**`ignore_bins` 必须写理由**，且理由要可审计（如"架构不可达""规格明确不支持"），不能用来掩盖"约束没写好"。

## 8. 证据链判定模型

### 8.1 四层证据

| 证据层 | 回答的问题 | 数据来源 | 判定 |
|---|---|---|---|
| **功能覆盖** | 场景发生过吗 | covergroup 命中 | bin 命中 = 通过 |
| **时序断言（SVA）** | 时序行为对吗 | 仿真断言统计 | 0 fail 且被触发 = 通过；未触发 = 部分；fail = 失败 |
| **数据比对（Scoreboard）** | 数据/资源结果对吗 | scoreboard 比对日志 | 检查项 pass = 通过；未实现 = 缺失 |
| **路径覆盖（PATH）** | 完整路径走通了吗 | PATH 组序列覆盖 | bin 命中且绑定 SVA/SB 通过 = 通过 |

### 8.2 矩阵格子的证据状态

| 状态 | 判定条件 |
|---|---|
| 🟢 | 功能覆盖命中 + SVA 通过 + Scoreboard 通过 + PATH 命中 |
| 🟡 | 四层证据中至少一层"部分"（命中但 SVA 未触发、scoreboard 未实现等） |
| 🔴 | 四层证据中至少一层"失败"或"缺失" |
| — | 该功能与该路径无契约关系，已记录理由 |

### 8.3 证据视图

建议生成四张可审计视图（详见配套工具）：

1. **用例 × 证据层矩阵**：每个用例提供哪几层证据；
2. **功能契约 × 证据层热力图**：每个 Feat 的证据链完整度；
3. **功能组 × 路径矩阵**：每个格子的证据状态；
4. **缺口与豁免看板**：缺口根因、补齐动作、责任人、豁免记录。

## 9. 收敛与签核

### 9.1 收敛标准

| 条件 | 标准 |
|---|---|
| 纵向功能覆盖点 | 100% bin 命中 |
| 组内交叉 | 100% 有意义组合命中 |
| 跨组交叉 | 100% 有意义组合命中 |
| 横向路径覆盖 | 每条主路径 100% 命中 + SVA 0 fail + SB 0 fail |
| 矩阵格子 | 所有适用格子 🟢，🟡 转 🟢 或走豁免 |
| 非法 bin | 0 命中 |
| 忽略 bin | 已审批并记录理由 |
| 需求追溯 | 无孤立需求、无孤立覆盖点、无孤立格子 |
| 种子基线 | 已建立并纳入回归 |
| 回归稳定性 | 固定回归集覆盖率稳定，连续 3 批增长 < 2% 视为平台期 |

### 9.2 缺口处理流程

```
发现未覆盖 bin / 🟡 格子
    ↓
分析根因
    ├─ 约束可覆盖但种子没抽到 → 加种子 / 调约束权重
    ├─ 约束覆盖不到 → 补约束 / 写定向 case
    ├─ 证据层缺失（SVA/SB 未实现）→ 补 checker
    ├─ 架构不可达 → 申请豁免（需审批）
    └─ 命中了但结果错 → DUT bug，进 debug
    ↓
补齐 → 重跑 → 更新矩阵
```

### 9.3 豁免管理

豁免记录必须包含：Bin/格子、所属组、豁免理由、审批人、日期、影响评估。  
**豁免不能用于掩盖"约束没写好"或"checker 没实现"。**

- 每个路径至少映射一个 Feat；
- 每个格子至少映射一个 SVA 或 SB。
