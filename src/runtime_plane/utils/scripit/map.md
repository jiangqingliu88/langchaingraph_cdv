### NPU 验证工程师核心工作流 (Standard Flow)

NPU 验证的核心目标：**确保芯片加速器（NPU）在 RTL 层面的行为，完全符合算法的期望，且在物理硬件上能跑出正确的结果。**

整个流程可以严格分为 **5 个阶段**：

#### 阶段一：算法参考模型 (Golden Model - PyTorch)
**目的：确立数学正确性。**

*   **动作**：由算法团队或验证团队使用 **PyTorch (或 TensorFlow)** 搭建算子参考模型。
*   **产出**：随机生成或基于真实模型提取的测试向量 (Test Vectors)，并计算出一个 **高精度（通常为 FP32）的理想结果**。这个结果是数学上的“绝对真理”。
*   **岗位要求**：熟悉 Python/PyTorch，能编写测试数据生成脚本（如我们写过的 `gen_hal_test_case.py`）。懂常见 AI 算子（Conv2d, MatMul, Add, Gelu 等）的数学原理。

#### 阶段二：行为级/周期级参考模型 (TLM/SystemC Model)
**目的：将“数学真理”翻译成“硬件能理解的语言”。**

*   **动作**：编写 C++ 或 SystemC 模型，**精确模拟 NPU 底层硬件的微架构行为**。
    *   处理硬件特有的**流水线延迟 (Pipeline Latency)**。
    *   处理自定义的数据格式（如 FP8 E4M3、Block Float、MX 格式的**舍入机制**）。
*   **产出**：生成一组**“硬件期望值 (Golden Hex)”**。这组数据是 SystemC 考虑了硬件精度损失后算出来的。
*   **岗位要求**：熟练掌握 C++/SystemC。**极其重要的考点**：理解 `IEEE 754` 标准、非标准浮点数的取整规则、浮点数误差模型。**为什么不能直接用 PyTorch 结果给 RTL 跑？** 因为 PyTorch 是在 GPU/CPU 上算的，它的取整规则和您的 NPU 硬件可能不一样，直接比对会产生大量“假报错”。

#### 阶段三：RTL 仿真与测试激励 (Verilog/SystemVerilog & C Testbench)
**目的：运行真实的硬件电路，并喂入数据。**

*   **动作**：在仿真器 (VCS, Xcelium, Questasim) 中运行 NPU 的 RTL 代码。
    *   **主核启动**：运行我们在 Python 里生成的 C 测试用例（ARM/RISC-V 核心）。
    *   **DMA 搬运**：将阶段二中 SystemC 模型计算时需要的**输入数据**，搬运到 NPU 的物理内存地址 (`BASE_ADDR_IN0`)。
    *   **驱动调用**：C 代码调用 HAL 接口，配置 NPU 寄存器启动计算。
*   **岗位要求**：了解 AMBA/AXI 总线协议、DMA 机制、以及裸机 C 代码在嵌入式 RISC-V/ARM 核心上的交叉编译和运行机制。

#### 阶段四：硬件结果回读与自动比对 (Scoreboarding - `DV_verify.py`)
**目的：判断硬件的 RTL 是否算对了。**

*   **动作**：
    *   C 代码将 NPU 算出的结果从物理地址回读到 CPU 内存 (`host_output`)。
    *   **调用验证脚本 (Scoreboard)**：CPU 上的 C 程序将 硬件实际输出 和 阶段二生成的 Golden Hex 进行逐元素比对。
*   **核心知识点（您的强项）**：
    *   **计算误差公式**：绝对误差 (Absolute Error)、相对误差 (Relative Error) 的计算。
    *   **容差设置 (Tolerance)**：根据数据格式设置容差。例如：INT8 误差必须为 0；FP16/FP32 允许 `1e-3` 的相对误差；FP8 允许 `5e-2` 的误差。**必须学会区分“RTL Bug 导致的误差”和“精度格式导致的固有误差”。**

#### 阶段五：仿真结束与回归测试 (End-of-Sim & CI/CD)
**目的：自动化地判断测试通过或失败。**

*   **动作**：C 代码发现比对失败 (`Fail_Count > 0`) 后，调用 **`simulation_end(1)`**（向特定系统寄存器写 1）；如果成功，调用 `simulation_end(0)`。
    *   仿真器 (TLM) 捕捉到此事件，立即结束仿真，并返回退出代码 (Exit Code)。
    *   后端 CI 系统（Jenkins/GitLab CI）根据退出代码将当前代码提交标记为 **PASS** 或 **FAIL**。
*   **岗位要求**：了解回归测试 (Regression Test) 的概念，懂得如何大批量、并发地跑测试，以保证每次代码更新后功能不被破坏。

### 💡 面试/工作时常见的高频考点 (Interview Q&A)

根据咱们的探讨，如果您去面试 NPU 验证岗，大概率会遇到以下问题，您可以这样来回答：

**Q1：PyTorch 结果和 RTL 结果对不上，你怎么排查？**
*   **答**：首先看误差值。如果误差在 `1e-4` 级别，先排除舍入差异，检查 **SystemC 模型和 PyTorch 的量化/取整方式是否一致**。如果误差巨大（如方向反了），马上检查 **C Testbench 的基地址是否正确**，或者 **DMA 搬运的数据长度是否对**。

**Q2：SystemC 模型的作用是什么？**
*   **答**：SystemC 是硬件验证的**“金标准 (Golden Model)”**。它不仅要验证算法的功能性，更重要的是**模拟硬件的微架构行为**（如流水线、握手协议、非标浮点取整）。它和 RTL 进行 **Bit-True** 或 **ULP 级** 的精细对比，把 PyTorch 的高精度结果转化为符合 NPU 精度的底层硬件期望值。

**Q3：验证脚本中的误差容差 (Tolerance) 应该怎么设？**
*   **答**：不能一概而论。对于 Int8/Int16 必须严格要求 **0 误差**，因为整数计算必须完全精确。对于浮点（FP16, BF16, FP8），由于硬件和仿真模型的取整顺序可能不同，需要设置合理的相对误差阈值（例如 `1e-3` 或 `1e-2`）。**目标是不放过真实的 RTL Bug，但排除因标准差异导致的假报错 (False Failures)。**

当您发现 RTL（或硬件 NPU）跑出来的结果，和 PyTorch 的高精度参考结果存在误差时，**第一步绝对不是去改硬件 RTL，也不是直接改验证脚本的容差（Tolerance）去掩盖问题**。

正确的排查逻辑，应该像剥洋葱一样，分 **4 个层次**去解决。

---

### 第一步：确认误差的量级（定性分析）

在动手之前，先看误差有多大。这决定了您的排查方向：

*   **误差极大（> 10% 或者完全不同）**：这**不是精度问题，而是逻辑/数据流问题**。通常是因为：数据传输错位（地址不对）、DMA 长度不对、算子配置参数错误（比如 `axis` 方向搞反了）。
*   **误差极小（在 `1e-3` ~ `1e-5` 之间）**：这才是正儿八经的**“精度/量化”问题**。这也是我们现在要重点讨论的。

---

### 第二步：逐级下探 —— 谁和谁不对齐？

在 NPU 验证中，通常有 3 个角色：
1.  **PyTorch (软件高精度)**：FP32，经典舍入。
2.  **SystemC/C++ 参考模型 (TLM)**：模拟硬件的微架构和具体舍入规则。
3.  **RTL (硬件)**：实际电路。

**排查顺序（必做动作）：**

1.  **比对 TLM 和 PyTorch**：跑一个简单的定点/浮点测试。如果 TLM（SystemC）和 PyTorch 在**同样的输入**下，得到的结果就存在微小误差。这说明**问题出在 TLM 模型本身**，它是严格按照硬件设计的，但还没有去“拟合”PyTorch 的数学约束。
2.  **比对 RTL 和 TLM**：如果 RTL 和 TLM 的结果是**精确一致的**（比如二进制 `0x40400000` 对 `0x40400000`），但两者都和 PyTorch 存在误差。恭喜您，**这说明您的硬件逻辑设计完全没问题**。您需要处理的是硬件和主流软件框架的“语义对齐”问题。

---

### 第三步：系统性的解决方案（如何把误差“搞没”）

经过第二步，如果您确定是**“硬件/SystemC 与 PyTorch 的固有误差”**，而您又必须让它们对齐（这在量产芯片验证中极其重要），您有以下 **3 个终极手段**（按照难度从低到高）：

#### 手段 1：在 SystemC/TLM 模型中采用“逐比特匹配”（最通用）
*   **原因**：PyTorch 虽然标准，但在 `FP16` 的累加上，或者存在 FMA（融合乘加）时，它的舍入行为是**黑盒**（底层依赖 CUDA/CUDA 核心）。
*   **做法**：不指望 TLM 用数学公式算出来。而是**让 TLM 模型直接读取经过编译器/量化器（Quantizer）处理过的二进制文件**。也就是让编译器决定硬件的位表示，TLM 不再计算，而是直接作为“门卫”去校验硬件 RTL。

#### 手段 2：修改对齐脚本的“数据对比基准”（高阶工程师做法）
*   如果 `TLM` 和 `RTL` 算出来的结果非常一致，但就是和 `PyTorch` 有 0.001 的误差，而您无法修改硬件逻辑。
*   **做法**：**修改验证脚本，不要用 PyTorch 直接生成的数据作为对比基线。** 对比基线应该是 **“从硬件经过反向解析出来的数据”**。
    *   比如，把硬件的 `0x40E00000` 反推回浮点数 `7.0`。这个 `7.0` 就是实测值，不再和 PyTorch 比对，而是作为一个客观的值传递到下一层级。

#### 手段 3：硬件和编译器联合排查（仅当误差不可接受时）
*   如果误差导致最终 AI 模型的推理精度下降了 0.5% 以上，这就不可接受了。
*   **做法**：**您的 NPU 硬件团队需要修改 RTL 的微架构。**
    *   *场景*：在矩阵乘累加中，一个浮点数乘完后，是先截断再累加，还是先累加再截断？两者误差虽然小，但累积起来很大。这种问题只能通过**修改 RTL（增加累加器位宽）** 或 **修改编译器调度策略** 来解决。

---

### 第四步：如果实在消除不了误差怎么办？(设置合理的 Tolerance)

经过上述深度排查，如果您确认这是硬件为了极致性能（面积/功耗）故意做的**“不精确匹配（Inexact Match）”**，那么**验证脚本**就需要设置**针对此算子的误差容忍度（Tolerance）**。

**这里有一个行业通用的“避坑原则”：**

1.  **绝对不要让 `DV_verify.py` 对所有算子都用一套全局容差（比如全局 1%）**。
2.  **正确的做法是“按算子、按层设置不同容差”**：
    *   对于标准的 `Add`, `Mul`, `MatMul`：容差设定为极小的 `1e-4` (0.01%)。
    *   对于非标算子（如 `Softmax`, `LayerNorm`, `Gelu`）：由于涉及到指数运算和除法，硬件实现受舍入影响极大。容差可以放宽到 `1e-2` (1%) 或 `1e-1` (10%)。
3.  **在日志中记录下为什么这个算子放大了容差**。
    *   最后提交的验证报告中必须写明：“`Gelu` 算子在超过 10000 次测试中，最大相对误差为 0.05%，在行业基线 `0.1%` 以内，通过测试。”
